## 结论与范围

建议先处理配置状态一致性与对外兼容说明，再收敛远程图片缓存的任务归属和重试语义，最后按实际热点决定是否优化合成层预遍历。所有实现方向均复用现有 scene、Signal/Owner、PaintCommand 与共享服务，不另起 UI 框架、不绕过宿主适配边界。

现有增量布局、fragment 复用、裁剪保护、诊断设施及文档分区已经具备基础，不宜以“全量重写”作为默认优化路径。本文的性能项只证明存在可减少的工作，不承诺帧率提升。

开始时已存在未提交的 [规格索引](../../../docs/开发者文档/规格文档/README.md) 与 [uicore 施工规划](../../../docs/开发者文档/规格文档/施工规划-uicore编译单元.md)；本轮保留它们，不将其中规划视为已实现事实，也不替其作产品目标裁决。

## 代码优化建议

### C1：删除 null 键不能只用返回值判断是否发生修改

**证据。** [DefaultMutableConfig.remove](../../../src/main/java/club/heiqi/config/DefaultMutableConfig.java#L128) 先调用 Map.remove，再以 oldValue != null 决定是否置 dirty、清除 pristine 和发送 REMOVE。[节点转可变值](../../../src/main/java/club/heiqi/config/DefaultMutableConfig.java#L384) 将显式 null 节点转为 Java null，因此“删除不存在的键”和“删除存在但值为 null 的键”返回值相同。[saveTo](../../../src/main/java/club/heiqi/config/DefaultMutableConfig.java#L170) 与 [asImmutable](../../../src/main/java/club/heiqi/config/DefaultMutableConfig.java#L233) 在 pristine 时仍返回原始树。

**触发与后果。** 从含显式 null 键的配置加载后，未做其他修改，直接 remove 该键：data 已删除键，但 pristine 仍可能为 true，保存或取不可变快照仍使用带旧键的 originalNode；dirty 与 REMOVE 事件也漏更新。这是底层可变配置入口的静态推导，不能扩大为所有 ModernConfig 保存路径都受影响。

**建议。** 将“键是否存在”与“旧值是否非 null”分开判断。实际删除后统一更新 data、dirty、pristine 和变更事件，保留删除不存在路径不发变更的语义。不要通过强制每次保存都重建树绕过该问题，否则会损失未修改配置的注释保留能力。

**验收。** 以 JSON/YAML 显式 null 键加载为起点，删除后验证 asMap().containsKey、asImmutable、保存再读取、dirty 与 REMOVE 事件一致；另验证不存在键的删除仍无副作用。[MutableConfigTest](../../../src/test/java/club/heiqi/config/MutableConfigTest.java#L63) 的现有 remove 用例使用非 null 值，不能替代此场景。建议在该测试族补真实回归用例，而非源码字面断言。

### C2：配置修改后保留已有注释元数据

**证据。** [保存分支及已知限制](../../../src/main/java/club/heiqi/config/DefaultMutableConfig.java#L170) 明确注明：未修改用原树保留注释，修改后从 data 重建而丢失注释。[不可变节点重建](../../../src/main/java/club/heiqi/config/DefaultMutableConfig.java#L441) 创建值节点和 Map 节点，没有恢复原节点注释。

**影响。** 用户手工注释过 YAML 后，只改一个配置值再保存，也可能丢掉无关路径的注释。其主要收益是配置可维护性；本轮未证明它是性能瓶颈。

**建议。** 先定义注释属于路径还是节点、替换父节点及删除列表元素时如何处理，再在既有 ConfigNode 模型内实现保留元数据的更新。优先评估只替换变更路径、复用未变子树；避免并存一份容易失配的独立“注释数据库”。若涉及公共 API 或持久化承诺变更，按仓库边界另行确认。

**验收。** 覆盖未修改 round-trip、只修改相邻值、嵌套删除和列表编辑后的注释归属；同时验证 C1 与数值类型保真。无需要求字节级格式完全相同，除非后续明确将格式保真作为承诺。

### C3：缓存清空不等于旧下载任务失效

**证据。** [request 捕获条目和回调](../../../src/main/java/club/heiqi/uilib/ui/image/DocumentRemoteImageCache.java#L68) 把 Entry 与 callback 放进异步任务；[clear](../../../src/main/java/club/heiqi/uilib/ui/image/DocumentRemoteImageCache.java#L96) 只清 map；[任务提交](../../../src/main/java/club/heiqi/uilib/ui/image/DocumentRemoteImageCache.java#L157) 未保留 Future；[线程池构造](../../../src/main/java/club/heiqi/uilib/ui/image/DocumentRemoteImageCache.java#L176) 使用未指定容量的 LinkedBlockingQueue；[下载完成发布](../../../src/main/java/club/heiqi/uilib/ui/image/DocumentRemoteImageCache.java#L181) 未核对条目是否仍归当前缓存所有；[缓存淘汰](../../../src/main/java/club/heiqi/uilib/ui/image/DocumentRemoteImageCache.java#L214) 只移除 map 条目。

**触发与后果。** 慢网中请求图片后清缓存或淘汰条目，旧任务仍可继续下载、解码和调用旧回调；同 URL 再次请求又创建新条目。缓存 map 的条目限制无法约束排队任务及其强引用。本轮没有测得实际队列积压，也没有证据证明已卸载工具栏被回写。

**建议。** 在现有共享缓存内明确“缓存条目／下载任务／消费者”的生命周期。定义清空和淘汰是否使旧任务失效；若采纳失效语义，复用内部世代或条目身份检查，在开始工作与发布结果前验证，清理未执行的旧任务，并制定有界排队、拒绝或合并策略。共享条目被某个控件卸载时不得取消其他消费者的有效请求。运行期缓存重置继续与进程退出 shutdown 分工，不将每次 clear 改成关停线程池。

**验收。** 用可控阻塞下载场景覆盖“排队→clear→再次请求同 URL”：按确定的合同验证旧任务不发布结果、新代正常完成、重复请求合并和队列容量控制；回调只投递结果，UI 在 owner 线程消费。已有超时、daemon、shutdown 和池重建逻辑必须保留。

### C4：临时失败应有明确的恢复入口

**证据。** [失败写入](../../../src/main/java/club/heiqi/uilib/ui/image/DocumentRemoteImageCache.java#L190) 将 HTTP、解码与 IO 失败置为 FAILED；[markLoading](../../../src/main/java/club/heiqi/uilib/ui/image/DocumentRemoteImageCache.java#L283) 仅接受 PENDING；[request 复用条目](../../../src/main/java/club/heiqi/uilib/ui/image/DocumentRemoteImageCache.java#L55) 因而会持续返回同一失败条目，直至 clear 或淘汰。[ChatToolbarIcons 失败终态处理](../../../src/main/java/club/heiqi/uilib/internal/chat3/input/ChatToolbarIcons.java#L115) 在失败后停止观察；这是合理的终态减负，不应改成每帧重试。

**触发与后果。** 首次下载遇到临时网络故障，同会话网络恢复后，重新挂载消费者仍可能拿到旧 FAILED 条目，无法自动重试。字母回退本身是已有正确行为。

**建议。** 在缓存服务内区分临时失败和不适合自动重试的失败，选择显式失效或有界退避后的“下一次 request 重试”。是否让已挂载页面自动恢复是独立产品决定；若需要，沿既有 signal/Owner 消费新代状态，避免 worker 直接写节点，也不强制所有消费者常驻轮询。

**验收。** 同 URL 先失败后成功；退避期不反复请求、重试时共享加载、多消费者获取一致结果、Owner 卸载后迟到完成不回写。保留 [ChatToolbarIconsTest](../../../src/test/java/club/heiqi/uilib/internal/chat3/input/ChatToolbarIconsTest.java) 已有的失败回退、多实例成功和卸载保护。

### C5：嵌套 opacity／transform layer 的包围盒避免重复扫描

**证据。** [合成层预遍历入口](../../../src/main/java/club/heiqi/uilib/ui/scene/paint/ScenePaintEngine.java#L184) 在每个需要合成的节点调用 subtreeContentBounds；[包围盒递归](../../../src/main/java/club/heiqi/uilib/ui/scene/paint/ScenePaintEngine.java#L349) 遍历后代并分配 ContentBounds。随后主绘制遍历继续进入子节点，内层合成节点再次扫描重叠子树。fragment 复用仍然存在，此项不是“每帧重建全部绘制命令”。

**建议。** 先用现有 [UiPerformanceMonitor](../../../src/main/java/club/heiqi/uilib/ui/diagnostic/UiPerformanceMonitor.java) 关联嵌套动画场景采样。确为热点时，在一次 paint 内按需后序求包围盒并复用到现有 PUSH 命令；无合成层的页面应继续不付额外全树扫描成本。优先帧内结果，避免未经论证引入跨帧缓存及新失效体系。

**验收。** 比较嵌套合成树的边界访问和分配、paint 阶段耗时，保持命令边界和画面等价。保留滚动、presentation offset、collapsed、透明剪枝、溢出子节点和变换原点语义；回归入口复用 [ScenePaintCompositeReplayTest](../../../src/test/java/club/heiqi/uilib/ui/scene/paint/ScenePaintCompositeReplayTest.java)。本文不报告加速比或帧率收益。

## 文档治理发现与建议

### D1：优先消除公共兼容说明中的“多个当前值”

[公共 API 清单旧现值](../../../docs/使用文档/公共API稳定清单.md#L172) 与 [旧上界叙述](../../../docs/使用文档/公共API稳定清单.md#L174) 仍把旧区间称为“现值／现为”；同文 [新版本说明](../../../docs/使用文档/公共API稳定清单.md#L178) 已注明新范围，[MyMod 声明](../../../src/main/java/club/heiqi/uilib/MyMod.java#L22) 也为 [4.11.0,4.12.0)。这是同文历史叙述未收口，不能说清单完全没有新版本说明。

建议把“当前接入要做什么”放在版本兼容节开头，旧批次全部明确为历史，移除旧段的“现值”措辞。实时区间指向源码，批准的兼容规则指向 [发布流程](../../../docs/开发者文档/发布流程.md)；FML 接受区间与公共 API 源码兼容性应分别解释。治理不改实际版本策略，也不通过文档擅自扩大兼容承诺。

### D2：现行语义与历史施工正文要让局部阅读也能分清

DataTable 视觉规格（旧资料已退役，原文见 Git 历史） 已有现行／历史说明，但其“现网色值”表及旧状态矩阵仍容易被搜索命中后直接复制。实际默认路径复用已主题化的通用控件。

建议现行正文只留“输入列带、可编辑性、状态可辨”等跨控件意图，具体 token 和行为落最近源码。下次维护该文件时，提出单文件范围的历史正文归档变更并保留回链；涉及内容搬移按仓库要求确认，不批量迁走全部存量。若暂不搬移，至少让历史章节标题与表格就地明确“历史，不作实现依据”。

### D3：契约指针要精确到负责该语义的位置

[公共 API 输入条目](../../../docs/使用文档/公共API稳定清单.md#L67) 把 leaf hover 的细节母本指向 UI 投影 Input Scope（旧资料已退役，原文见 Git 历史）。后者主要负责投影间仲裁；最深节点交互态、不向祖先回写和装饰节点穿透的详细定义在 [控件包 R6](../../../src/main/java/club/heiqi/uilib/ui/scene/control/package-info.java#L41)。

建议公共清单保留稳定性、调用者后果与定义链接，完整实现契约只在最近源码维护；投影合同继续负责跨宿主语义。修正文档定义指针不等于改变输入主权规则。对旧编号采取“自述语义＋定义链接”，不新增一层编号登记表。

### D4：父导航与在办材料的状态保持一致

[开发者入口](../../../docs/开发者文档/README.md#L8) 将规格目录整体称为长期有效的现行规范母本，但 [规格索引在办节](../../../docs/开发者文档/规格文档/README.md#L21) 明确包含未实施规划。建议父导航描述改为“现行规范与在办材料，按文件状态阅读”；不要根据目录名推断已实现。

本次不覆盖正在编辑的规格索引与施工规划。后续收口时，外部依据需要可携带的标题和版本／提交定位；仅本机绝对路径无法支持其他工作树复核。规划中的目标冲突由规划任务自行裁定，不在审查报告里替其定稿。

### D5：把已有治理能力接到入口，不恢复已退役的重门禁

[CI 工作流](../../../.github/workflows/build-and-test.yml#L9) 委托固定的上游构建工作流，并显式配置脚本宿主检查；[产物守卫](../../../build.gradle.kts#L54) 验证 devtools 不进入发布包。[审计工具定位](../../../tools/audit/README.md#L3) 明确为按需诊断、不参与提交阻断。远端 reusable workflow 本轮没有展开，不能断言全部 CI 都不检查文档。

建议开发者导航增加“构建／产物守卫／按需诊断”入口，明确各自覆盖和运行条件。文档检查如后续采用，先对改动文件报告本地目标、锚点及状态冲突，积累实际误报后再决定是否阻断；不恢复已退役的注册表、逐实例台账或源码字面快照测试。

| 信息 | 建议唯一落点 | 其他位置怎样引用 | 更新触发 |
|---|---|---|---|
| 局部设计意图、生命周期和失败语义 | 最近源码／包注释 | 使用文档只解释调用后果并给链接 | 修改对应实现时 |

| 跨模块故障复盘 | 反馈层 | 局部根因优先写代码注释 | 再碰到对应故障时顺手收口 |

不另设必须定期全库盘点的流程。每次修改由该改动的维护者检查相关入口和引用；审阅者只确认当前值唯一、定义能定位、状态一致、验证没有夸大。已归档文件通过 Git 保留历史，后续引用必须重新核对源码，不为追踪每个结论再造持续维护的台账。

## 建议实施顺序与完成标准

1. **先做事实修订与正确性回归。** D1 的旧“现值”收口、C1 的复现和修复优先；分别验证文档无自相矛盾、null 删除读写一致。无需先做架构迁移。
2. **按模块处理用户可见恢复能力。** C2 在配置模块解决元数据归属；C3/C4 在同一缓存服务中先定任务和失败语义再实现。涉及 API／配置承诺的变更单独提案。
3. **测量后安排性能工作。** C5 先采样重叠子树遍历，再决定投入；验收同时看正确画面与测量结果，不能只看缓存命中率。
4. **文档治理随触达落地。** D2—D5 在对应文件后续维护时小步处理；不借本轮审查批量搬文档、修改协作规范或推进尚未确认的 UICore 构建拆分。

代码改动后按仓库要求跑完整 build；实机验证需用户明确要求。本文只是文档交付，未把建议用例写成“已通过”。
