# 决策：采用分层 AI 协作记忆框架

## 背景

原有协作文档体系以 `AGENTS.md` 和 `docs/AI记忆文档.md` 为核心，虽然已经能承载基础协作规则，但存在两个明显问题：

- 会话中的重要信息无法稳定、及时地回写到仓库
- `AI记忆文档.md` 容易同时承载导航、长期事实、阶段进度和计划，随着项目推进会持续膨胀

这些问题会导致多 Agent 协作时频繁重复探索、上下文断裂以及核心文档难以维护。

## 候选方案

1. 继续维持单一核心记忆文档，只通过更严格的书写纪律控制膨胀
2. 引入外部数据库、向量记忆或独立记忆服务
3. 在仓库内建立分层记忆框架，将规则、当前态、长期事实和决策记录拆开维护

## 最终选择

选择方案 3：在仓库内建立分层记忆框架。

具体拆分为：

- 规则层：`AGENTS.md`
- 当前态层：`docs/记忆/当前态/`
- 长期事实层：`docs/记忆/长期事实/`
- 决策层：`docs/记忆/决策/`
- 专项沉淀层：`docs/开发者文档/errors/`、`docs/开发者文档/reviews/`

`docs/AI记忆文档.md` 降级为总导航入口，不再承担大段项目知识堆积。

本次只迁移 Harmes-Rust 的协作记忆框架，不迁移其 Rust / egui 桌面 Agent 产品形态。

## 选择原因

- 保持纯仓库内实现，便于版本控制、审查和团队共同维护
- 不依赖外部基础设施，适合当前项目协作方式
- 小文件、单职责更适合多 Agent 按需读取和更新
- 将“当前态”和“长期事实”分离后，可以显著减少核心文档膨胀
- 决策单独沉淀后，后续协作者更容易理解历史取舍
- 复用 Harmes-Rust 已验证的协作形态，同时避免把不属于本 Java / Minecraft UI 库的产品架构决策带入本项目

## 影响范围

- 所有后续协作者进入任务时，需要优先读取 `docs/记忆/README.md` 和对应层级文件
- `AGENTS.md` 中的 AI 记忆协作规则同步适配分层结构
- `docs/AI记忆文档.md` 需要长期保持精简
- 当前任务、计划、交接信息不得再直接堆进总导航文档
- 目录结构、主入口、脚本命令、运行方式、能力边界变化应写入 `docs/记忆/长期事实/`
- 关键方案取舍、重要实现约束和接口开放边界变化应写入 `docs/记忆/决策/` 或既有专题文档

## 后续注意事项

- 如果未来项目规模继续扩大，可进一步按子系统拆分 `长期事实/` 和 `决策/`
- 除非用户明确要求，否则暂不引入外部记忆服务
- 需要对外公开的信息仍以 `docs/使用文档/` 为准，不能只写入 AI 协作记忆层
