### 易错设计分析与处置

**问题根源**：UiPerformanceMonitor 全局单例同时承担采集+读取，但采集是
per-壳层局部行为、读取是全局共享——scope 错配导致所有权丢失。
McScreenBridge（demo 壳）不驱动 monitor，getRuntimeStats() 静默返回 empty，
demo 页读 fps 必踩坑（静默不报错）。

**Oracle 关键发现**：采集深埋 Widget.java:110,198 硬编码 getInstance()，
scene demo 走 surface.render 不经 Widget.render，故 demo 不需要完整 monitor，
只需轻量帧率探针。生产路径单例当前能工作（主屏/HUD 各自 beginFrame），
无紧迫性强行改。

**落定方案**：组合式 FrameRateProbe + 基类默认采集
- 新增 FrameRateProbe（ui/diagnostic）：纯 long[] 环形缓冲，HISTORY_SIZE=120
  SLOW_THRESHOLD_NANOS=16_666_667L（与 monitor 对齐），tick/getAverageFps/
  getAverageFrameTimeMs/getMaxFrameTimeMs/getSlowFrameCount/reset
- AbstractSceneHostWidget 持有 protected final frameProbe，render() 首行
  自动 tick()，子类继承即用
- 与 UiPerformanceMonitor 正交：后者服务 Widget 树深度采集，前者服务
  scene demo 帧率采集，共享 UiRuntimeStats 输出契约但数据源物理隔离
- 生产路径零改动

**未做（留待远期）**：UiPerformanceMonitor 单例本身的 scope 错配
（Widget.java 硬编码 getInstance 的传播问题）属子系统大重构，仅当
生产路径出现多壳统计互踩真实需求时启动（策略 A）。已知缺陷：HUD 与
主屏 beginFrame screenName 切换会导致 history 互相 clear，留待策略 A
一并解决。

## 重要纪律（长期沿用）
- 帧率/真机实测必交用户跑，沙箱无 GUI。
- scene 新栈改动对照 NORTH_STAR 不变量自检，偏离按《修订纪律》登记。
- 完成独立任务后检查是否需更新 `当前态/`、`长期事实/`、`决策/`、`errors/`、`reviews/`。
- 子代理任务中断必须用原 task_id 恢复 session 保留进度，不得新开 session 空跑重做。
- Markdown 正文不写超长行（≤200 字符），表格行结构例外但控制单格长度。
- 并行 fixer 只并行写代码，build 统一由主 Agent 串行跑，避免并行 Gradle 竞争 build/ 目录。
- 侦察报告的「推测/未验证」项 = 必须补查项；同类修复后全量 grep 兜底确认无残留旧模式。
- fixer 只写代码，记忆文档（docs/记忆/）由主 Agent 统一管理。
- demo 页是控件真机验证的前提，控件完成后必须建 demo 页接入 hub。
- fixer → build → test → review → commit 是硬性链路，build/test 通过不等于 review 通过，
  改动简单不是跳过 review 的借口（ERROR-20260624-skip-review-before-commit.md）。
- wrapper 延迟建树（return () -> {}）是 B1 教训硬约束，bind 必须在 Supplier 体内执行才能
  登记到正确 Owner。
