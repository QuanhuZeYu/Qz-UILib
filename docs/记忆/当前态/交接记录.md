## 给下一个 agent 的施工提示词（方向E：滚动期绘制命令免重建 = 命令坐标解绑滚动偏移，回放期叠加）

> ModernConfigTemplateScreen 方向E 续接：方向A/B/C/D 已全部收口。**方向D（输入帧 render 段全量重建）已用七轮外科探针完成诊断（探针已干净回退，工作区从 HEAD 干净起步），真凶坐实为「滚轮滚动每帧全量重建 ~740 条绘制命令 ~16ms」**，详见上方「第 9 次交接」。用户已拍板做**架构性根治（方案2）**，非补丁。本提示词即方案2 的施工指引。
>
> **要解决的根因（已坐实，勿重新诊断绘制侧，可直接施工）**：
> - 滚动偏移当前在 `DocumentVisualTraversal.resolveBoxContext()`（约 292~293 行）`childOffsetX = boxOffsetX - getScrollLeft(...)` / `childOffsetY = boxOffsetY - getScrollTop(...)` 处减入，并经 `createEntry`（约 483 行）向滚动容器整棵后代子树传播，最终被 `DocumentPaintEngine` 固化进每条命令的**绝对坐标**（`box.getLeft() + offset` 形式）。
> - 于是滚动一改 offset → 全部后代命令坐标失效 → `HtmlLikeDocumentWidget.resolvePaintCommands()` 因 `scrollVersion` 变化使 `cachedPaintCommands` 失效 → `buildPaintCommands` 全量重建 740 条 ~16ms。
> - **scrollVersion 100% 由 `DocumentScrollState.updateOffsets()` 的 `version++` 驱动，且滚轮滚动是唯一来源（探针 `D.scBump.wheelN.nonWheel0`，nonWheel 恒 0）**。纯 hover/鼠标移动不触发（全程 cacheHit ~3.5ms）。
>
> **方案2 核心思路（架构性）**：让绘制命令携带「文档内容坐标」（**不含滚动偏移**），把滚动偏移移到**回放期**叠加。这样滚动只改回放参数、不使命令缓存失效、零重建。
> - **回放期已有天然注入点**：`DocumentPaintRenderer.render(context, commands, offsetX, offsetY)` 对**所有**命令类型统一做 `command.getLeft() + offsetX`（renderCommand/renderTextCommand/effect/transform/custom/clip 全部如此），当前 offsetX/offsetY 传的是 widget 屏幕绝对位置 `getAbsoluteX()/getAbsoluteY()`（全局平移）。方案2 要在此基础上叠加**每条命令所属滚动容器链的 -scrollOffset**。
>
> **关键技术约束（已坐实，务必遵守，否则破坏正确性）**：
> 1. **滚动是局部的，不是全局的**。一个文档可有任意多个并发滚动容器（`DocumentScrollState.entries` 是 `Map<ElementNode,ScrollEntry>`，每个 overflow 容器一个 entry），还可嵌套。所以**不能简单给整批命令加一个全局 -scrollY**，必须按命令所属的「滚动容器链」分别叠加各自的 scrollOffset。这是方案2 最大的工程难点。
> 2. **clip 矩形坐标当前不含自身 scrollOffset**（`ClipContext` 存 `boxOffsetX/boxOffsetY` 而非 childOffset，约 290 行），即视口框滚动时不动、只有被裁内容动——这个语义正确，方案2 改造后必须保持：clip 命令叠加「祖先滚动容器链」偏移、但不叠加自身的。
> 3. **sticky / fixed 定位**：`resolveBoxContext` 里 sticky（`DocumentStickyPositioning`）和 fixed（`fixedContainingBlock*`）与 scrollOffset 在同一处交织计算。方案2 把 scrollOffset 抽到回放期后，必须确认 sticky/fixed 的偏移语义不被破坏（sticky 本就是相对滚动容器的特殊偏移）。**这是高风险点，需专门测试**。
> 4. **CUSTOM 命令已有 `DocumentCustomRenderBounds` 固化滚动态**（方向B 的产物，`attachCustomRenderBounds` 约 171 行），方案2 改造滚动偏移来源后必须与之协调，别让文本控件选区/光标/行号层错位。
> 5. **命令缓存 key 解绑 scrollVersion**：`resolvePaintCommands()`（约 891 行）当前用 `cachedPaintScrollVersion` 判定失效，方案2 完成后滚动不应再使命令缓存失效（这是收益来源），但 scrollbar thumb 位置等仍需随滚动更新——评估 scrollbar 命令是否也要走回放期偏移、还是单独处理。
>
> **不会破坏指针更新（已与用户确认并坐实）**：用户曾遇到「滚动时指针样式不更新」回退，特别在意。已坐实指针更新走**交互管线**（`onMouseScroll → findElementAt → hitTest → dispatchLatestScrollIfChanged 检测 scrollVersion 变化 → updateHoveredElement`），与**绘制管线**分离。方案2 只改绘制侧命令坐标与回放偏移，**严禁改动 scrollVersion 的产生（updateOffsets 的 version++）与交互侧消费（dispatchLatestScrollIfChanged 约 1309 行）**，则指针更新零影响。**必须加专门回归测试覆盖「滚动后指针刷新」**。
>
> **施工建议步骤**：
> 1. 先补一轮探针坐实 `buildPaintCommands` 内部 16ms 的耗时分布（场景遍历 vs BoxContext 解析 vs 样式/动画解析 vs 文本测量各占多少），确认方案2 收益落点（绕开重建能省多少）值得这个改动面，再正式动手。子代理已分析：`resolveVisualScene` 是 O(根+topLayer) 常数级、大头在 `appendBoxCommands` 递归内的惰性 `resolveBoxContext` + stacking 排序 + 样式/动画解析 + 文本测量。
