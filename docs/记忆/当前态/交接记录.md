### 根因与修复要点

- **根因**：`FontBatchRenderer.java:259` 的 y 锚点是 em-box 顶（`baselineY = y + (64-descent)*scale`），
  前一次 half-leading 重构假设 y 是 content-area 顶（baseline−ascent），坐标系错配。
  全链路 fontSize 到渲染器 charSize 1:1 透传（scene 不经 UI_TEXT_SCALE），em-box 显示高 == fontSize。
- **新公式**（`ScenePaintEngine.calculateTextTop`）：
  - emHeight = fontSize
  - CENTER: `paddingTop + (innerHeight - emHeight) / 2`
  - TOP: `paddingTop`
  - BOTTOM: `paddingTop + (innerHeight - emHeight)`
  - 不做下边界钳制，em-box 高于 innerHeight 时允许 CSS overflow:visible 向上溢出
- **测试防盲区**：`FixedTextMeasurer` 保持不变（被 24 测试用），在垂直对齐用例显式设
  fontSize=20、lineHeight=16 使新旧模型期望值分叉（CENTER 9 vs 旧 11、BOTTOM 14 vs 旧 18），
  堵住前次"测试全绿真机偏上"的测试桩掩盖盲区。
- **epoch 失效链**：textTop 不再依赖运行时度量，固定尺寸节点 box 不变时不再隐性错位，
  完整性反而提升（reviewer 确认）。

### 已知边界

- **多行文本**：layout 层按 `countLines(\n)*lineHeight` 多行撑高，paint 层 calculateTextTop
  是单行模型（单个 emHeight=fontSize），paint 只发一条带原始 `\n` 的 TEXT 命令。
  既有不一致，非本次引入，多行垂直对齐属独立后续工作。
- **padding 失效**：`setPadding` 只调 `markSelfLayout` 不调 `markSelfPaint`，
  固定尺寸节点动态改 padding 时 textTop 不刷新。既有问题，非本次引入。
- **scene 核心 main 侧 SceneTextMeasurer.ascent/descent/lineGap 已无消费者**
  （lineHeight 仍用于 layout 多行高度），接口瘦身属独立架构决策。
- **TOP 测试用例**因 `FixedTextMeasurer` 的 `halfLeading=0` 恰不分新旧模型，
  区分能力靠 CENTER/BOTTOM（已知盲区，可接受）。

## 重要纪律（长期沿用）
- 帧率/真机实测必交用户跑，沙箱无 GUI。
- scene 新栈改动对照 NORTH_STAR 不变量自检，偏离按《修订纪律》登记。
- 完成独立任务后检查是否需更新 `当前态/`、`长期事实/`、`决策/`、`errors/`、`reviews/`。
- 子代理任务中断必须用原 task_id 恢复 session 保留进度，不得新开 session 空跑重做。
- Markdown 正文不写超长行（≤200 字符），表格行结构例外但控制单格长度。
- 并行 fixer 只并行写代码，build 统一由主 Agent 串行跑。
- 侦察报告的「推测/未验证」项 = 必须补查项；同类修复后全量 grep 兜底确认无残留旧模式。
- fixer 只写代码，记忆文档（docs/记忆/）由主 Agent 统一管理。
- demo 页是控件真机验证的前提，控件完成后必须建 demo 页接入 hub。
- fixer → build → test → review → commit 是硬性链路，build/test 通过不等于 review 通过，改动简单不是跳过 review 的借口（ERROR-20260624-skip-review-before-commit.md）。
- wrapper 延迟建树（return () -> {}）是 B1 教训硬约束，bind 必须在 Supplier 体内执行才能登记到正确 Owner。
