## 给下一个 agent 的任务（工程化重构，非打补丁）

**目标**：从底层重构文本控件的测量/布局，使 ModernConfig 大视图稳态 render 从 ~320ms 降到个位数 ms 量级；同时消除 TextArea/CodeEditor/TextInput 之间重复的文本测量实现。**不要**用「加个 if 跳过」「局部记一个上次结果」这种补丁式修法蒙混，要建立可复用、可测试、语义清晰的基础设施。

**先研究、再设计、后实现，分阶段提交**：

1. **研究阶段（只读，产出设计文档，不改业务代码）**
   - 通读 `DocumentTextAreaControl`、`DocumentCodeEditorControl`、`DocumentTextInputControl` 的测量/布局/渲染路径，列出三者重复与差异点（逻辑行模型、可视行换行、码点边界 X、滚动偏移、选区/光标定位）。
   - 摸清 `TextMeasureService` / `TextLayoutHelper` / `UiRenderContext.measureTextWidth` / `FontService.textMeasureEpoch` 的能力与契约，判断能否承载共享缓存层、缓存失效如何与字体代/内容变更挂钩。
   - 弄清 custom renderer 每帧被调用的触发链（谁在 paint 期调 `DocumentCustomRenderer.render`、layer 重绘是否可避免），评估「测量与绘制解耦、测量结果跨帧复用」的可行性。
   - 产出 `docs/记忆/决策/` 下的设计文档：现状问题、目标、候选方案对比、选定架构、风险与回滚。

2. **设计要点（建议方向，最终以研究结论为准）**
   - 抽出**统一文本测量/可视行布局组件**（如 `TextLayoutEngine` / `VisualLineLayout`），供三个控件共用，替换各自私有的 `VisualLineMetrics` 重复实现。
   - 测量算法从 **O(N²) 降到 O(N)**：用逐字符增量宽度累加得到前缀边界 X 数组，禁止对每个位置重测整段前缀子串。
   - **缓存层**：可视行布局结果按「文本内容 + 可用宽度 + 字体测量代(epoch)」缓存，仅在输入真正变化时重算；稳态（不打字、不改尺寸）零测量。
   - **测量与绘制解耦**：selection 层和 caret 层不应各自触发一次全文测量；测量一次、两层共享；无选区且光标不可见时根本不需要可视行的逐字符边界。

3. **实现与验证**
   - 走 AGENTS.md 流程：从 4.0 建 `refactor/<简述>` 分支（重构性质用 `refactor`，纯性能可用 `perf`），提交标题 `[Refactor]:`/`[Perf]: 中文标题`，`git merge --no-ff` 合回，提交者身份 QuanhuZeYu。
   - 单元测试覆盖新测量组件（换行、CJK/码点、空行、选区边界、光标定位），并保证三个控件行为不回归（参考既有 `src/test` 下控件测试）。
   - 本机可编译实测：`./gradlew.bat --no-configuration-cache compileJava`（约 20–42s，JDK25）；定向测试 `./gradlew.bat test --tests ...`。游戏内帧率实测需交用户（沙箱无 GUI）。
   - **完成后回退临时诊断埋点**（见上「诊断埋点现状」），保持 4.0 干净。

4. **验收标准**
   - 大视图稳态（不交互）TextArea/CodeEditor 的 custom renderer 单帧耗时降到 <2ms 级；整屏 render 进入个位数 ms。
   - 打字/选区/滚动时仍正确（增量重算只动受影响行）。
   - 三个控件不再各自实现逐前缀测量，共用同一套基础设施。
