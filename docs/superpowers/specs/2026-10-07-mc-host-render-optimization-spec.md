# MC宿主渲染优化规格

> 状态：用户已采纳本稿建议，进入实施。原版替代默认开启；采用有序图元流、固定索引与提交段顶点上传，纹理数组先做无平台探针并与二维纹理对照。

## 1. 目标与范围

通过合批降低绘制提交、纹理切换和重复 GL 状态管理的开销，弥补 Unicode 整形、多字体和动态逻辑带来的性能成本。实际收益按 CPU/GPU 与慢帧测量，不以 draw call 减少直接宣称更快。

本专题覆盖 UILib 在 MC 宿主的矩形、文本、图像回放及原版字体替代入口。scene 页面输出 PaintPlan；原版入口直接输出不可变文本绘制载荷，二者复用字体/排版服务、资源及同一批次构建/backend，不为原版调用创建 scene 节点或运行时。生产 backend 自有 shader、VAO/VBO，平台类型止于宿主边界。字体生成和性能门槛见[字体规格](2026-10-07-uilib-font-renderer-spec.md)。不自动扩展为原版世界区块、实体或任意第三方渲染器改造。

## 2. 合批合同

原始绘制次序决定遮挡。按原次序扫描，把相邻且状态兼容的绘制组成一批；合批不改变透明混合、阴影、裁剪、坐标或输入结果。颜色、UV 和位置可成为顶点数据，同批不要求每个图元同色。

批次兼容事实至少包括 shader/材质、所采样纹理资源、裁剪、混合/深度行为、目标 framebuffer 和坐标变换。顶点承载差异时可合并，否则改变这些事实即提交前批。普通二维纹理基线按实际纹理绑定拆批；第 7 节的纹理数组提案把不同页作为同一资源的层处理。两者均不做全局纹理排序，不引入 bindless。

| 情形 | 行为 |
| --- | --- |
| 连续同图集、同裁剪的多色文字 | 一批顶点并顺序绘制，不逐字绑定/上传/提交 |
| 连续同材质矩形 | 位置和颜色写顶点，按容量合批 |
| 文本后绘制遮挡矩形，再画文本 | 按顺序提交，不能把两段文字按纹理搬到一起 |
| 阴影、正文和下划线等 | 保留实际图元次序，兼容者可合批；不按种类全局重排 |
| 实际绑定资源改变、裁剪改变、容量到界 | 提交当前批并继续，无丢图元；同数组内换层不要求拆批 |
| 空裁剪或完全不可见图元 | 跳过实际绘制与 GPU 字形申请，布局及原文仍保留 |
| 原版物品或其他宿主委托绘制 | 先提交 UILib 批次，调用委托，之后重新建立自己的已知状态 |

合批器处理有序、已定位的绘制数据，不重新解析、整形或布局，不回读可变节点。字形未就绪按字体规格留空白；不为合批等待后台资源。

## 3. 提交范围与宿主状态

### 3.1 UILib 自有回放

一次 replay 是明确的批次范围。入口保存实际会触碰的宿主状态，范围内建立一次已知状态，按需要切换；结束及异常退出均按合同恢复。矩形/文字不逐图元 glGet 和恢复全部状态。外部渲染打断时先提交，重新进入后重建状态，不能用旧状态缓存猜测第三方当前状态。

顶点 staging 和 GPU 缓冲复用并有容量上限，满时分批提交。资源生命周期覆盖所有引用它的有效批次/计划，不能上传或淘汰后让旧 UV 指向其他字形。

### 3.2 原版字体替代调用

普通即时 FontRenderer 调用内部合批，返回前提交已就绪文字，保持返回值与后续绘制顺序。对于 Angelica 等已知宿主延后提交几何的范围，文字按该宿主的正式提交合同捕获并回放，保持所属 pass、变换、深度和裁剪；不能仅凭 Java 调用先后就认定实际 GPU 顺序。宿主适配层承担该区别，字形服务不感知 Angelica。

跨调用合批只发生在 UILib 自有 replay 或已接入并明确绘制屏障的宿主范围。scene 范围由框架管理；已知宿主范围由适配器管理。不同矩阵/深度/裁剪条件仍按序形成批次，范围结束或屏障自动提交，页面业务不需手动 flush。任意未知 Mod 调用不自动加入全帧缓冲，不拦截全局 GL 调用猜测顺序。

### 3.3 坐标与资源

UILib scene 直接使用 framebuffer 像素。原版替代入口保留原调用者的 GUI/世界变换与坐标语义，转换只在适配层。不能让合批把同字号但不同变换的文字画到同一位置，也不能破坏原版 GUI Scale 布局。

资源重载和窗口变化按依赖更新；后台完成经呈现 prepare 边界发布，不能在 replay 中途修改批次载荷。运行时关闭在上下文线程释放 GPU 资源。

## 4. 默认开启与宿主兼容（H1 已裁定）

原版字体替代默认开启，可配置关闭；UILib 页面始终使用自有引擎。默认安装路径必须覆盖标准 FontRenderer 的显示、度量和共存验收。关闭只是不接管入口，不是在运行错误时暗中恢复原版。

scene backend 恢复进入态；原版适配入口遵守其可观察尾状态，包括标准入口的 alpha-test、末字形颜色及必要纹理状态。这些兼容细节由 MC 适配器承担，不让通用合批器依赖固定管线。旧代码已存在相关处理，重构先检查真实调用点及宿主契约，不能一律用“全部恢复进入态”替代。

## 5. 无平台测试机优先开发

先制作 agent 可直接运行的独立测试机，不启动 MC/Forge。测试机消费生产状态、布局、字体服务和批次构建器，提供样例场景、输出图像、批次轨迹和机器可读统计。驱动样例用代码修改并重复执行；不要求人工逐次点页面。

开发验证分两条：

- **无需 GL 的真实集成**：真实字体和复杂文字排版、优先级、CPU 光栅、动态更新及生产合批器；软件输出比较合批前后顺序/画面，检查屏障与容量拆批。
- **独立 GL 上下文集成**：复用生产 shader、上传及 backend，渲染到测试目标，导出图像和异步计时；验证颜色、裁剪、透明、状态恢复及资源换代。依赖/驱动能力先探针核查，不用 GL mock 宣称 GPU 已通过。

方法级单元测试从简，仅补真实集成无法经济覆盖的回归。MC 特有注入、原版接口返回语义、GUI Scale 及 Angelica/LWJGL3ify 共存最后在指定实例验证，每轮交少量简单操作，不自动启动游戏。

## 6. 验收与性能证据

| 场景 | 验收 |
| --- | --- |
| 同状态连续多色文字/矩形 | 在容量内合成兼容批次，画面和原次序一致 |
| 透明重叠、阴影、嵌套裁剪及宿主委托插入 | 不因合批改变遮挡，不漏画，不污染后续绘制 |
| 图集换页、缓冲满及字体换代 | 正确拆批，无旧 UV、丢字或提前释放 |
| 冷缓存、静态页、快速滚动、多个文本控件 | 复用稳定结果，按需上传；可见资源完成后自动更新 |
| 原版替代开启/关闭及标准度量/绘制 | 开启进入同一服务，关闭沿原路径；尺寸查询与画面一致 |
| 无平台与 MC 同样样例 | 正式逻辑复用；核心不依赖 Minecraft/Forge/LWJGL，差异定位到宿主入口和 GPU 环境 |
| 纯 Forge 1.7.10、原有 Java8/LWJGL2、无 LWJGL3ify/Angelica | 自有页面与默认原版字体替代可运行，允许按用户授权安装 UniMixins，不补装 LWJGL3ify/Angelica、不更换实例 Java/LWJGL、不退回原版字体或删减文字能力 |
| LWJGL3ify/Angelica 宿主 | 相同文本与绘制合同回归通过，可选兼容接入缺席不影响 LWJGL2 路径 |

性能表分别比较：原版引擎、自有引擎逐图元提交、自有引擎合批提交。后两项使用相同字体、几何、缓存状态和图元序列，隔离合批收益；逐图元方式只用于开发基准，不形成第二套字体实现。记录 CPU 构建/提交、GPU、帧分位数、draw call、状态/纹理切换、上传量和内存；热点样例合批必须获得可重复收益，兼容样例达到字体规格已审定门槛。

先提交无平台运行结果，再做 MC 短小验证；独立环境结果不外推为所有 Mod 或所有显卡均兼容。

## 7. 已采纳的有序合批设计（A/B实测决定最终资源路线）

按页批次、顶点多色、CPU/GPU缓冲复用、受控跨调用提交、投影缓存和无平台收集器等既有能力作为基线，不计作新增收益；实际基线由当前源码与测量证据核对。

### 7.1 批次顺序：采用有序图元流

提案：高亮背景、字形、装饰先由文本绘制逻辑按语义输出有序图元；合批器不再在结束时统一搬动它们。字形按原视觉序列存储，不再把所有同页字形拉到一起。字体/字重不是独立批次键，实际材质、资源和状态才是键。

旧页序列 A→B→A 会按首次激活页合成 A→A→B；新基线按 A→B→A 提交。这是重叠正确性选择，不能为了降低 draw call 改回全局页排序。保留同页连续合批，页频繁交替的性能问题由资源组织解决。

### 7.2 页切换：两条可选路线

- **O1 A：普通二维纹理，按相邻状态合批。** 最少新增机制，先验证正确性与性能；频繁跨页时会拆批。
- **O1 B（推荐做无平台探针后采用）：纹理数组。** 同尺寸/格式的图集页成为数组层，顶点携带 layer，跨层保持原顺序并继续合批。单色与彩色保留独立数组/格式，shader 依据图元类型选择；数组组、采样策略或状态变化才拆批。

B 对应旧页分组的真实局限，需验证目标 GL/GLSL、层数限制、采样、容量和内存。数组按有界页组配置，不能启动预分配最大层数；页组变化属于批次事实，资源换代保留有效引用。不能任意 resize/重排后让旧计划指向新层。若探针无收益或内存代价不合适，提交实测结果再裁决 A，不暗中增加并行渲染体系。

### 7.3 缓冲提交：一次顶点上传，复用固定索引

推荐使用有界线性 staging：一个提交段内的有序图元连续存放，顶点一次上传，批次仅记录绘制范围与状态；不再每页重复拷贝到同一 direct buffer 并覆盖上传。

四边形索引模式固定，EBO 在建立/调整容量时生成上传，普通帧只更新顶点和绘制范围。VAO/VBO 在该提交段内保持绑定，结束/委托屏障再按合同恢复。减少旧实现的索引生成、索引上传和逐批解绑；旧实现本来已有容量复用，不能把“复用VBO”当新增点。

先使用常规流式缓冲，记录同区覆盖可能造成的驱动等待。环形映射、持久映射和实例化不作为先决条件，仅热点实测要求时追加比较。顶点打包同样先测，不能因字段较多就删掉必要裁剪或字形信息。

### 7.4 裁决与验证表

| 事项 | 当前提案 | 比较证据 |
| --- | --- | --- |
| 页分组与绘制顺序 | 采用有序流，拒绝全局同页重排 | 重叠/半透明跨页图像与原序一致 |
| 跨页合批 | O1 B 探针，与 A 对照后定案 | 同图元 CPU/GPU、拆批数、页组切换及图集内存 |
| 索引和顶点提交 | 固定EBO＋提交段一次顶点上传 | 索引上传量、CPU复制、提交时间及驱动慢帧 |
| 跨调用范围 | 自有/已知宿主范围，普通调用即时 | 文本/矩形/物品混排，告示牌和名签实际落屏顺序 |
| 更多高级机制 | 暂不引入 | 当前方案测出具体热点后再提出 |

先在无平台测试机上实现正式有序收集器与对照图像，再在独立 GL 上下文比较 A/B 及缓冲方案。旧页分组只保留开发期基准，不能以旧顺序为正确图像标准。最终 MC 验证默认接管后的 GUI/HUD、告示牌与名签，以及宿主延后提交场景。
