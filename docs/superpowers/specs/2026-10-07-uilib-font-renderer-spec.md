# UILib 字体渲染器规格 · 批量审阅稿

> 状态：待用户审改；本轮只编写规格，生产实现暂停。选项中的推荐答案是作者提案，不代表用户已认可。

## 1. 审阅方式与确定需求

每题单选，除非注明多选；可以回复“Q1B、Q4改为……，其余采用推荐”，也可以直接修改本文。修改某题时，只替换该题涉及的行为，其他必需能力保持。技术实现由作者负责，不要求用户选择库、线程数或图集算法。

已确定的需求：

- UILib 自有字体选择、整形、度量、光栅和 GL 回放；正式路径不调用 Minecraft FontRenderer。
- logical px 与 framebuffer px 一一对应。GUI Scale 不改变字号；窗口实际尺寸变化自动重排，裁剪、滚动和命中使用同一坐标事实。
- 正式支持 UTF-8，并支持双向文本、阿拉伯文、印度文字、泰文及彩色 emoji，执行控制字符效果。脚本整形包括上下文连接、标记定位、重排、连字与字距；段落方向可声明 auto/LTR/RTL，语言可声明并继承主题。
- 默认随库提供 Minecraft 使用的开源字体，并补齐必需脚本和彩色 emoji；可配置系统字体，基础显示无需用户安装字体。
- 性能不能比原版差太多；字形按需生成，CPU 与 GL 分离，GL 侧按预算增量上传，避免单次处理整个字符集。
- 每段可声明有序字体候选，未声明时继承主题默认链；同页可并存不同字体、字号。候选字体、字号、主题、语言和资源变化自动失效更新；业务只提交内容与样式。

共同内容模式、几何及交互遵循[核心规格](2026-10-07-uilib-core-contract-design.md)第 9、13.1—13.2 节；本文件独立定义字体合同。数学专题继续暂停。

## 2. 选择题：行为与验收裁定

### Q1. “控制字符效果”包括哪些内容？

- **A（推荐）：Unicode 文本控制。** 执行下表；独立 CR 作为换行，BS 和 ESC 不执行终端动作，显示可辨识控制符标记并诊断。
- **B：增加行内覆盖。** 在 A 基础上，独立 CR 返回本行起点，BS 回退一个显示簇位置，后续文本覆盖对应显示位置；不删除源文，不执行 ANSI。
- **C：增加 ANSI 显示模式。** 普通文本采用 A；显式 ANSI 模式增加 B 和 SGR 颜色/样式。终端光标寻址、屏幕清除等命令仍显示标记并诊断。
- **D：其他。** 写出需要的控制序列与效果；完整终端模拟需要另立专题。

| 所有答案均须支持的字符 | 显示效果 |
| --- | --- |
| LF、CRLF | 显式换行，CRLF 合为一次换行 |
| Tab | 到下一制表位，间距由样式声明 |
| Bidi 标记、嵌入、覆盖、隔离及结束符 | 按 Unicode 双向算法影响视觉顺序，本身无可见字形 |
| ZWJ、ZWNJ、变体选择符 | 影响整形或呈现选择，本身无独立字形 |
| 零宽空格、Word Joiner、软连字符 | 允许断行、阻止断行、仅采用该断点时显示连字符 |

其他不具显示语义的 C0/C1 控制符采用可辨识标记并诊断，不触发宿主动作。Minecraft § 格式码仅在显式 Minecraft 内容模式解释，普通文本和 Markdown 不猜测模式。

### Q2. 无效 UTF-8 或不成对 UTF-16 代理项如何处理？

- **A（推荐）：继续显示并报告位置。** 解码边界用 U+FFFD 替代 Unicode maximal subpart 定义的无效子段；Java 字符串的不成对代理项同样替代。诊断保留原输入范围，后续有效文本照常显示。
- **B：拒绝本次内容。** 返回带位置的输入错误，不将部分结果作为有效文本提交；调用方处理错误。

原字节/字符串由调用方保留，显示替代不写回业务。入口保留输入范围到逻辑文本的映射，不能静默丢字符。

### Q3. 默认 emoji 呈现与覆盖如何约定？

- **A（推荐）：遵循 Unicode 默认呈现。** 默认 emoji 呈现用彩色，默认文本呈现用文字字形；VS15/VS16 显式请求文本/emoji 呈现。
- **B：默认优先彩色。** 无呈现选择符且存在 emoji 字形时优先彩色；显式 VS15 仍采用文字字形。

两项均要求覆盖所选 Unicode/Emoji 数据版本的完整 RGI emoji 集，包括肤色、旗帜、键帽和 ZWJ 序列。实施时锁定同一发布版本的数据及默认字体，并在资源清单列明；后续更新通过资源换代生效。非 RGI 序列仍按整形和候选能力显示，不能据此承诺任意组合都有单个彩色字形。

彩色字形保留原色，文本颜色不染色；整体透明度和祖先裁剪生效。缺少整个受支持序列的字体是覆盖缺陷，不能用逐码点拆开代替通过验收。

### Q4. 自选系统字体的缺字回退如何工作？

- **A（推荐）：系统字体优先，自动补齐。** 有序自选候选之后接默认补充字体链；无法显示的内容仍可用内置字体呈现。
- **B：严格采用显式候选。** 未声明候选时使用默认链；已声明时只尝试该链，全部缺字则显示替代字形并诊断。

回退按能正确整形的文本簇/脚本片段选择字体，保持上下文；不在阿拉伯连接或组合序列中任意逐码点换字体。字体文件不可用由统一资源入口诊断，和有效字体缺字区分，不偷偷改用任意系统字体。两段内容的选择结果互不受加载顺序影响。

### Q5. 字号和多字体行高采用什么语义？

- **A（推荐）：字号指定 em 像素尺寸。** 默认行高覆盖本行实际字体的 ascent/descent 及行距，含回退文字和 emoji；指定行高时按明确声明布局，超出部分遵循裁剪规则。
- **B：字号指定 em 像素尺寸，默认固定行距。** 行距由主字体确定，回退字形可能超出行盒；溢出与裁剪按声明处理。

字号不是每个字形的可见墨迹高度；保持字号意味着保持像素比例，不能通过偷偷缩小回退字体补齐行高。基线、字形偏移、advance 与行盒是共同排版结果。

### Q6. GPU 字形尚未就绪时显示什么？

- **A（推荐）：临时轮廓占位。** 在排版确定的位置显示区别于缺字的轻量标记，保留真实 advance 和行高；就绪后只使相关绘制失效。
- **B：暂留空白。** 保留真实位置和尺寸，就绪后补画；新文字可能短暂不可见。

缓存已就绪时直接显示；两项均不能阻塞 draw 同步生成整段字形，也不能让上传完成导致换行或字符位置跳动。缺字替代是稳定显示结果，等待占位只是资源状态，诊断和外观须可区分。

### Q7. “性能不能差太多”如何量化？

- **A（推荐）：采用明确候选门槛。** 等价中英场景，热缓存每帧文本 CPU、GPU 耗时的 p95 各自不超过原版的 1.25 倍；若原版该项低于 0.20 ms，则改用绝对增量不超过 0.05 ms。整体帧时间 p95/p99 增量各不超过 1 ms。这些是待审目标，是否达到由同机实测决定。
- **B：先看基线再定数值。** 保留同机比较和增量纪律，完成原版与候选探针后提交测量表，再裁定具体门槛。
- **C：自定门槛。** 写出允许的文本耗时差距及慢帧差距。

对比使用相同实例、机器、framebuffer、像素字号、可见字量与裁剪条件；覆盖静态热缓存、首次大量新字形、滚动及切字体。记录文本 CPU/GPU、整体帧时间分位数、内存、生成数量和上传量；无新数据时不强制等待 GPU 查询结果。

原版不能正确显示的复杂脚本/emoji单列正确性与耗时，不删减功能凑等价比较。启动、字体载入和整形也计入观测，不能只报告 draw。工具噪声及测量下限随结果说明。

### Q8. 增量就绪延迟怎样验收？

- **A（推荐）：先给测量表再定时限。** 当前可见需求优先；测首屏最后一个字形就绪时间、滚动新行等待及主线程慢帧，结合 GPU/字体大小提出时限。
- **B：固定候选目标。** 常规字号、资源已加载且可见需求能装入预算时，首屏字形全部就绪不超过 100 ms；滚动新行不超过 50 ms。超大字号和资源首次载入单列，不冒充达标。
- **C：自定时限。** 写出目标设备、可见字量/字号和允许等待。

无论选哪项，已提交的当前可见需求不能被预取长期阻塞。需求超过内存预算时，服务报告资源不足状态并保留等待占位，不能无限增大队列或不停淘汰同一批可见字形。实施基准表须明确输入规模，不能只写“普通页面”。

### Q9. 默认包覆盖哪些印度文字？

- **A（推荐）：完整列明本轮覆盖。** 天城文、孟加拉文、古尔穆基文、古吉拉特文、奥里亚文、泰米尔文、泰卢固文、卡纳达文、马拉雅拉姆文与僧伽罗文；均具真实字体、整形和显示样例。
- **B：扩大集合。** 在 A 之外指定需要的脚本；不从“印度文字”推导为全球所有古今文字。

两项均保留中文、拉丁、阿拉伯、希伯来双向混排及泰文。泰文需要语言断行；未列文字仍经 Unicode 与字体候选流程处理，覆盖情况由资源清单说明。

### Q10. 无合法软断点且内容超宽时？

- **A（推荐）：默认保持完整并溢出。** 作者可显式启用应急断行，断点必须是合法字素/整形边界；明确禁止断行的内容不强行拆开。
- **B：默认应急断行。** 可拆内容按合法字素/整形边界断开；Word Joiner 等明确禁止的断点仍不采用。

省略策略由控件声明；省略号参与整形，删除范围对应完整簇。RTL 省略位于实际视觉末端，不把省略号写回源文。阿拉伯文按最终行边界重新整形，不能切割一次整形结果假装正确换行。

## 3. 推荐技术设计（作者负责，可直接批注）

### 3.1 职责与主流程

复用 scene 的测量、依赖追踪、不可变 TextLayout/PaintCommand 与宿主 replay。核心保留平台无关的文本与几何，GL 对象只在 backend；业务不接触字形队列、纹理或上传时机。

流程：

输入/显式内容转换 → Unicode 分段与 Bidi → 候选字体与脚本整形 → 按宽度断行并修正行边界 → 不可变行/字形定位及来源映射 → 可见字形需求 → 后台光栅 → GL 增量上传 → 同一定位回放

度量取得实际字体的 metrics/advance，不依赖 GPU 是否就绪。测量和绘制消费同一排版产物；视觉命中返回源文逻辑范围，字素内部不返回半个代理对/组合标记位置。Bidi 的边界位置保留方向归属，供编辑器处理光标与选区，不在字体层另建编辑状态。

优先评估 ICU4J 类 Unicode/Bidi/语言断行、HarfBuzz 整形与 FreeType 彩色光栅的组合。具体版本、绑定和 native 分发在实施前核对 Java 8、GTNH/LWJGL3ify、字体颜色格式及许可证；Java2D 单独不作为覆盖全部要求的默认方案。依赖不能满足时更换绑定/引擎，不缩减上述必需能力。

默认资源方向：Unifont 承担中英及广泛字符补充；Noto 系列补充复杂脚本，Noto Color Emoji 承担彩色序列。具体文件与版本以真实覆盖探针选定，随包保存上游来源和完整许可。配置系统字体按 family/style 解析实际 face，选择界面按需枚举，普通帧不扫描系统字体目录。

### 3.2 按需增量与效率

- **按实际 glyph 建稀疏缓存。** 身份包括实际 face/资源代际、glyph ID、像素字号及影响光栅的样式；整形位置和来源映射不写进共享字形。无需 Unicode 全集索引或启动全字体预生成。
- **合并需求。** 同一字形的等待者共享一次生成/上传；可见片段申请字形，有限预取排在可见需求后。关闭、滚动和字体换代撤销过期需求；后台任务完成时按代际检查发布。
- **分离任务。** 字体元数据、整形和光栅属于 CPU 服务，GL 仅由上下文线程执行。单次光栅有输入尺寸上限，不能假设可在字形内部随意抢占；异步运行防止其阻塞渲染线程。
- **控制上传。** 每帧使用时间、字节和提交数预算；超大区域按行块上传，完整字形上传完成后才发布就绪。驱动调用耗时实测，时间预算是提交边界。
- **采用实际格式。** 单色覆盖率与 RGBA 彩色图集分开存储；合并同页脏区域，但合并额外上传量也计入预算。连续可合并绘制使用批量顶点，不跨遮挡/裁剪边界重排序。
- **有界复用。** CPU 字形、排版、等待数据和 GPU 页分别有可配置预算。当前有效回放资源固定引用到 replay 完成；淘汰非使用资源，资源不足按 Q8 处理。页面释放引用，运行时释放共享资源。

旧实现已经有可见优先和时间/字节预算。候选改进的可检验差异是：稀疏实际字形缓存、跨文本请求合并、单色存储、区域批量更新。以相同输入比较生成/上传吞吐、重复工作、慢帧及内存，取得结果后评价是否优于旧实现。

### 3.3 动态更新与失败归属

| 变化/失败 | 处理 |
| --- | --- |
| 文本、候选、字号、语言、宽度 | 相关排版失效；最终行位置更新，按新结果请求字形 |
| 单色文本颜色、整体透明度 | 只更新绘制，不重新整形或光栅 |
| GPU 字形就绪 | 在呈现 prepare 边界通知相关绘制失效；不在 replay 中改节点或计划 |
| 字体/资源重载 | 代际换新，旧有效计划维持完整引用直到不再使用，不能混用旧度量和新字形 |
| 有效候选全部缺字 | 显示稳定替代字形，保留源文范围并诊断 |
| 字体文件读取/解析失败 | 统一资源入口报告字体身份与原因，不等同缺字；不增加静默系统替换或无限重试 |
| 节点关闭、运行时关闭 | 取消相关需求/订阅，释放引用；GL 删除在上下文线程完成 |

后台只递交完成结果；主呈现流程统一发布。文本布局、图集位置与资源生命期不能由不同线程各自修改。backend 恢复其触碰的 GL 状态，字体图集与 shader 不污染其他 Mod。
