# UILib 字体渲染器规格

> 待审阅，实施暂停。本规格只定义用户要求与验收，算法方案另见实施设计。

## 1. 显示与字体

- UILib 自行管理字体选择、整形、度量、字形资源和GL回放，不调用 Minecraft FontRenderer 测量或绘制。
- 使用原生 framebuffer 像素；字号、排版、裁剪和命中共用坐标。Minecraft GUI Scale 不改变文字像素大小，窗口实际尺寸变化自动重排。
- 默认随库提供 Minecraft 中文等语言使用的开源字体 GNU Unifont，允许配置选择系统字体；默认提供显示下述必需内容的有效字体组合，不能要求用户先安装字体才能通过基本验收。补充字体的具体文件和许可证在设计中列明，不能只靠Unifont承诺彩色emoji和全部脚本覆盖。
- 每段内容可声明有序字体候选；未声明时采用主题默认候选。同页可并存不同字体、字号，同一码点不受其他内容加载顺序影响。
- 字体或字号变化自动更新度量、换行和绘制，不要求业务重新挂载。颜色变化不重新生成单色字形。

## 2. Unicode 与文本效果

### 2.1 输入与整形

- 字节输入正式支持UTF-8，解码后按Unicode处理；Java字符串入口须保留同等文本。编码无效须可定位，不能静默丢字符。
- 必须支持中文、拉丁文字、双向文本、阿拉伯文、印度文字和泰文。需要真实脚本整形：上下文连接、组合标记、重排、连字及字距；不能逐码点摆放代替整形。
- 双向文本按Unicode双向算法确定视觉顺序，允许自动/LTR/RTL段落方向；混排中的数字、标点与隔离/嵌入控制符作用正确。源文维持逻辑顺序，绘制及命中保留视觉位置到源文的关系。
- 换行和字体回退遵守字素簇及整形边界，不拆代理对、组合簇或emoji序列；阿拉伯文换行后的行边界需要正确整形。泰文等无空格文本按语言断行规则处理。
- 度量、基线、换行、省略和GL绘制消费同一份排版事实；GPU字形未就绪不能改变advance或引起文字跳动。

### 2.2 彩色 emoji

- 必须实际显示彩色emoji，覆盖常用单码点、变体选择符、肤色修饰、旗帜和ZWJ组合；不能用黑白字形或逐码点分拆冒充。
- 尊重文本/emoji呈现选择符。彩色字形保持原有颜色，文本颜色不将其染成单色；整体透明度和祖先裁剪仍生效。
- 整个emoji序列参与共同基线与行高，来源关系保留到完整序列。候选回退要找到能呈现该序列的字体资源。

### 2.3 控制字符

必须执行文本控制效果，不把控制符画成缺字方框或无条件删除。当前可确定的集合：

| 字符 | 效果 |
| --- | --- |
| LF、CRLF | 显式换行；CRLF为一个换行 |
| Tab | 前进至下一制表位，制表位间距可声明 |
| 双向方向标记、嵌入/覆盖/隔离及结束符 | 影响Unicode双向排版，本身无可见字形 |
| ZWJ、ZWNJ、变体选择符 | 影响连接/字形选择，本身不单独占可见字形 |
| 零宽空格、Word Joiner、软连字符 | 分别允许/阻止断行、仅在相应断行时显示连字符 |

待用户明确：单独CR是否回到行首覆盖、BS是否退格、ESC是否解释ANSI颜色/光标控制。不能把终端模拟或原版§格式码自行纳入“控制字符效果”；格式码仍由明确的内容模式解释。

缺字与字体文件不可用分别诊断。所有有效候选都缺字时保留原文范围并显示替代，不使整段消失；字体加载错误不能用任意系统字体静默掩盖。

## 3. 性能

- 性能不能比原版渲染方案差太多。比较必须使用同一实例、机器、原生像素字号、可见字量和裁剪条件，记录原版与UILib的文本CPU耗时、GPU耗时、帧时间及内存。
- 分别测缓存已热的持续绘制、第一次出现大量不同字形、滚动进入新内容及切换字体。原版不能正确显示的复杂脚本/emoji单独报告，不能通过删减功能制造等价比较。
- 无变化帧不重新解析/整形/光栅；已缓存字形不重复生成/上传；不能每帧全量扫描字符、系统字体或所有图集。
- CPU缓存、待生成/上传数据和GPU图集都有有限预算；预算满时不破坏当前回放资源，也不让队列无限增长。
- “差太多”的量化门槛在实现前用原版基线和候选方案实测提出，供审阅；当前没有性能通过证据，不能自行用平均FPS接近替代文本耗时及慢帧检查。

## 4. 懒加载与增量生成

- 首次启动不遍历Unicode全集、不预生成整个字体；整形确定实际glyph后，只申请当前需要的字形资源。
- 字形身份含实际字体/资源版本、glyph、字号及影响生成的样式；不同内容共享相同资源，同一未完成字形请求合并。
- 当前可见字形优先。后台需求不能阻塞可见需求；滚动/关闭/切字体后更新需求，失效结果不能发布到新字体资源。
- CPU整形/光栅与GL上传分离。GL仅在上下文线程执行，每帧按时间和上传字节预算增量推进，不能在draw期间为整段文本同步生成全部字形。
- 大字形/大批次拆成可控工作，不能一个任务穿透整帧预算。预算控制是调度边界，不把GL驱动调用时延误称绝对可控。
- 字形未就绪时保持真实排版位置，使用可辨识临时占位；与“字体缺字”区分。完成后通知相关绘制失效，无需业务刷新，未受影响文本保持原样。占位外观和可接受就绪延迟待设计实测后审阅。
- 单色字形和RGBA彩色字形分别按实际格式存储；批量提交相邻图集更新，减少逐字GL调用。合批不得改变遮挡顺序、裁剪或字形颜色。
- 资源换代、图集淘汰和关闭须保证有效计划不引用已释放页/过期UV。节点释放自身引用，不能释放其他内容使用的共享字体。

## 5. 验收

| 场景 | 预期 |
| --- | --- |
| 同一内容从UTF-8字节与Java字符串输入 | 源文及视觉结果一致，补充平面字符不拆分 |
| 中英/阿拉伯文/印度文字/泰文/双向混排 | 正确连接、组合、视觉顺序和语言断行，测量与画面一致 |
| emoji、肤色、旗帜、ZWJ、呈现选择符 | 对应完整字形与颜色，不拆成多个独立符号 |
| 控制字符样例 | 对应第2.3节效果，无多余方框，原文保留 |
| 两字体同码点/打开页面后切默认字体 | 字体结果独立，相关内容自动更新，不丢节点及业务状态 |
| 切GUI Scale/改变窗口尺寸 | 前者像素字号不变，后者重排，裁剪和命中对齐 |
| 首次大量不同字符、连续滚动新字符 | 按预算增量就绪，不单帧全量生成；反向滚动不等待后台无关字形 |
| 无变化帧/重复文本/小预算淘汰 | 复用资源，占用有界，无串字、旧UV或重复生成 |
| 同机对比原版 | 分场景给出CPU/GPU及慢帧证据，按审定门槛评价 |

UTF-8/整形/回退/增量队列采用真实字体与正式生产流程做无平台验证；字形颜色、复杂脚本观感、GL状态和性能在指定MC实例验证。人工每轮只交少量简单操作，出现问题先收敛再展开。
