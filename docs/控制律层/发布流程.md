# 发布流程

当前仓库只保留一次性的 `4.6.2` recovery，不提供通用 tag 自动发布、Release 创建/上传或其他制品渠道门禁。本文件不构成本地 agent 的 Gradle、网络、workflow dispatch、push、tag 或 Release 授权。

## 固定身份

- tag：`4.6.2`
- annotated tag object：`6155c157b823c928accc25b037f7a95e7e83d669`
- peeled commit：`e86a731cf10c5fa9e0f3dd87fe52126646bf8ed1`
- 既有 draft Release ID：`357902877`

tag 禁止移动、删除重建或强推；workflow 禁止创建、上传、覆盖或删除 Release/资产。

## 两 job 闭环

`.github/workflows/recover-4.6.2-release.yml` 只允许从默认分支 dispatch：

1. `verify`（`contents: read`）按固定 tag 完整 checkout，核对 tag object、peeled commit、HEAD 与唯一 `modVersion=4.6.2`；用 Java 25 执行 `test build`；精确收集 main/dev/sources/dev-preshadow 四个 JAR 与 `.changelogs/4.6.2.md`，验证 ZIP、UTF-8、大小和 SHA-256并生成 manifest；最后按数字 ID 核对 draft、notes 和四资产，上传本 run bundle。
2. `publish` 仅在 `publish-existing-draft` mode 运行，是全仓 workflow 唯一 `contents: write` job。它下载同 run bundle、重新计算 manifest，PATCH 前再次按 ID 完整核对；唯一写操作是对 Release `357902877` 设置 `draft=false`。随后同时按 ID 和 tag GET，要求同一 ID、非 draft、非 prerelease、`published_at` 非空且 notes/四资产仍匹配。

## 用户授权顺序

1. 本地提交通过独立 review。
2. 用户另行授权 merge/push，等待默认分支常规 CI。
3. 用户授权 `verify-only` 并核对 run 结果。
4. 用户再次授权 `publish-existing-draft`，使用 workflow 中要求的精确 confirmation。
5. 核对最终 Release 后更新 `docs/反馈层/交接.md`。

任一步失败都保持 `INCOMPLETE` 并保留现场；不得移动 tag、删除 draft、重试写入、操作 issue #65 或把本地静态检查写成远端成功。未来通用 tag 发布、JitPack、Maven 或本地 agent Gradle 能力均须独立任务重新设计与验证。
