## 两 job 闭环

`.github/workflows/recover-4.6.2-release.yml` 只允许从默认分支 dispatch：

1. `verify`（`contents: read`）按固定 tag 完整 checkout，核对 tag object、peeled commit、HEAD 与唯一 `modVersion=4.6.2`；用 Java 25 执行 `test build`；精确收集 main/dev/sources/dev-preshadow 四个 JAR 与 `.changelogs/4.6.2.md`，验证 ZIP、UTF-8、大小和 SHA-256，生成 manifest 并上传本 run bundle artifact。该 job 不读取 Release 或 draft API。
2. `publish` 仅在 `publish-existing-draft` mode 运行，是全仓 workflow 唯一 `contents: write` job。它下载同 run bundle、重新计算 manifest，在 PATCH 前按固定 ID `357902877` 完整核对 draft 状态、notes 和四资产；唯一写操作是设置 `draft=false`。随后同时按 ID 和 tag GET，要求同一 ID、非 draft、非 prerelease、`published_at` 非空且 notes/四资产仍匹配。

## `4.6.3` 一次性人工正式发布合同

本合同只适用于 `4.6.3`，不修改或复用固定 `4.6.2` recovery，也不恢复通用发布自动化。全过程以精确 Git object、CI run 与数字 Release ID 为身份，不以分支名、tag 名或资产名的再次搜索代替已取得的身份。

### 候选、合入与最终 CI

1. 将本次文档提交随 `fix/font-depth-state` 候选分支显式推送，并等待绑定该远端分支 tip 的常规 `Build and test` CI 达到 `completed/success`。既有 run `30153547093` 只绑定代码候选 `79aa0bd640a6fc7546dfd3ff719b5652c138b67c`，不能替代文档提交后的候选 CI。
2. 候选 CI 成功后，重新核对远端 `4.0` 合入前基线仍为 `15545344139f36fb36de1a78af3de1f1fd5cb926`；不一致即停止。仅在该基线上用 `git merge --no-ff` 合入候选并记录最终 merge commit `M`，再显式推送 `4.0`，禁止 force 或以 fast-forward 代替 merge commit。
3. 等待精确绑定 `M` 的常规 CI 达到 `completed/success`。候选 run、其他分支 run 或本地静态检查均不得替代最终 CI；候选 CI 完成前不得推送 `M`，避免两个 Gradle CI 重叠。
4. 只从绑定 `M` 的成功 run 取得 main、dev、sources、dev-preshadow 四类 artifact ZIP。逐个验证 ZIP 可读且只提取预期 JAR，并对四个独立 JAR 核对精确名称、非零大小与 SHA-256；正式 Release 只能上传这四个 JAR，不得上传 ZIP、聚合 artifact 或其他文件。

### Annotated tag

1. 在确认 `refs/tags/4.6.3` 尚不存在后，以 `M` 为目标创建 annotated tag，记录 tag object `T`，并显式推送该 tag ref；禁止让 Release Create 隐式生成 lightweight tag。
2. 推送后从远端核对 `refs/tags/4.6.3` 的 object type 为 `tag`、ref 指向 `T`，且 peeled commit 精确为 `M`。任一身份不符即停止，不得 force、移动 tag 或删除重建。

### ID-bound draft 与正式化

1. tag 与四资产核验完成后，只 Create 一次 `4.6.3` draft，并使用 `.changelogs/4.6.3.md` 作为正式 notes。数字 Release ID 只能取自该次 Create 响应；响应未明确给出 ID 时停止，不得重复 Create，也不得按 tag 或 list 重新发现 draft。
2. 此后的 draft GET、四资产 upload、发布前核对与 `draft=false` PATCH 全部贯穿使用同一数字 ID。上传前后均按 ID 核对 tag、notes 与资产集合；四资产必须与最终 `M` run 记录的名称、大小和 SHA-256 一致，禁止覆盖既有资产。
3. PATCH 前再次按 ID 要求 draft、非 prerelease、notes 与四资产全部匹配；唯一正式化写入是对该 ID 设置 `draft=false`。PATCH 响应不确定时先按 ID GET 当前状态，不得盲目重复 PATCH。
4. 正式化后同时按 ID 与 tag 两个端点复验：二者必须返回同一 Release ID，且 `draft=false`、`prerelease=false`、`published_at` 非空，notes 与四资产身份仍完全一致。

### 失败停止与现场保留

任一 ref、CI、ZIP、JAR、digest、tag object、peeled commit、Release ID、notes 或资产身份不符即停止。禁止 force、移动 tag、删除重建 Release、覆盖资产、重复 Create 或对不确定写响应盲重试。若 tag 或 draft 已部分成功，保留现场并准确记录 `M`、`T`、Release ID 和已完成步骤，交用户决定后续动作；不得用清理或重建掩盖部分成功。
