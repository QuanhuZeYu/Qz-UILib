# 发布流程

本文件记录项目当前标准的 tag 发布流程，供用户与维护者的专门发布流水线执行；不构成本地 agent 的构建、脚本、tag 或发布授权。

## 当前标准

- tag 发布先复用 GTNH release workflow 构建和上传资产，再由本项目后置步骤统一整理 GitHub Release 标题和正文。
- tag 发布默认通过 `.changelogs/<tag>.md` 覆盖 GitHub 自动生成的 release 正文。
- release 标题统一强制设置为 tag 名，例如 `4.2.0`。
- 若不存在对应覆盖文件，release workflow 会保留 GitHub / GTNH workflow 自动生成的说明，只改写标题。
- 覆盖文件必须存在于 tag 指向的那次提交中，不能在 tag 推送后补写。
- `release-tags.yml` 先执行同 workflow gate（Gradle test、scene 边界、文档纪律），gate 成功后才调用 GTNH release reusable job；本地 release notes 仅在该 job 成功后执行。
- 正常四渠道投递保持不变；Maven 继续使用 releases 仓库，版本串保留 `-beta`/`-alpha`/`-rc`。
- GitHub 后置步骤按 tag 后缀设置 prerelease：`-beta`/`-alpha`/`-rc` 标为预发布，正式 tag 显式取消预发布；标题和 `.changelogs/<tag>.md` 正文规则不变。
- GTNHGradle 2.0.25 的公开 Modrinth/CurseForge 配置扩展在 `addon.late.gradle` 中按版本后缀映射 `beta`/`release`；projectId 为空时不创建对应任务，启用后自动生效。

## 标准步骤

1. 确认待发布代码已经完成验证，工作区干净。
2. 在仓库根目录创建或更新 `.changelogs/<tag>.md`。
3. 将覆盖文件随发布相关修改一起提交，并按仓库规范合并回发布分支。
4. 在包含该文件的提交上创建 tag。
5. 推送分支与 tag，触发 release workflow。
6. 发布后检查 GitHub Release 标题是否为 tag 名，正文是否来自 `.changelogs/<tag>.md`。

## 覆盖文件规则

- 目录固定为 `.changelogs/`。
- 文件名必须与 tag 名完全一致，例如：`4.2.0` 对应 `.changelogs/4.2.0.md`。
- 文件内容使用 Markdown，作为 GitHub Release 正文直接发布，不负责 release 标题。
- 建议至少包含：本次更新、兼容性说明。
- 本地验证命令和结果只记录在协作交接、提交说明或开发者文档中，不写入远端 GitHub Release 正文。

## 命令示例

```bash
git add .changelogs/4.2.0.md
git commit -m "[Docs]: 添加4.2.0发布说明"
git tag -a 4.2.0 -m "4.2.0"
git push origin <当前分支>
git push origin 4.2.0
```

## 重新发布已有 tag

- 只有在用户或维护者明确要求重新发布同一版本时，才允许移动已发布 tag。
- 重新发布前必须先提交 `.changelogs/<tag>.md` 和发布流程修正，确认新提交就是 tag 应指向的提交。
- 推送移动后的 tag 时优先使用 `--force-with-lease`，避免覆盖远端未知更新。
- 重新发布后必须检查 release workflow 是否成功、Release 正文是否被覆盖、资产是否重新生成。

## 注意事项

- 若 tag 已存在且对应提交中没有覆盖文件，本次 workflow 不会自动读取后补的 changelog。
- 覆盖文件不能可靠控制 release 标题，标题由 workflow 在发布后统一改写为 tag 名。
- 若需要完全手工控制单个版本的 release 内容，优先更新对应 `.changelogs/<tag>.md`，而不是只在 GitHub 页面手动编辑。
- 若未来要调整自动生成策略，应同步检查 `.github/workflows/release-tags.yml` 与本文件是否一致。
