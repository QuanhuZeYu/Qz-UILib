# 发布流程

本文件记录项目当前标准的 branch/tag 发布流程，供用户与维护者的专门发布流水线执行；不构成本地 agent 的构建、脚本、tag 或发布授权。

## Publication 双门禁

- branch/PR workflow 在常规构建成功后执行 publication gate：先自测分类器，再验证普通 Maven publication，最后模拟 JitPack canonical publication。任一步失败都不得合并或创建发布 tag。
- tag workflow 重复上述本地门禁，并在调用 GitHub Release reusable job **之前**串行完成真实 JitPack Remote 检查与全新目录中的显式 `:dev` consumer 编译、哈希核对。远端或 consumer 未通过时不得创建 GitHub Release。
- 普通 Maven publication 必须保留正确的 Gradle Module Metadata（GMM）：module component 与 GAV 一致，API/runtime 指向 dev，reobf 指向 main，sources 指向 sources，URL 与 hash 均正确。
- 仅 `JITPACK=true` 的组合方案禁用 GMM。此时 canonical POM 与 main/dev/sources classifier 是消费合同，JitPack `.module` 返回 404 是**预期且必需**；该结论不得外推到普通 publication。
- 真实 JitPack 的成功矩阵以 `docs/传感层/门禁脚本说明.md` 为准。branch 模拟通过不是远端成功事实，只有 tag workflow 的 Remote 与 clean consumer 通过才能解除远端门禁。
- GTNH Maven 发布不是 Qz-Miner 或 GitHub Release 的 publication 前置条件，不要求为该前置门禁配置 Maven 凭据；workflow 中相应步骤若未启用，不得写成已发布，也不得误报为 JitPack 失败。

## GitHub Release 规则

- tag 发布通过全部门禁后复用 GTNH release workflow 构建和上传资产，再由本项目后置步骤统一整理 GitHub Release 标题和正文。
- tag 发布默认通过 `.changelogs/<tag>.md` 覆盖 GitHub 自动生成的 release 正文；标题统一为 tag 名。
- 若不存在对应覆盖文件，release workflow 保留自动生成的说明，只改写标题。覆盖文件必须存在于 tag 指向的提交中，不能在 tag 推送后补写。
- GitHub 后置步骤按 tag 后缀设置 prerelease：`-beta`/`-alpha`/`-rc` 标为预发布，正式 tag 显式取消预发布。
- GTNHGradle 的公开 Modrinth/CurseForge 配置按版本后缀映射 `beta`/`release`；projectId 为空时不创建对应任务，启用后自动生效。

## 标准步骤

1. 确认代码、4.6.1 发布正文与 publication gate 已完成本地验证，工作区干净。
2. 将 `.changelogs/4.6.1.md` 和 `CHANGELOG.md` 随发布文档提交，经 branch/PR gate 后按仓库规范合并回发布分支。
3. 在通过 gate 的最终提交上创建 annotated tag `4.6.1`；tag 一经创建即视为不可移动。
4. 推送分支与 tag，触发 tag workflow；不得提前手工创建 GitHub Release。
5. 等待真实 JitPack Remote 与 clean `:dev` consumer 门禁通过，再等待 reusable release job 和本地 release notes 步骤完成。
6. 发布后检查 GitHub Release 标题、正文和资产，并核对 JitPack canonical 成功矩阵；GTNH Maven 只按实际结果单独记录。

## 覆盖文件规则

- 目录固定为 `.changelogs/`。
- 文件名必须与 tag 名完全一致，例如：`4.2.0` 对应 `.changelogs/4.2.0.md`。
- 文件内容使用 Markdown，作为 GitHub Release 正文直接发布，不负责 release 标题。
- 建议至少包含：本次更新、兼容性说明。
- 本地验证命令和结果只记录在协作交接、提交说明或开发者文档中，不写入远端 GitHub Release 正文。

## 维护者命令示例

```bash
git add CHANGELOG.md .changelogs/4.6.1.md
git commit -m "[Docs]: 准备4.6.1 JitPack发布说明"
git tag -a 4.6.1 -m "4.6.1"
git push origin <当前分支>
git push origin 4.6.1
```

## 失败重试与版本升级

- `4.6.1` annotated tag 不得移动、删除后重建或强推。DNS、连接超时、JitPack 5xx 等非确定性基础设施失败，可针对**同一 tag、同一 commit**重试 JitPack 构建或重跑失败的 workflow。
- 若 Remote 发现错误 GAV、classifier、hash、POM、module 状态、peeled commit，或已缓存制品存在确定性语义污染，不得用移动 tag 覆盖；修正代码与门禁后发布 `4.6.2`。
- 重试不得把预期矩阵改宽以迁就错误远端结果；同 tag 重试成功前，4.6.1 仍视为未发布。

## 注意事项

- 若 tag 已存在且对应提交中没有覆盖文件，本次 workflow 不会自动读取后补的 changelog。
- 覆盖文件不能可靠控制 release 标题，标题由 workflow 在发布后统一改写为 tag 名。
- 若需要完全手工控制单个版本的 release 内容，优先更新对应 `.changelogs/<tag>.md`，而不是只在 GitHub 页面手动编辑。
- 若未来调整 publication 或自动生成策略，应同步检查 `.github/workflows/build-and-test.yml`、`.github/workflows/release-tags.yml`、`jitpack.yml`、`scripts/check-publication.ps1` 与本文件是否一致。
