# 发布流程

本文件记录项目当前标准的 branch/tag 发布流程，供用户与维护者的专门发布流水线执行；不构成本地 agent 的 Gradle、Remote、workflow dispatch、tag、push 或 Release 授权。

## 渠道拓扑

- **branch/PR publication gate** 是合并与创建发布 tag 前的代码质量门禁：在常规构建后执行 publication SelfTest、普通 Maven Local `RequiredCorrect` 与 JitPack canonical 模拟 Local `Forbidden`。它守卫代码进入发布分支，不把任何远端渠道串成另一渠道的前置依赖。
- **GitHub Release** 采用 read contract + write wrapper：`_github-release-contract.yml` 只读验证 immutable tag、目标 commit、质量门禁、权威 notes、四资产与远端 preflight；`_github-release-publish.yml` 是唯一最小写发布入口。两者均不依赖 JitPack 或 Maven。
- **JitPack** 由 `jitpack-advisory.yml` 独立检查 canonical Remote 与 clean `:dev` consumer。它是 fail-closed 的 JitPack 渠道 advisory，但成功或失败均不阻断 GitHub Release。
- **未来 Maven** 必须使用独立 workflow、凭据与 gate；不得加入 GitHub Release 的 `needs`，也不得把未配置、skipped 或失败混写成 JitPack/GitHub Release 状态。

普通 Maven publication 必须保留正确 Gradle Module Metadata（GMM）：component 与 GAV 一致，API/runtime 指向 dev，reobf 指向 main，sources 指向 sources，URL 与 hash 均正确。仅 `JITPACK=true` 的 canonical 组合禁用 GMM；此时 POM 与 main/dev/sources classifier 是消费合同，`.module=404` 是该渠道的预期状态，不能外推到普通 Maven。

## 仓库自有 GitHub Release 合同

### 身份、质量与 bundle

- tag caller 先解析 annotated tag object 与 peeled commit；reusable 合同采用 side-by-side 双 checkout，隔离发布控制面与目标业务树：

| 区域 | 来源 | 工作区路径 | 职责 |
|---|---|---|---|
| `control` | `${{ job.workflow_repository }}@${{ job.workflow_sha }}` | `${{ github.workspace }}/control` | 提供当前已审计 reusable commit 内的 `check-github-release.ps1` 与 manifest 生成程序 |
| `target` | `${{ github.repository }}@refs/tags/<tag>`，`fetch-depth:0` | `${{ github.workspace }}/target` | 提供 immutable tag 的 Git、Gradle、源码、scene/doc 门禁、权威 notes 与四资产 |

- read contract 的 `gate`/`preflight` 与 write wrapper 的 `publish-release` 都先 checkout `control`、再 checkout `target`，均使用 `persist-credentials:false`；所有 run step 以 `target` 为 working directory。Release checker 固定从 `control` 执行，但 `RepositoryRoot`、bundle、notes 与 manifest 路径均为 `target` 的绝对路径，故 manifest 程序来自控制面而身份和数据只绑定目标 tag。该 `job.workflow_*` 方案适用于本仓库所在的 GitHub.com，不外推为 GHES 合同。
- 合同从 `target` 重新验证 tag 类型、tag object、peeled commit、`HEAD`、`modVersion=<tag>`，并要求目标 commit 内存在非空 `.changelogs/<tag>.md`。
- 合同从目标 commit 重新执行 `test build`、scene 边界门禁与文档纪律门禁，不复用其他渠道的制品或结论。
- Release bundle 必须精确包含 `main`、`dev`、`sources`、`dev-preshadow` 四个非空有效 JAR；文件名精确、SHA-256 两两互异。notes 与四资产的名称、大小、hash 连同 tag object/commit 写入当前 run manifest，上传下载后再次核对。
- Release 标题与 tag 名一致，正文精确来自 `.changelogs/<tag>.md`；`-beta`、`-alpha`、`-rc` 后缀决定 prerelease，正式 tag 不标 prerelease。测试结果不得写进 Release 正文。

### Draft、正式化与并发

- read contract 的 `gate` 只上传一次 `qz-github-release-<tag>-<run_id>`，`preflight` 下载本 run artifact、重做 Local 并输出且仅输出 `absent|matching_published`。write wrapper 的 `verify` 以 `contents:read` 调用该合同；唯一 `contents:write` 的 `publish-release` 再下载同 run artifact、重做 Local，并在任何写操作前拒绝缺失或未知的 `release_status`。
- `absent` 才创建 draft，随后按 asset ID 下载四资产并核对大小/hash，验证 draft 标题、notes、资产和 prerelease 状态后才正式化，最后再验证 published 状态；`matching_published` 跳过全部写步骤但仍执行 Published 完整复验。
- 已存在且完全匹配的正式 Release 只做幂等复验，不覆盖；正式 Release 任一身份、正文、状态或资产不匹配即 fail-closed。
- 已有 draft、同 tag 多条 Release、冲突正式 Release均 fail-closed；workflow 不删除、不覆盖、不续传 draft，也不使用 `--clobber`。失败遗留 draft 必须由用户先调查并决定后续处置。
- GitHub Release concurrency 只位于两个顶层 caller：都按 `qz-github-release-<tag>` 分组且 `cancel-in-progress:false`，两个 reusable 不声明 concurrency，避免 nested workflow 自等待或自取消。GitHub Actions 最多保留一个 pending run 且不保证 FIFO，故这里只承诺同 tag 互斥，不承诺严格排队。只有 tag caller 的 `release`、recovery 的 `publish` 与 write wrapper 的 `publish-release` 三个精确 job 可获得 `contents:write`；read contract 零写权限。

## 标准 tag 发布

1. 确认代码、`CHANGELOG.md`、`.changelogs/<version>.md` 与 branch/PR gate 已完成验证，工作区干净；由用户授权合并。
2. 在通过 gate 的最终提交上创建 annotated tag `<version>`；创建前核对目标 commit，创建后 tag object 与 peeled commit 均视为不可移动。
3. 由用户分别授权 push 分支与 tag。tag push 自动触发 `release-tags.yml`；不得提前手工创建同 tag Release 或 draft。
4. 等待仓库自有 GitHub Release 合同完成，并核对身份、标题、notes、四资产与 draft/prerelease 状态。JitPack advisory 可独立并行或随后收敛，不改变 GitHub Release 结论。
5. 分别记录 GitHub Release、JitPack 与未来 Maven 的实际结果；一个渠道成功不得冒充另一渠道成功。

- `recover-4.6.2-release.yml` 只接受上述固定身份，不读取 dispatch ref 猜测目标；confirmation 首先要求 `GITHUB_REF == refs/heads/<default_branch>`，从非默认分支或 tag 发起的 dispatch 在进入 reusable 前立即失败。`verify-only` 以 `contents:read` 直调 read contract，完整 nested graph 零 `contents:write`；Release 不存在是合法只读结果。
- 用户应先单独授权 dispatch `verify-only`，核对远端 run 结论后，再另行明确授权 `publish`。两种模式都要求输入包含 mode、tag object 与 commit 的精确确认串；`publish` caller 才以写权限上限调用 write wrapper。
- `publish` 仅在 Release 不存在时走 draft→远端下载复验→正式化→最终复验。已有匹配正式 Release只复验；已有 draft、冲突正式 Release或并发状态异常均失败，不自动清理或覆盖。
- 旧 verify-only run `29897718082` 在启动阶段因 read caller 的 nested graph 含旧 `publish-release contents:write` 而成为 `startup_failure`；jobs 与 artifacts 均为空，未创建或修改 Release。该 run 不含权限拆分，禁止 rerun；修复 merge/push 后必须由用户重新授权一次全新 verify-only dispatch。read/write 拆分当前只通过本地传感，真实 nested output 与同 run artifact 仍待新 run 实证，`4.6.2` Release 状态保持 `INCOMPLETE`。

## 失败与重试边界

- annotated tag 永不因 workflow、网络或渠道失败而移动。包含当前代码的普通失败 run 可在用户判断后重跑并完整重验身份、质量、notes 与四资产；旧 `startup_failure` run 不含权限拆分，必须新 dispatch，不能 rerun 冒充验证新图。
- GitHub API、构建或下载失败保持 fail-closed；若留下 draft，后续 run 会阻断并等待用户调查，不得由自动化删除、覆盖或续传。
- JitPack DNS、超时、5xx、pending 或确定性 GAV/classifier/hash/metadata 错误只影响 JitPack advisory。可按 JitPack 合同对同一不可移动 tag 重试非确定性失败；确定性污染须在后续版本修复，但不得据此阻断或改写 GitHub Release。
- 未来 Maven 的凭据、审核与重试边界由其独立 workflow 定义，不得复用 GitHub Release 写权限。

## 维护规则

- 调整 Release 合同时同步核对 `.github/workflows/release-tags.yml`、`.github/workflows/_github-release-contract.yml`、`.github/workflows/_github-release-publish.yml`、`.github/workflows/recover-4.6.2-release.yml`、`scripts/check-github-release.ps1` 与本文件。
- 调整 JitPack 时同步核对 `.github/workflows/jitpack-advisory.yml`、`jitpack.yml`、`scripts/check-publication.ps1` 与 JitPack 决策；不得重新把 advisory 接入 GitHub Release `needs`。
