# 持久任务规范

## 1. 文件与索引

需要跨轮设计或执行的工作使用 `.opencode/tasks/<id>.md`，推荐 ID 为 `YYYYMMDD-简短标识`。任务文件进入版本控制，不由后续任务覆盖；`.opencode/tasks/INDEX.md` 只列活动任务和已归档任务的最小指针。

简单问答、只读定位或当前轮可闭环的轻量工作不创建任务。工作模式、状态机、所有权和恢复规则见 `PERSISTENT-WORKFLOW.md`。

## 2. 必需结构

```markdown
# 任务：简短标题

## 元数据
- ID：`YYYYMMDD-short-id`
- 状态：`DRAFT|READY|ACTIVE|BLOCKED|DONE|CANCELLED`
- 所有者：当前唯一所有者；未分配写“无”
- 创建日期：`YYYY-MM-DD`
- 更新日期：`YYYY-MM-DD`
- 分支：实时分支或“待创建”
- 起始 HEAD：完整哈希或“待核对”
- 依赖：任务 ID 或“无”

## 目标
- 可观察的最终结果。

## 非目标
- 本次明确不处理的事项。

## 已确认设计
- 已由用户、权威文档或代码事实确认的决定与必要假设。

## 写集
- `允许修改的仓根相对路径`。

## 验收
- A1：可观察且可判定的通过条件。

## 风险
- R1：触发条件、影响与观测入口；没有则写“无”。

## 进度与证据
- 已完成动作、静态检查、CI/用户证据及明确缺失的证据。

## 唯一下一步
- 只有一项可立即执行的动作；完成时写“无”。

## 结果
- 未完成时写“待执行”；完成/取消时写状态、文件、证据和提交信息。
```

## 3. 写回纪律

任务必须足以在没有旧聊天的情况下，仅凭权威文档、任务文件和实时 Git 恢复。影响后续动作的目标、决定、假设、状态、证据、阻断与下一步不得只保留在上下文中。

在设计确认、状态变化、所有权变化、发现阻断、获得关键证据、提交前自审和结束会话时覆盖式更新正文，并同步 `INDEX.md`。正文保留当前有效事实，不堆工具原始输出、逐轮流水账或固定尝试计数。

写集必须完整明确。必要改动不在写集，或公共 API、依赖/版本、发布取舍未决时保持零写，将任务置为 `BLOCKED` 或退回 `DRAFT`，并把请用户决定的事项作为唯一下一步。

## 4. 执行与完成

任务进入 `ACTIVE` 前必须已有可判定验收。内置 `build` 只修改写集，按仓库边界执行静态验证，对照目标、非目标、验收、风险和 Git diff 自审，再按 Git 规范提交。

`DONE` 的结果至少记录改动文件、静态/CI/用户证据、缺失证据、残余风险和提交标题/标识。无法取得任务必需的 CI、编译、测试或运行态证据时不得写成通过，应保持 `BLOCKED` 或明确标记 `INCOMPLETE`。

完成或取消后任务文件作为 L3 情景档案保留；长期业务状态、决策和错误预防事实须归并到对应 L2 权威文档，不能仅藏在归档任务中。
