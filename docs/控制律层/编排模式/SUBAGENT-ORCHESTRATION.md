# 子代理调度纪律

> 本文件是主 agent 调度子 agent 的**行为纪律**，不是固定流程模板。
> 目标只有两个：**指导主 agent 主动用子 agent**（别自己扛），**多盘查避免错误**（别轻信）。
> AGENTS.md 控制律层·Subagent 编排指向本文件作为权威。

## 1. 核心理念：主 agent 是用户代理

主 agent（`.opencode/agents/build.md`，覆盖内置 build）**不是调度器**，而是**用户代理**：

- **每次 Task 工具调用 = 替用户开了一个子会话去问专家**。就像用户自己 `@oracle`/`@explorer` 一样，主 agent 把这个手动过程自动化。
- **拆任务视角是"用户会怎么一步步问"**，而非"我有几个工人可派"。
- 目标是让更难、更长期的任务得以自动化：大需求 → 拆成若干本该手动去问的子会话 → 串/并联 → 持续跟踪到完成。

子 agent 全部由 opencode 原生 `.opencode/agents/*.md` 提供，一律 `task: deny`（不再二次派发，防递归），只有主 build 可 `task: allow`。

## 2. 该问谁：控制论映射

子 agent 是控制论闭环各层的执行者（= 用户会问的"对象"）：

| 子 agent | 控制论层 | 何时调（= 用户会问什么） | 权限 |
|---|---|---|---|
| `@oracle` | 设定值 | 架构裁决 / 方案深评 / 疑难诊断 / 规划与复审 | 只读 |
| `@designer` | 设定值 | UI/UX 设计方案 / 视觉交互取舍 / 设计走查 | 只读 |
| `@explorer` | 传感 | 代码侦察 / 定位 / 返回压缩上下文 | 只读 |
| `@librarian` | 传感 | 外部文档 / 库用法 / 行业标准调研 | 只读 + web |
| `@fixer` | 控制律 | 按清单实施 / 写测试 / 编译验证 / 提交（含 UI 实现） | 可写 |
| `@reviewer` | 反馈 | 独立审核 / 核对硬约束与不变量 / 测试有效性 | 只读 |

派发优先级（可外包的优先派，主 agent 聚焦规划/裁决/整合/验证）：
代码侦察/定位 → `@explorer`；外部调研 → `@librarian`；架构裁决/深评/简化审查/反复修不好 → `@oracle`；UI/UX 方案与走查 → `@designer`；明确范围的实现/测试/机械改动（含 UI 实现）→ `@fixer`；独立审核 → `@reviewer`。

## 3. 闭环本能（不是模板，是思维框架）

控制论闭环（传感 → 设定值 → 控制律 → 反馈）是天然的思维框架，**不是要背诵的固定步骤**：

- **任何非平凡执行都要形成闭环**：派出去前先传感（探现状），方案前对齐设定值（宪章/硬约束），实施后有反馈（盘查复核）。单向"派出去就信"是失控的。
- **闭环可长可短**：简单任务一两个 agent 就闭环（explorer 探一下 → fixer 改 → reviewer 扫一眼）；复杂任务多轮闭环首尾衔接（上一轮复审结论是下一轮规划的输入），直到全部完成。
- **无需独立终审**：每轮闭环的反馈环节就是审核，最后一轮的复审即终审。
- **不套模板**：不要把任务硬塞进"诊断型/实施型"格子。用户怎么问，你就怎么拆——有时只派一个 explorer 就够，有时需要 oracle+librarian 并行交叉，有时需要多轮 fixer→reviewer 拉锯。

## 4. 盘查纪律（防子 agent 幻觉 / 偷懒 / 臆造）

这是本文件的**核心**。盘查对象是**一切信号源**——子 agent 会幻觉、会偷懒、会臆造，用户也会误判、会漂移，同理待之。主 agent 对任何单点输入都保持健康的怀疑——盘查即控制论的**二次传感 + 反馈层交叉验证**。

**分水岭（盘查用户信号时必须划死）**：用户信号的**事实层**（可验证的观测：用户断言的 `file:line`、现状、数据）可交叉验证、可上报矛盾；用户的**设定值层**（目标、价值取舍、优先级）只可**澄清**，不可**盘查否决**。盘查用户 ≠ 盘查用户主权——拿"盘查"当"否决用户目标"的授权即越权。

### 4.1 不轻信单点结论
- 关键事实（`file:line` / 约束条目 I?R? / API 签名）自己抽检核对，不照搬子 agent 的断言
- 诊断结论要证据链（假设排序 + 证据 + 未验证风险），不收"应该是 X"的空话
- 向用户交付的报告必须区分"已验证事实" vs "推测"

### 4.2 写盘改动必经独立复审
- fixer 的代码改动完成后，必经一次独立审核：代码用 `@reviewer`，架构疑点新开 `@oracle` session
- 复审不通过 → 回规划重做，不带着已知缺陷往下走

### 4.3 冲突即盘查
- 多个子 agent 结论互相矛盾，或与上下文已有信息冲突 → 追加一轮盘查，不直接采信任一方
- 复杂诊断优先多视角交叉验证（如 oracle 从两侧正交切分 + librarian 查行业标准），三方一致才高置信

### 4.4 证据优先
- 复审 / 诊断一律引 `file:line` 作证据，不空泛评定
- 问题按严重度标注（P0 阻断 / P1 重要 / P2 可后续）

### 4.5 范围防越界（派 fixer 前）
- 给 fixer 的任务必须是**可执行清单**（改哪个文件、改什么、加什么测试、验证命令），不只是方向
- 现有已验证可用的调用方默认不迁移（避免零收益回归风险），迁移单列后续批
- 每批改动"单调增量"（加约束/加诊断/加封装）优于"触碰核心数学"

### 4.6 验收标准（fixer 产出）
- 编译 + 全量测试绿才提交；不绿带着失败测试提交即违规
- 提交标题 `[English]: 中文标题` + 中文 Markdown 正文（守 AGENTS.md Git 规范）

### 4.7 工具调用 5 分钟红线（成本约束，所有子 agent 共用）

**根因（为什么是 5 分钟）**：LLM 的 prefix cache（上下文缓存）TTL 一般约 5 分钟。一次 bash/工具调用若超过 5 分钟，下一次模型调用时缓存已过期，整个对话前缀**全量重算**，input token 按全价计费——长上下文下账单爆炸。

**红线**：任何子 agent 的**单次工具调用不得超过 300 秒**。这不是软建议，是硬成本约束。

**守红线策略**（长任务三选一）：
1. **拆分**：长构建 / 全量测试 / 大批量检索拆成多次短调用，每次 < 5min
2. **后台 + 轮询**：长任务后台启动，主流程不阻塞等待，分批回查
3. **派子 agent**：长耗时操作派给 fixer/explorer 在**子会话**里跑——子会话的长调用**不打断主会话的缓存**，主 agent 继续推进

**这条约束反向强化"派子 agent"的理由**：长耗时的 shell 操作派出去，主 agent 的 prefix cache 不被打断，主会话注意力与成本都保住。这正是"模拟用户"思想的体现——让专家在子会话里慢慢跑，用户（主 agent）继续干别的。

## 5. 派发纪律

### 并行与串行
- 只读 agent（oracle/designer/explorer/librarian/reviewer）可并行派发（同一消息多个 task 调用）
- 写盘 agent（fixer）必须串行，不得并行多个 fixer；读与写不同批并行

### 守 token
- 派发只传路径 / 行号 / 线索（如 `HtmlLikeDocumentWidget.java:495`），不贴整文件
- 真机日志排查（`run/client/logs/fml-client-latest.log`）、批量文件检索一律派 subagent，主 agent 不亲自全量读

### 任务状态机与 task_id 生命周期

每个派发任务都必须带状态，状态转移为：

`NEW → RUNNING → COMPLETED | INTERRUPTED | TIMEOUT | INCOMPLETE | FAILED`

- `COMPLETED`、`FAILED`、`UNKNOWN` 或缺少状态都是终态；终态绝不传旧 `task_id`，也不以旧 session 继续执行。
- 只有 `INTERRUPTED`、`TIMEOUT`、`INCOMPLETE` 三种状态可以恢复原 `task_id`。恢复必须保持同一目标、角色和范围，且同一任务的恢复次数累计最多 5 次。
- 审查已完成但结论为不通过，任务状态仍为 `COMPLETED`；按审查修复项新开 fixer。已完成的 fixer 经复审后发现问题，同样新开 fixer，禁止恢复已完成任务。

### Session 复用与中断恢复
- 禁止优先复用交接记录里登记的专家 session；只有上项三种可恢复状态才允许用原 `task_id` 恢复原 session。
- 子 agent 中断（空结果/超时/未完成）必须先按状态机登记为对应可恢复态，再用原 `task_id` 恢复，不新开同一任务重做。
- Oracle 成本高，但除三种中断恢复外一律新开 session；终态任务一律新开后续任务。

### 执行失败：5 次恢复重试预算（主 agent 对子 agent 失败的纪律）

**对象**：本节约束的对象是**主 agent**，不是子 agent。子 agent 自身的执行纪律（传感/纠偏/范围）由本文件其他条款管；本节管的是**主 agent 看到子 agent 失败时该怎么做**。

**触发条件**：派出的子 agent 返回失败——空结果、超时、未完成、报错空手——主 agent **不得立刻换路或放弃**，必须按控制论闭环恢复。

| 步骤 | 主 agent 动作 |
|---|---|
| **传感（先于纠偏）** | 先分析子 agent 回执（或空回执）：是哪类失败——工具调用报错（编译/测试失败）/工具超时/上下文不足/任务描述歧义/未给清所需权限。没回执看仓库现状（git log/状态/diff）反推子 agent 走到哪 |
| **恢复 session** | 仅对 `INTERRUPTED`、`TIMEOUT`、`INCOMPLETE` 使用原子 agent 的 `task_id` 恢复原 session；终态不得传旧 `task_id`。恢复必须保持目标/角色/范围一致，并计入同一任务最多 5 次的累计恢复预算 |
| **纠偏只补误差点** | 恢复会话的 prompt 只补本轮失败点的缺失信息：补漏改的 file:line、补没说清的约束、补被遗漏的不变量、补测试/验证命令。**不重新描述整个任务**（子 agent 已有上下文）。守本文件 §4.5 范围防越界 |
| **5 次硬预算** | 同一子 agent 同一目标最多 5 次恢复重试。每次恢复前必须有新的纠偏信息传给子 agent，不能凭空"再试一次看看" |
| **5 次后仍失败才升级** | 5 次恢复后子 agent 仍未完成，主 agent 才可：（a）升级到 `@oracle` 重新诊断方案是否走偏；（b）亲自接手最小剩余改动（守主 agent 直接做边界）；（c）向用户报告并 question 拍板下一步 |

**串联约束**：子 agent 内部步骤的串联（编译/测试/提交/合并）由子 agent 自己负责；主 agent 关心的是**任务级**串联——上个子 agent 失败恢复 5 次仍不收敛才考虑换路。

**反模式**：
- 子 agent 一次空返回主 agent 就换路或放弃 —— 禁，先用完 5 次恢复预算
- 可恢复态却新开 session 重做 —— 禁，必须用原 `task_id` 恢复；终态却传旧 `task_id` —— 禁
- 恢复 prompt 重新描述整个任务 —— 禁，只补误差点缺失信息（守 token + 用已有上下文）
- 5 次后空手向用户"做不到" —— 禁，必须先尝试 (a) 升级 oracle 重诊断 或 (b) 主 agent 亲自接手最小改动，并向用户给出传感读数（已尝试什么、剩什么没试、为何 5 次不收敛）

**配套纪律**：主 agent 在派发复杂任务时仍应给出**可执行清单**（守 §4.5）+ 必要不变量提示，从源头降低子 agent 失败概率；子 agent 失败后是否提示重试也由主 agent 主动发起，不依赖子 agent 自纠偏。

## 6. 主 agent 直接做（不派发）

- 单文件单点小改（< 20 行）
- 信息已在上下文、调度开销明显大于收益
- 最终结论整合、跨 lane 冲突裁决、面向用户的中文答复与提问

## 7. 与用户衔接

用户是终裁者，但也是**有限带宽、有限观测的信号源**。与用户衔接的真正目标不是"把决策扔给用户"，而是**维持经过用户的反馈回路可观测**——让用户在读得懂的粒度上做知情决定，而非被高上下文淹没后橡皮图章。假监督有两副面孔：**信息不足**（用户读不懂 → 盖章）与**信息过载**（警告洪水淹没带宽 → 盖章），两者同为失控。决策点用中文 question 向用户拍板，subagent 不替用户做架构决定。以下三支柱共同防守。

### 7.1 决策可评估性（举证责任在主 agent）
- 呈递决策 = 可判断粒度 + 证据（引 `file:line`）+ 关键权衡 + 不确定性/风险 + 推荐及理由。这是 §4.1/§4.4 的证据标准从"子 agent→主 agent"延伸到"主 agent→用户"，不另起一套清单。
- **可评估性 = 信息量最优化，不是最大化**：呈递到用户能做知情判断的**最小充分粒度**即止。上不轰炸（守带宽），下不空结论（留抓手）——支柱 1 的上界与支柱 3 的下界在这一点会合。

### 7.2 冲突上浮（检测器 + 上报器，不是裁决器）
- **总纲**：上浮是**举证义务，不是否决权**。主权恒归用户。你的职责是确保用户的 override 是**知情的（informed）**，不是确保它**正确**。
- **禁令**：禁止以"我理解架构/控制论"为由，拒绝执行已知情的用户指示。
- **冲突分三级，动作不同**：
  - 撞设定值不变量 / 硬约束 → **必须上浮一次**，明示违反哪条编号（I?/R?）+ 推荐 + 风险
  - 撞传感事实（用户说的 `file:line` 不存在 / 现状已变）→ 陈述事实一次
  - 仅次优 / 风格 → 可提，不阻塞
- **一次性原则**：冲突上浮是一次性的。用户 informed override 后即执行，不再就同一冲突反复示警。唯一例外：override 撞**不可逆 / 影响面大 / 安全相关**操作，可再确认一次；确认后仍执行（撞内置安全护栏的走护栏，不由本纪律覆盖）。

### 7.3 带宽分级（判据写死，模糊即上浮，自决必留痕）
- **判据由本文档固定，agent 无权运行时自行放宽**。可逆性 / 影响面语义**对齐系统安全护栏的 low/medium/high 分级**，不另立阈值。此节与 §6「主 agent 直接做」是同一套"何时自决"标准，不重复造。
- **自决白名单**：单文件 < 20 行且信息在上下文、纯读、一键可回滚的本地改动、lint/format；
  布局语义可逆 + 单 primitive 全部消费者一致 + 用户已给方向 → 白名单（不上浮 oracle；改 shared 多消费者或真改 I*/R* 仍走黑名单）。
- **必上浮黑名单**（均属安全护栏 high 线）：删多文件、改设定值宪章（`NORTH_STAR.md`）、改硬约束（I1-I12/R1-R12）、改 auth、改生产、任何不可逆操作。
- **模糊即上浮**：判定落在白名单外、或可逆性/影响面存疑 → 一律上浮，不默认自决。
- **自决必留痕**：自决要留痕（改了什么 + 为何判低风险 + 依据哪条白名单），供用户抽查。**举证责任倒置**——agent 为"我判低风险所以自决"举证，不是用户为"你不该自决"举证。无留痕的自决 = 违规。

### 7.4 防表演性上浮（假监督的镜像）
- 上浮本身消耗用户带宽，**故上浮同受带宽分级约束**：分级 + 批量 + 带推荐，降低用户解码成本。抛警告洪水免责 = 用决策疲劳逼出橡皮图章 = 假监督换个方向。
- **批量呈递**：同类中低风险决策攒一批一次过目，不逐个打断。
- **默认值 + 反对期**：给默认推荐"若无异议我按 X 推进"，沉默视为通过——**仅限可逆决策**，不可逆的必须显式确认（对齐 7.3 黑名单）。
- **信噪比可事后审计**：上浮后用户次次 override，说明 agent 误判了严重度，该校准阈值。

### 7.5 缺口与漂移（P1，明示不装可信）
- **谁盘查主 agent 的呈递**：主 agent 自己也是模型，对"够不够格上浮 / 呈递够不够可评估"的判断也会漂移。高风险决策的证据链，落用户前可选择性外包 `@reviewer`/`@oracle` 预审一次。别把"用户 0 噪声"的假设平移成"主 agent 呈递 0 噪声"。
- **override 不跨会话漂移**：用户一次性 informed override 进 handoff 的"纠偏"层留痕时，**必须标注"用户一次性 override，非宪章变更"**——否则一次性例外会漂移成永久规则，污染设定值（见 `SESSION-HANDOFF.md`）。

### 7.6 真机与异步
- 真机实测 / 性能指标（帧率等）交用户跑，沙箱无 GUI；主 agent 不阻塞等待真机结果，默认视为通过继续推进，仅当用户主动回报异常时再介入修复。此"默认通过"限于真机实测，**不得扩用到不可逆决策**（那走 7.3 黑名单）。

## 8. 跨会话（时间维延伸）

本文件管"同一会话内主 agent 如何调度子 agent"。**跨会话如何保住工作记忆**见同目录 [`SESSION-HANDOFF.md`](SESSION-HANDOFF.md)：在上下文压缩前主动停、按控制论五层结构化转储、新会话冷启动核对后续接。两者共同支撑长时自动化任务——调度纪律让单会话扛复杂度，交接让多会话扛时长。
