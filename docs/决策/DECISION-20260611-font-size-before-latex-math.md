# 决策：先扩展字体字号能力再实现 LaTeX 数学公式

## 背景

项目计划增加数学公式渲染能力，输入以 LaTeX 风格数学语法为主。现有 HTML-like 文本链路主要按统一字号测量和绘制字符串，公式排版需要上下标、分式、根号、大运算符等多级字号与二维盒模型。如果直接引入外部 LaTeX/AWT 渲染器，公式字体、fallback、字符覆盖规则和现有 `FontService` 可能不一致。

## 候选方案

- 先接入外部 LaTeX 渲染库，快速生成公式位图。
- 直接在公式模块里临时缩放文本绘制，绕过字体引擎字号能力。
- 先扩展字体引擎字号能力，再基于统一字体系统实现公式 AST 与 box layout。

## 最终选择

先扩展字体引擎的字号能力，再实现数学公式渲染和排版能力。

## 选择原因

- 数学公式依赖多个字号层级，必须让字号参与文本测量、布局、裁剪和绘制，不能只在最终绘制阶段套 `GL11.glScalef(...)`。
- 底层 glyph 渲染以矩形面片为核心时，应按目标 UI 像素尺寸提交 glyph quad；后续高清大字号可让 glyph atlas 按 `font + codePoint + weight + style + fontSizePx` 区分缓存。
- 公式普通符号、希腊字母、上下标和文本片段应复用现有字体匹配、fallback 和字符字体规则，避免与 UI 普通文本割裂。
- 自研公式 AST + box layout 可以控制能力边界，先实现 LaTeX 数学子集，不把完整 TeX 宏系统作为首期目标。

## 影响范围

- 字体系统需新增字号维度，覆盖测量服务、文本布局、glyph 度量、glyph/page 缓存和批量渲染。
- HTML-like 文本布局需记录布局时字号快照，确保 paint command、裁剪和 hit-test 使用同一口径。
- 数学公式模块应在字号能力稳定后接入，作为 replaced element 或内部公式控件参与文档布局与绘制。
- 使用文档、LTS API 清单和当前态计划需要在能力落地时同步更新。

## 后续注意事项

- 对外建议使用 UI 像素 `font-size` 心智，内部再映射到 glyph quad 的目标像素尺寸；不要把原始 GL 变换暴露给页面作者。
- 需要保持默认字号映射与当前视觉效果兼容，避免已有页面文本尺寸变化。
- 首批公式能力只承诺 LaTeX 风格数学子集，优先覆盖 `^`、`_`、`\frac`、`\sqrt`、常见希腊字母、基础大运算符和 inline/block 公式。
- 实现批次至少通过 `git diff --check`、相关定向测试和 `compileJava`；涉及游戏内视觉时再使用 `runClient21` smoke。
