# 配置同步分类 alias 与 smoke 顺序依赖

## 错误现象

`/qzuilib test` 中直接点击最后一项“运行时配置同步”会失败，状态提示为“属性不存在。”；先点击倒数第二项“运行时远程 HUD”后，再点击最后一项则可以通过。

## 触发场景

- 配置同步目标使用 `fontSystem` 等主分类名描述字段。
- 运行时权威 `Configuration` 中可能存在历史小写分类名，例如 `fontsystem`。
- 配置同步 smoke 在打开会话后立即通过 `Channel` 上报字段变化，并通过 `Fetch` 保存仅包含单字段的部分草稿。

## 根本原因

- 分类解析规则不统一：定义捕获路径曾隐式尝试小写分类，保存路径却直接使用主分类名查询权威配置。
- Forge 1.7.10 的 `Configuration.getCategory(...)` 不是无副作用查询；分类不存在时会创建空分类，导致后续属性读取为空并冒出“属性不存在。”。
- smoke 只提交单字段草稿，放大了 Channel 与 Fetch 处理顺序差异，形成“先跑其他网络用例后更容易通过”的错觉。

## 修复方案

- 配置分类默认按大小写敏感精确匹配；只有 `CategorySpec.addAlias(...)` / `ConfigSyncCategorySpec.addAlias(...)` 显式声明的历史名称才参与兼容查找。
- 配置同步定义快照记录实际解析到的分类名，保存、回滚、草稿读写都使用同一套已确认存在的分类解析。
- 保存前缺失权威分类或属性时，返回明确的配置同步错误，不再把空属性传入通用属性校验。
- 配置同步 smoke 仍走 Channel 上报一次 no-op 字段变化，但 Fetch 保存携带完整打开草稿，避免单独运行依赖前置 smoke 的预热状态。

## 预防措施

- 不要把 `Configuration.getCategory(...)` 当作查询 API；查询前必须先通过 `hasCategory(...)` 或统一解析工具确认存在。
- 新增历史分类兼容时必须显式声明 alias，不要引入隐式忽略大小写匹配。
- 运行时 smoke 如果需要验证异步 Channel 与显式 Fetch 保存，应避免用不完整草稿制造额外时序敏感性。
