# ERROR-20260629 决策升级未做尽职调查：双向严父依赖物理不可能却升级并提交

## 错误现象

2026-06-29，主 Agent 将架构决策 `DECISION-20260628`（config 与 uilib 包依赖方向）升级为"双向严父依赖"（config 与 uilib 相互独立、只能软依赖），并直接修改决策文档提交（commit `8bf5372f`）。

事后经 Oracle 裁决与用户拍板，发现该升级在物理上不可能成立：

1. **与决策自身 L41 物理冲突**：决策文档 L41 明确「配置页业务全在 config UI 层内」，而"双向严父依赖"要求 config 与 uilib 相互独立只能软依赖，二者直接矛盾，升级前未做一致性检查。
2. **反射化硬点未识别**：P0/P1 已落地代码中 `ConfigScreen extends AbstractSceneHostWidget` 这条继承关系是 compile-time 硬依赖，反射化不动，物理上无法拆成软依赖。
3. **违反 Java 语言事实**：Java 语言层面"接口契约本身就是 compile-time 依赖"，双向禁 import 在 retaining type safety 前提下物理不可能。

升级 commit 已被 revert（`3f153ae8`），改用精确三档红线（`6648ddb5`），再扩大豁免（`ee1e181d`）。

## 触发场景

用户提出架构方向变化："config 与 uilib 应相互独立只能软依赖"。

主 Agent 未做任何可行性尽职调查，直接：

- 修改决策文档 `DECISION-20260628`，升级为"双向严父依赖"
- 未派 Oracle 做架构可行性评估
- 未读 P0/P1 已落地代码识别硬点
- 未对照决策其他条款（L41）做一致性检查
- 直接 `git commit`（`8bf5372f`）

即"用户说啥就改啥"，把用户提出的架构方向意图直接当成可行性已验证的结论动手改文档。

## 根本原因

1. **未核实 Java 语言层面底层事实**：没有确认"接口契约本身就是 compile-time 依赖"这个 Java 语言事实，导致"双向禁 import 仍 retaining type safety"的方案在物理上不可能成立却未被识别。
2. **未读已落地代码识别硬点**：升级前没有读 P0/P1 已落地代码，未识别 `ConfigScreen extends AbstractSceneHostWidget` 这条继承关系是反射化不动的 compile-time 硬依赖。
3. **未做决策条款一致性检查**：升级前没有对照决策文档其他条款（尤其是 L41「配置页业务全在 config UI 层内」）做一致性检查，导致升级与既有条款物理冲突。
4. **未派 Oracle 做架构可行性评估**：包依赖方向属于物理约束级别的架构变更，升级前应派 Oracle 做可行性评估，但主 Agent 直接动手改决策文档。
5. **把用户确认意图等同于可行性已验证**：AGENTS.md §0 明确「信条和不变量本身的改动属重大架构变更，必须经用户确认」，但用户确认的是"架构方向意图"，不等于"可行性已验证"。主 Agent 混淆二者，听用户说啥就改啥。

## 修复方案

1. **revert 错误升级 commit**：`3f153ae8` 撤销 `8bf5372f` 的"双向严父依赖"升级。
2. **精确三档红线**（`6648ddb5`）：
   - 核心层零依赖
   - config UI 层硬依赖
   - `uilib.ui.*` 严禁反向 import `config.ui.*`
3. **扩大豁免**（`ee1e181d`）：uilib 自身 mod 配置接入代码可 import config 全部包（config schema / runtime / ui），放在专门包内不污染通用组件包 `uilib.ui.*`。

## 预防措施

1. **任何决策升级必须先派 Oracle 做可行性评估**：尤其涉及包依赖方向这种物理约束级别的架构变更，升级前必须派 Oracle 做架构可行性评估，单次工具超时不超过 300 秒（AGENTS.md §7 子代理工具超时约束）。
2. **升级前必须读相关已落地代码识别硬点**：识别 `extends` 关系、compile-time 硬依赖类、Java 语言事实等物理约束，不能仅凭推理或用户口述就动手。
3. **升级决策时必须与其他条款做一致性检查**：标注潜在冲突，冲突未解决前不得升级并提交。
4. **用户提出架构方向变化时，先做可行性尽职调查再动手改文档**：不要"用户说啥就改啥"，用户确认意图不等于可行性已验证。
5. **AGENTS.md §0 已明确「信条和不变量本身的改动属重大架构变更，必须经用户确认」**——但用户确认意图不等于可行性已验证，仍需走尽职调查流程（派 Oracle / 读代码 / 一致性检查）后再动手改文档。
