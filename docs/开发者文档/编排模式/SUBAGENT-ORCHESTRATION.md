# 子代理编排模式

> 本文件定义两类固定编排，供主 Agent 在同类问题中复用。
> AGENTS.md 第 7 节"Subagent 协作"指向本文件作为编排详细规范。

## 何时使用

主 Agent 判断任务性质后选用对应编排：

- **bug 排查 / 疑难诊断**（用户报错、性能问题、行为异常、根因不明）→ 用「多 Oracle + Librarian 复核编排」
- **明确改动实施**（已确认根因/方案、特性开发、重构落地）→ 用「编排二：ABC 循环单元」

两类编排可串联：先用复核编排定位根因，再用实施编排落地修复。

## 编排一：多 Oracle + Librarian 复核（诊断型）

### 适用场景
- 真机报错/卡死/异常，根因不明
- 怀疑系统性设计缺陷，需要多视角交叉验证
- 需要对比行业标准判断当前做法是否合理
- 用户主动要求"复核""审查""排查"

### 执行结构
```
并行派发（同一消息内多个 task 调用）：
  Oracle A1 —— 代码侧诊断（读源码、追链路、定位嫌疑）
  Oracle A2 —— 另一侧诊断（与 A1 分工，如布局引擎侧 vs 数据侧）
  Librarian  —— 行业标准调研（Qt/Flutter/Compose/Web 对比 + 最佳实践）

主 Agent 汇总三方结论 → 给用户综合报告 + 真机验证清单
```

### 分工原则
- A1/A2 按问题域正交切分（如"字体度量侧" vs "布局引擎侧"），避免重复读同一批文件
- A1/A2 在任务书中互相提供协作线索（"需 A2 验证 X"）
- Librarian 独立调研行业标准，不读项目源码，只产出对比事实
- 三方结论汇总后若一致→高置信；若分歧→主 Agent 裁决或追加一轮

### 输出要求
- 每个 agent 产出：根因假设排序 / 证据链 / 未验证风险
- 主 Agent 综合：问题清单（按严重度）+ 行业对比 + 改进方向（不实施）
- 交付给用户的报告必须明确"已验证事实" vs "推测"

### 完成后
- 若根因明确且需修复 → 转入「编排二」实施
- 若根因仍不明 → 追加真机验证项交用户跑，或追加一轮复核
- 复核结论沉淀到 `docs/决策/` 或 `docs/开发者文档/errors/`

## 编排二：ABC 循环单元（实施型）

### 适用场景
- 根因/方案已确认，需要落地修改
- 特性开发、重构、易用性优化等明确改动
- 用户主动要求"开始优化""实施""修复"

### 执行结构
```
A (oracle) —— 规划：分批裁决 + 每项具体方案 + 测试策略 + 风险评估 + 给 B 的有序执行清单
B (fixer)  —— 实施：按 A 的清单执行 + 写测试 + 编译验证 + 全量测试 + git 提交
C (oracle) —— 复审：读 B 的产出，评定正确性/测试有效性/不变量/遗漏；通过则该单元结束，不通过则给修复项回到 A 重新规划
```

**循环**：一个 ABC 单元完成后，C 复审若发现仍有未完成项或有新的下一批工作，可直接衔接下一个 ABC 单元（C 的结论作为下一单元 A 的输入），首尾衔接直到全部任务完成。无需独立的终审环节——最后一个 ABC 单元的 C 复审即终审。

### 各环节纪律
- **A**：必须给 B 可执行的有序清单（改哪个文件、改什么、加什么测试、验证命令），不只是方向
- **B**：严格按 A 清单执行；测试全绿才提交；提交标题 `[English]: 中文标题` + 中文 Markdown 正文
- **C**：只读不改，逐项核对 A 的规划是否落地；发现遗漏明确标 P0/P1/P2 并裁决"回 A 重规划"或"该单元通过"；通过时给合并建议

### 范围控制
- A 在规划阶段裁决分批（哪些本轮做、哪些后续做），B 不越界
- 现有已验证可用的调用方默认不迁移（避免零收益回归风险），迁移单列后续批
- 每批改动是"单调增量"（加约束/加诊断/加封装）优于"触碰核心数学"

### 验证纪律
- B 每步：编译 + 全量测试绿才提交
- 单次工具调用超时不超 300 秒（守全局规范第 4 节）
- C：引 file:line 作证据，不空泛评定

### 完成后
- 最后一个 ABC 单元 C 通过 → 交接记录更新 → 任务完成
- C 不通过 → 回 A 重规划修复项
- 决策类结论沉淀到 `docs/决策/`

## 通用纪律（两类编排共用）

### 派发与分工
- 为降低主 Agent 上下文与 token 成本，优先把可外包的工作派给专职 subagent，主 Agent 聚焦规划、裁决、整合与验证，不做默认实现工人
- 优先派发：代码侦察/定位/"X 在哪"派 explorer（返回压缩上下文，勿让主 Agent 全量读文件）；库用法/官方文档/版本行为/疑难 bug 外部调研派 librarian；架构裁决/方案深评/反复修不好的问题/代码与简化审查派 oracle；明确范围的实现、测试编写、机械改动派 fixer；UI/UX 设计与视觉实现、设计走查派 designer
- 派发时只传路径/行号/线索，不贴整文件（如 `HtmlLikeDocumentWidget.java:495`），守 token 成本规范
- Oracle 模型成本高，除任务中断恢复外一律新开 session

### 主 Agent 直接做（不派发）
- 单文件单点小改（小于 20 行）
- 信息已在上下文、调度开销明显大于收益的活
- 最终结论整合、跨 lane 冲突裁决、面向用户的中文答复与提问

### 并行与串行
- 只读 agent（explorer/oracle/librarian/designer 等侦察/调研/审查）可并行派发（同一消息多个 task 调用）
- 写盘 agent（fixer）必须串行执行，不得并行多个 fixer；读与写不得同批并行

### Session 复用
- 优先复用交接记录里登记的可复用专家 session（如 `ora-1`/`exp-2`/`fix-2`），省去重复建上下文的 token
- 复用时必须在 task 的 `task_id` 显式传该 session 别名，仅在正文写"复用"无效

### 中断恢复
- 子代理中断（空结果/超时/未完成）必须用原 task_id 恢复原 session，不新开让其空跑重做

### 独立审核
- 实现完成后必经一次独立审核：代码用 @reviewer，架构复核用全新 @oracle session

### 派发主 Agent 不亲自做的活
- 真机日志排查（`run/client/logs/fml-client-latest.log`）、批量文件检索一律派 subagent，主 Agent 不亲自全量读

### 与用户衔接
- 决策点用中文 question 向用户拍板，subagent 不替用户做架构决定
- 真机实测/帧率必交用户跑，沙箱无 GUI；主 Agent 不阻塞等待真机结果，默认视为通过继续推进，仅当用户主动回报真机异常时再介入修复
