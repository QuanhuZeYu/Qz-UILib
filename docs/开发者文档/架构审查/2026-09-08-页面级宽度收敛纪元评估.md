# 页面级宽度收敛纪元评估（方案 D）

> 日期：2026-09-08
> 状态：方案 D 已实施（核心代码与消费链完成，待全量构建验证）
> 关联：提交 `e61e92d6`（装配期 advance 回填）、测试 `MarkdownTableColdWidthTest`、`踩坑记录.md` 2026-09-08 条目

## 一、问题

用户报告「同一次游戏内，第一次打开 Markdown 页面错误、第二次正确」。上一轮已定位并修复主因：冷启动宽度测量预算
（`FontConfig.widthCacheMissBudgetPerWindow = 64`，每 16ms 窗口）耗尽后，`TextLayoutService#measureCodepointWidth`
返回固定 `spaceWidth` 近似值且不写缓存（`TextLayoutService.java:1466-1469`），CJK 被低估 55.6%（见 §二.4 实测），
列宽随之算窄、文字压过表格竖线；布局产物被缓存，错误留到下一次重新布局。

已交付的修复（`e61e92d6`）是**装配期回填**：`GlyphRuntimeTables#publishAssembledAdvance` 把
`GlyphGenerator` 早已算出、此前被丢弃的 `TextLayout.getAdvance()` 按 `measureAwtWidth` 同式归一化写进宽度缓存。
实测把该场地的测量 miss 从约 89 降到 5，预算压力大幅缓解。

**但回填不覆盖「布局早于装配」的那一帧**：页面首次构建时字形尚未 RESIDENT，宽度缓存为空，仍要走 AWT 测量；
一旦该窗口预算耗尽，近似值进入布局产物，而页面**没有任何机制**在字形就绪后主动重算——用户只能靠关掉再打开。

方案 D 的目标：**让页面层布局产物对「宽度从近似态收敛到真实态」这件事敏感，自动失效重算**。

### 2.2 纪元的语义与来源：只有「字体换代」一种

- `FontService.getTextMeasureEpoch()`（`FontService.java:546-549`）返回 `ActiveFontGeneration.textMeasureEpoch`，
  由 `FontGenerationBuildRequest` 保证「每构建一代 +1」（`FontGenerationBuildRequest.java:30-31` 的不变量）。
- chat3 用的是**另一个**纪元：`FontService.getRuntimeVersion()`（`ChatMarkdownPipeline.java:380`、
  `ChatSceneController.java:86-88`），同样只在字体换代时变化。

**两者对「宽度缓存从近似态收敛到真实态」完全不敏感**——这就是缺口。

### 2.3 缺口定位

| 数据源 | 当前信号 | 页面层是否可见 |
| --- | --- | --- |
| 字形几何就绪 | `GlyphRuntimeTables.inkEpoch`（`:50-63`），`cacheGlyphGeometry` 时 +1 | 仅 LaTeX（经 `LatexCache`） |
| 宽度缓存填充 | **无任何信号** | 否 |
| 近似值产生 | **无任何记账**，只有统计计数 `widthCacheBudgetRejectedCount` | 否（仅诊断） |

### 2.4 压力实测（本次评估新增）

用 Python 从 `MarkdownTableColdWidthTest` 的 `SOURCE` 字面量还原样本（脚本：工作站 `temp/cold_width_budget_pressure.py`）：

| 口径 | 字符数 | 去重码点 | 相对预算 64 |
| --- | --- | --- | --- |
| 整段样本 | 195 | **89** | 超出 25 |
| 表格行 | 143 | 63 | 恰好在内 |
| 正文行 | 52 | 38 | 在内 |

构成：CJK 统一汉字 56、ASCII 28、CJK 标点/全角 5。

近似分支误差（`charSize = 9.0`、`spaceWidth = 4.0`）：CJK 低估 **55.6%**，ASCII 小写低估 11.1%。

即：**冷启动首帧一屏的码点规模本身就在预算量级上**，游戏内叠加聊天与正文后必然越界；越界的那部分字符被按空格宽排版。

## 三、方案 D 的定义与边界

### 3.1 框架级落点

**数据源在字体层，消费只在页面层**：

1. `GlyphRuntimeTables`（字体层数据）：新增「宽度近似债务」记账与「宽度收敛代」。
2. `TextLayoutService`（字体层服务）：近似返回时记账、真值写入时清账；暴露 `currentWidthConvergeEpoch()`。
3. `DefaultTextMeasureService.getEpoch()`（**页面层端口**）：返回「字体换代代 + 宽度收敛代」的复合值。
4. chat3 两处改用同一纪元来源，消除「双纪元」不一致。
5. `LatexCache` key 并入宽度收敛代（LaTeX 盒宽同样依赖 advance）。

### 3.2 页面范围边界（本次只做这些）

- 改 `TextMeasureService.getEpoch()` 的实现与它的消费方（§2.1 表内全部）。
- **不改** `FontService.getTextMeasureEpoch()` 的返回值——它参与 generation 构建协议不变量，混入宽度代会破坏
  `textMeasureEpoch == baseTextMeasureEpoch + 1` 的校验。
- **不改**测量算法、归一化口径、渲染层、atlas 装配流程。
- **不新增**第二套缓存或第二套布局引擎。

## 四、设计要点

### 4.1 为什么不能逐字形 bump

`publishAssembledAdvance` 每个字形调用一次。若每次就 +1 纪元，页面层后果是：

- `SceneLayoutEngine.layout` 每帧把所有已测文本叶 `markSelfLayout()` → 下帧全页重测；
- `ChatLineLayouter.layoutInternal` 直接 `cache.clear()`（`:145-148`）→ 聊天全部消息重切分；
- `TextLayoutEngine` / `PrefixWidthCache` 全部 miss。

冷启动装配成百上千字形 = 成百上千次全页重排，**不可接受**。节流是硬约束，不是优化。

### 4.2 收敛信号：近似债务记账（推荐）

语义：**只有「曾经用过近似值」这件事才产生债务；债务清偿完毕才是一次收敛。**

- 记账点：`measureCodepointWidth` 的预算耗尽分支（`TextLayoutService.java:1466-1469`）→ 置位该码点。
- 清账点：同一码点的真值写入——测量成功（`:1471-1472`）或装配回填（`publishAssembledAdvance`）。
- 收敛点：债务计数由 > 0 归零时 `widthConvergeEpoch++`。

实现：按码点 bitset（`long[CODEPOINT_COUNT / 64]`，约 139 KiB/字重，相对 `widthCache` 的 4.4 MiB/字重可忽略）
+ `AtomicInteger` 债务计数。装配线程与布局线程都会写，须原子。

**为什么必须是精确到码点的集合**：若只记「近似次数 / 真值写入次数」两个计数器，同一帧里 64 个正常测量的真值写入
会立刻把 25 笔债务「冲平」，导致过早收敛。必须按码点对账。

### 4.3 复合纪元

`getEpoch()` 的契约只要求「变化时返回新值」，消费方（`SceneNode.lastMeasuredEpoch`、`ChatLineLayouter.cachedEpoch`、
`TextLayoutEngine.cachedEpoch`）一律做 `!=` 比较。故复合值只需可区分：

```
return (generationEpoch << 16) | (widthConvergeEpoch & 0xFFFF);
```

（generation 远小于 32768；收敛代一次会话内不会绕回 65536。）

### 4.4 收敛是幂等的

债务归零后不再有新的近似产生（缓存已填），纪元停止变化 → 稳态零重排。这是方案 D 相对「周期性强制重排」的关键优势。

## 五、影响面与风险

| 风险 | 说明 | 处置 |
| --- | --- | --- |
| 纪元抖动 | 装配线程在布局过程中清账 → 同一帧不同节点看到不同 epoch | 自限：债务归零后停止；代价是收敛期多一帧重排 |
| 聊天缓存全清 | `ChatLineLayouter` 在 epoch 变化时 `cache.clear()` | 收敛次数 = 冷启动期 1~N 次，可接受；不做改动 |
| 与 generation 协议冲突 | `FontService.getTextMeasureEpoch()` 不可改 | 只在页面层端口复合，见 §3.2 |
| 债务永不清偿 | 某近似码点此后既不被装配也不被重测 | 保守不 bump，保持现状（不劣化） |
| 双纪元残留 | chat3 仍用 `getRuntimeVersion()` | 本次一并改到统一来源 |
| 复合值回绕 | `widthConvergeEpoch` 超 65536 | 实际不会；必要时改 long 组合或 32 位异或 |

## 六、备选方案对比

| 方案 | 做法 | 能否自愈 | 代价 |
| --- | --- | --- | --- |
| A 取消预算 | `budget <= 0` 恒真 | 不适用（不再有近似） | 冷启动卡顿，失去保护 |
| B 均值兜底 | 近似分支返回「已测字符平均宽」 | 否（仍是近似且被缓存） | 误差从 55.6% 降到个位数，但错误仍固化 |
| C 延迟布局 | 布局等字形就绪 | 是 | 首帧空白/骨架，改动面最大 |
| **D 收敛纪元** | **本次评估对象** | **是** | 中：约 280 行 + 测试 |
| H 布局产物标记「含近似」 | 只在受影响的布局上失效 | 是，粒度最细 | 需要贯穿所有布局产物的标记通道，改动面大于 D |

结论：**B 与 D 互补而非互斥**（B 降低误差量级，D 保证最终收敛）；若只做一件，D 的保证更强。

## 七、验证方案

1. **关系形锁**（`MarkdownTableColdWidthTest` 同场地扩展或新增）：预算收紧 → 布局 → 装配 → 再布局，断言
   第二次列宽向量 == 无预算列宽向量，且 `epoch()` 在收敛后发生变化。
2. **稳态锁**：收敛后连续 N 次布局，`epoch()` 恒定、`ChatLineLayouter` 缓存不再清空（钉住不雪崩）。
3. **负向验证**：停用债务置位（或停用收敛 bump），锁 1 必红；`finally` 恢复并校验锚点。
4. **全量**：`gradlew.bat build` + checkstyle；测试计数由 Python 读取 JUnit XML 汇总。

## 九、实施后的边界与验证项

1. **游戏内布局与装配的时序**：若页面首次布局必然早于字形 RESIDENT，方案 D 的收益最大；若布局总在装配之后，
   收益只落在「预算耗尽」的兜底上。判据：在软件渲染场地复现「布局 → 装配 → 再布局」并观察列宽是否自愈（锁 1 即是）。
2. **是否同时并入 `inkEpoch`**：LaTeX 盒宽依赖 advance，理论上也需宽度收敛；但 `LatexCache` 已含 `inkEpoch`，
   两者是否冗余需实测确认。
3. **是否同时实施方案 B**：B 能把误差从 55.6% 降到个位数，让「收敛前的首帧」观感更好，代价是继续使用近似值。
4. **复合值的位宽约定**：已采用高 16 位 generation、低 16 位收敛代；消费方只做 `!=` 比较。一次会话内收敛代应远小于 65536，generation 代应远小于 32768。
