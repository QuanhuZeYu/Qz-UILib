## C-01：文本编辑能力与 R9 冲突

**能力范围已裁决**：用户选择常规完整编辑能力，见反向需求基线 D-02。旧“光标恒末尾、不做选区/剪贴板”等能力限制不作为新规格约束；D-03 已确认编辑文本与业务最终值分开，各自有明确权威；D-04 已确认业务按场景声明提交策略；D-05 已确认明确拒绝时保留草稿、说明原因且不抢回焦点；D-06 已确认以实际修改开始编辑会话，按声明的完成动作及接受结果结束，完成后显示规范化文本，焦点不单独决定会话；D-07 已确认异步提交期间可继续编辑，旧结果不得覆盖新草稿或结束新会话；D-08 已确认外部更新策略交业务决定，草稿与业务值操作必须明确区分；D-09 已确认草稿生命周期由业务管理，控件卸载不隐含提交或丢弃草稿；结果权威顺序继续确认。源码红线及实现本轮尚未修改。

**双方**：[控件 R9](<D:/Code/MC/Qz-UILib/src/main/java/club/heiqi/uilib/ui/scene/control/package-info.java#L105>) 要求零内部状态，caret 永远末尾，明确不做选区、方向键、字符定位、IME、剪贴板、闪烁；[文本控件指南](<D:/Code/MC/Qz-UILib/docs/使用文档/02-控件/场景文本输入与浮层.md#L65>) 已声明复制/剪切/粘贴/全选/撤销/重做；[生产编辑模型](<D:/Code/MC/Qz-UILib/src/main/java/club/heiqi/uilib/ui/scene/control/SceneTextInputPrimitive.java#L195>) 创建 selection/caret 等模型。

**矛盾**：同一标准文本控件不能同时遵守“光标恒末尾无选区”和“字符编辑/选区操作”。R9 没有把档位 A 限为历史参考，仍是包级合并红线。不能以“新代码已有”默认废掉红线，也不能用旧红线删去现用能力。

**推荐**：保留外部业务文本的权威与回调确认，将 selection/caret/编辑事务明确为 UI 编辑状态而非第二份业务真值；档位 A 改为旧能力范围或限定能力档位。IME 的原生承诺单列，生产模型有选区不证明 IME 完整支持。

**裁决与验收**：明确标准输入最低能力、readOnly/disabled 差别、外部拒绝变更时编辑状态如何同步；生产控件验证中间编辑、代理对删除、选区与剪贴板、外部替换值。当前阶段只记录。

## C-02：preferred 的含义不一致

**表达方向已裁决**：用户选择 A，见 D-10。固定、自然、填充/剩余空间分配明确区分，最小/最大边界独立声明，同一种声明不因宽高或容器种类变义。D-11 已确认自身最小/最大边界优先，固定尺寸也受限制，最小值大于最大值须明确报出。D-12 已确认父空间不足也不突破最小尺寸；D-13 已确认普通容器默认允许溢出，裁剪与滚动明确声明；D-14 已确认固定尺寸经自身边界限制后不因父空间不足自动缩减；D-15 已确认自然尺寸默认不缩减，声明的换行重新测量与压小布局盒分别表达；测量与分配细则及旧接口迁移继续确认。以下保留原始冲突证据。

**双方**：[布局宽度模型](<D:/Code/MC/Qz-UILib/docs/开发者文档/布局约束与踩坑.md#L8>) 与 [computeWidth](<D:/Code/MC/Qz-UILib/src/main/java/club/heiqi/uilib/ui/scene/layout/SizingCalculator.java#L110>) 定义 preferredWidth 钉死并不受 max 限制；[SceneNode minWidth 注释](<D:/Code/MC/Qz-UILib/src/main/java/club/heiqi/uilib/ui/scene/node/SceneNode.java#L239>) 同时说 preferred 是目标宽、SHRINK 会被内容取代，随后又说显式钉死不参加 min/max。[grow 尺寸契约](<D:/Code/MC/Qz-UILib/src/main/java/club/heiqi/uilib/ui/scene/layout/ConstraintResolver.java#L587>) 又把 preferredWidth 作为撞底下界；[height clamp](<D:/Code/MC/Qz-UILib/src/main/java/club/heiqi/uilib/ui/scene/layout/SizingCalculator.java#L315>) 将 preferredHeight 作为 max clamp 后不可低于的下界。

**判别**：宽度同处注释的“被内容取代”与“优先钉死”是真矛盾；grow/视口对尺寸的不同解释也可能是上下文特例，不能未经实验宣称所有分支都错。

**推荐**：顶层需求分清固定外尺寸、自然尺寸、最小/最大边界、剩余空间分配。再决定 preferred 在各上下文的单一含义或明确限定含义，避免仅改名称或加特判。本轮不确定新 API，更不更改兼容承诺。

**验收**：在文本、SHRINK 容器、ROW/COLUMN grow、滚动视口分别叠加 preferred/min/max，明确优先级与溢出政策；布局位置、paint clip、hit-test 使用同一盒。整数余数归谁属于低层政策，未经需求不固定末位吸收。

## C-03：首帧派生主题不能为空，但 Computed 默认为空

**已裁决**：用户选择 A，D-17 确认正式主题派生入口保证有效初值并可立即挂载标准控件，后续保持动态更新，业务无需手算初值或主动刷新；不因此将任意 Computed 改成同步求值。下面保留冲突与历史补偿证据，代码尚未修改。

## C-04：Toast 指南要求业务 flush，母本禁止

**已裁决**：用户选择 A，业务提交状态或意图，UILib 负责调度与呈现；最终状态可合并，有顺序意义的操作不得丢失。参见反向需求基线 D-01。下面保留冲突证据与验收；具体实现方式尚未选择，旧指南及代码未修改。

**双方**：[通知指南](<D:/Code/MC/Qz-UILib/docs/使用文档/02-控件/场景文本输入与浮层.md#L116>) 要求同帧两次 show 中间 flush，否则覆盖前条；[State/Intent 母本](<D:/Code/MC/Qz-UILib/docs/开发者文档/规格文档/UI投影宿主语义.md#L31>) 禁止 consumer/content 调 scheduler/flush/layout/paint。

**同一触发**：一个业务回调连续投递成功通知与警告。按指南正确使用就违反母本；按母本正确使用又丢前条。[Toast.show](<D:/Code/MC/Qz-UILib/src/main/java/club/heiqi/uilib/ui/scene/control/SceneToast.java#L468>) 复制 entries.get 再 set；[Signal 读写](<D:/Code/MC/Qz-UILib/src/main/java/club/heiqi/uilib/ui/reactive/Signal.java#L32>) 表明 get 不读 pending。

**推荐**：保留宿主/调度职责边界，由现有通知 Host 累积投递意图；不要求业务主动刷新帧管线。不要把改 Signal.get 全局语义当默认修复。

**验收**：同一业务处理连续不同 show，正常宿主刷新后全部条目依次保留，业务不 flush。同时检查追加与到期处理交错；不把“每次都 flush”的测试当作同帧累积证据。

## C-05：受控文本与帧内事件累计没有共同定义

**状态分工已裁决**：D-03 将编辑文本与业务最终值分开，编辑状态通过框架管理；D-01 要求连续编辑依序保留。旧红线不能再把尚未接受的编辑文本等同于业务值。D-04 已确认按场景声明提交策略；回调协调与具体累计实现尚待收口。下面是原有冲突证据。

**双方**：R9 要求纯函数读取 value.get 算新 String，不得缓存文本；Signal.get 只返回提交值，set 延迟。[TEXT_INPUT handler](<D:/Code/MC/Qz-UILib/src/main/java/club/heiqi/uilib/ui/scene/control/SceneTextInputPrimitive.java#L509>) 读 props.value，编辑并上抛。若 consumer 只排队 set，多次事件处理之间不 flush，则后一次会用旧外部值。

**来源**：[历史同帧中文回归](<D:/Code/MC/Qz-UILib/src/test/java/club/heiqi/uilib/ui/scene/host/SceneTextInputFieldModelTest.java#L13>) 记录过真实丢字族问题；但当前测试 fixture 自建累积字段，不覆盖生产控件。这里是高可信静态风险，未重新运行生产控件确认。

**推荐**：区分“赋最终值”（last-write-wins 合法）与“连续编辑/追加意图”（不得丢）。明确谁在批次内持有编辑工作值、外部拒绝/规范化回调时如何恢复；保持业务值唯一权威，不加 handler flush 或永久第二真值。

**验收**：生产输入经 router 同帧多 TEXT、退格与插入组合，只一次正常提交；每个动作依序作用。单独验证原生 IME 提交、不同 consumer 接受/拒绝模式。

## C-07：ESC 的 scene 消费与 native fallback 未闭环

**合同已裁决**：D-18 确认 ESC 按层处理，消费即停止外层关闭，宿主依据处理结果执行 fallback；页面关闭政策归业务。具体消费回执、输入法/编辑处理与浮层优先级待设计，以下保留静态证据，尚未修改生产代码。

验收小窗口、大字号、长标题与动态内容；标题/操作可达、正文视口有界、独立滚动互不影响。当前只有接入摩擦的源码证据，未认定实机溢出。
