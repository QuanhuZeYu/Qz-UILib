# UILib 反向需求基线

状态：**反向整理草案，供需求审阅**。它提取已有要求、记录实现事实并提出缺口；不覆盖现行规范，不将待裁决建议变成公共兼容承诺。本轮只建立规格与查冲突，不改生产代码、不删测试。

## 1. 目标与依据

用户目标：以真实需求驱动代码，优先消除需求之间未取舍的矛盾；随后让测试只保护真实行为，不让测试里的历史实现反过来定义产品。

UILib 为 UI 作者提供可动态更新、可布局、可交互、可渲染的通用内容；宿主负责输入、投放与生命周期；业务负责意图的业务含义、权限和异步结果。Architect 的重构面板是当前真实消费者，不能把其业务规则搬进通用 UI 核心。

证据基线：UILib 分支 4.0，HEAD `c0b81132d1b0e0de2beb13a6c83f8d7ec6b0a1bb`；Architect 主仓 main，HEAD `2801924d220eb4dac12a1142d04b4dd1326a841c`；重构 worktree codex/rebuild-scratch，HEAD `376057c8e6e0e56ad72cf3d6aa164b7ff7ff9c18`。以上哈希仅作定位，文档链接指向工作目录。

UILib 原有规格索引及 uicore 施工规划存在协作者未提交改动，未修改它们。Architect 消费的开发 jar 标识为 `4.11.0-4-0.40+883888b20e-dirty`，与 UILib 当前 HEAD 不同。不能把本轮源码审查结果直接宣称为该 jar 的行为。

证据优先辨别其用途：

- **现行要求**：用户明确约定、目标仓现行语义母本、明确适用的类契约。发生相互矛盾时记录双方，不能凭代码或测试选胜者。

- **待裁决建议**：本轮提出的规则或取舍。未认可前不改变现有边界。
- **待观测**：有代码线索但无当前版本真实运行反馈。不能写“已复现/已修复”。

## 核心骨架与后续裁定顺序

本节按用户要求从核心骨架组织规格；下方 D 编号保留为稳定的裁定依据，不再把编号顺序作为设计推进顺序。此处归纳已确认语义，不替代原裁定，也不将下面的待确认事项升级为需求。

| 骨架主题 | 已确定的职责与不变量 | 对应裁定 |
| --- | --- | --- |
| 状态与调度 | 状态/派生系统独立成立，直接状态写后立即可读；呈现运行时订阅变化并调度，顺序操作不得丢失 | D-01、D-38、D-39 |
| 状态权威与编辑 | 草稿、业务值分开；业务决定提交、接受/拒绝、外部更新政策；框架协调会话与结果 | D-03 至 D-08 |
| 身份与生命周期 | 框架创建 UUID；普通更新保持交互连续性，销毁重建是新生命周期；独立编辑状态生命周期由业务管理 | D-09、D-24 至 D-26、D-31 |
| 布局与动态适配 | 尺寸意图分开，边界独立且最小值不可突破；框架测量并分配空间，页面选择适配方案 | D-10 至 D-16、D-23 |
| 输入与宿主 | 输入按范围路由，消费阻止外层重复处理；纯提示不参与输入；宿主提供真实输入法信息 | D-18、D-19、D-27、D-34 |
| 标准控件职责 | 公开表达主题/文案策略，框架负责有效主题初值和内部适配 | D-17、D-20 |

母本已有的平台边界继续适用：核心平台无关，GL 止于 backend/replay，布局/绘制/命中使用同一 logical px，宿主负责平台转换与触碰状态恢复。专项模块未在本轮全库重建。

后续优先补齐会改变骨架的边界，按依赖推进：

1. **状态更新主流程**：直接状态读写的可见时机、派生与呈现的协调，首次挂载及动态更新如何形成一致的布局/绘制/命中事实。D-39 已确定状态系统与呈现运行时的职责边界，D-38 确认直接状态 set 后立即 get 新值；优先明确副作用归属和对外一致性，派生求值及 Effect 时机留给下层设计。
2. **生命周期主流程**：业务、编辑状态、控件与宿主之间的持有/释放职责，动态内容变化如何更新已有控件，避免普通更新隐含销毁重建。
3. **输入范围主流程**：页面、模态层、非模态交互层如何选择当前范围，宿主消费结果与关闭请求如何闭环。
4. **业务结果边界**：乱序权威、未知结果及表单应用的责任，不把网络/业务事务藏进通用控件。

已有常用细节保留在所属专题：文本能力 D-02；按钮显示 D-21/D-22；文本键盘与只读/禁用 D-27 至 D-29、D-34；撤销历史 D-30 至 D-33；焦点导航 D-35 至 D-37。暂不继续逐个裁定时间阈值、像素取整、快捷键变体或提示放置；需要影响上述骨架时再前置，否则交给相应设计与验收阶段。

骨架收束条件：目标、责任、状态/生命周期/输入主流程及已知失败归属明确，真实面板场景能沿主流程表达；剩余可逆实现选择由设计承担，不无限追加确认题。之后按专题整理正式契约、接口与实现计划，保留用户逐项确认的关键语义审阅方式。

## 已确认裁定

### D-01：业务提交变化，框架负责调度与呈现

用户逐项确认选择 A。业务只提交状态变化或语义意图，UILib 负责调度并呈现结果；业务无需调用刷新、布局或绘制，也无需显式提交刷新批次。框架允许批处理，不要求每次调用立即重绘。

连续提交按语义处理：赋最终状态可以合并；文本编辑、通知追加等有顺序意义的操作必须依序保留，不能因合并丢失。这里确定责任与结果，不预定队列、缓存或 Signal.get 的实现。

验收：同一次业务响应连续追加通知，正常宿主刷新后全部保留；连续文本编辑按顺序作用，业务不调用 flush。文本权威、拒绝编辑和回调确认方式继续逐项裁定。C-04 的职责冲突已裁决，代码与旧指南尚待后续对齐。

### D-02：标准文本输入采用常规完整编辑能力

用户逐项确认选择 A。标准文本输入支持光标定位、方向键移动、选区、复制/剪切/粘贴、全选、撤销/重做，以及中文输入法提交；单行与多行遵循各自的换行规则。旧 R9 的“光标恒末尾、不做选区与剪贴板”等能力限制不作为新规格约束。

本项只裁定能力范围。业务文本与编辑草稿的分工见 D-03；回调接受/拒绝、外部值更新的协调规则继续逐项确认；IME 预编辑呈现、候选窗口定位、快捷键及撤销边界尚未细化。中文输入法提交是需求，不能凭已有代码声明实现通过。

验收场景：在文本中间定位并修改，选中片段替换，复制/剪切/粘贴及全选，撤销/重做，中文输入法提交；单行/多行分别检查换行行为。验证必须覆盖生产控件与对应宿主输入路径。

### D-03：编辑文本与业务最终值分开

用户逐项确认选择 A。编辑文本由 UI 编辑状态承载，允许负号、空字符串等暂时不完整的输入；业务最终值由业务校验并接受。光标、选区及编辑文本经框架状态机制管理，不由控件藏一份不可追踪的副本。编辑文本与业务值表达不同语义，各自有明确权威，不能以“唯一真值”为由把二者强行合并。

名称、搜索等场景可配置为随输入更新。提交时机见 D-04；明确拒绝的处理见 D-05；规范化显示与编辑会话见 D-06；外部更新及草稿生命周期继续逐项确认；此项不预定具体 API、缓存或内部字段。

验收：将坐标 12 改成 -5 的过程中可保留负号，清空后重新输入不会被强制还原；未接受的编辑文本不冒充合法业务值。同帧连续编辑应依序作用于编辑状态，遵循 D-01。

### D-04：业务按场景声明编辑提交策略

用户逐项确认选择 A。UILib 统一支持随输入提交、确认时提交、失焦时提交，以及表单“应用”统一提交；业务明确选择适用策略，框架按声明执行，不凭控件类型暗自决定。此处提交是请求业务接受编辑结果，不自动等同于网络请求或服务端保存。

策略只决定何时请求接受，不取消 D-03 的草稿与业务值区分，也不改变 D-01 的框架调度职责。明确拒绝的草稿/提示处理见 D-05；Enter、多行换行及 IME 确认顺序见 D-27；失焦与 IME 的协调、重复提交与表单原子性继续逐项确认；具体 API 与默认策略尚未决定。

验收：分别配置搜索随输入、字段确认、字段失焦及表单统一提交，观察业务接受请求只在声明的触发条件发生；纯编辑阶段保留草稿，业务无需调用刷新。

### D-05：明确拒绝提交时保留草稿并说明原因

用户逐项确认选择 A。业务明确拒绝编辑提交时，业务最终值保持原值；输入框保留被拒绝的编辑文本，显示拒绝原因并允许继续修改。拒绝本身不强制抢回焦点；失焦提交被拒绝也不因此强制重新聚焦。

本项只约束明确拒绝。接受后的规范化显示见 D-06；异步结果未知、编辑后错误提示的更新时机，提交过程中出现更新草稿的协调见 D-07。错误原因由业务提供，UILib 承担对应提示呈现；不预定提示组件或具体接口。

验收：提交超出业务允许范围的坐标或不允许的名称，草稿不被还原、错误原因可见、最终值不变；用户可继续修改。拒绝反馈不主动改变当前焦点。

### D-06：编辑会话与规范化结果的显示

用户选择规范化显示规则 A，并确认采用编辑会话定义。正在编辑由明确的编辑会话判断，焦点不单独决定其开始或结束。用户首次修改文本（输入、删除、剪切、粘贴或开始输入法组字）开始会话；仅聚焦、移动光标、选择或复制文本不开始会话。

随输入提交获得接受不结束会话，业务值可更新，输入框仍保留正在编辑的原文。用户明确确认，或按业务声明策略完成编辑并获接受后，会话结束并显示业务接受的规范化结果，即使焦点仍留在输入框。拒绝时保留草稿与原因，遵循 D-05。

失焦只是可能触发完成的事件，按声明策略解释：失焦提交获接受后可结束会话；表单统一应用不因切换字段就完成该字段提交。框架不能把“有焦点”等同“正在编辑”，也不能把“失焦”等同“已接受”。

本项针对接受结果对应当前草稿的情况；异步结果与更新草稿的匹配见 D-07；外部业务值变更见 D-08；草稿生命周期与控件卸载见 D-09；取消操作及子状态恢复细则继续确认。输入法组字开始会话不表示组字阶段即应提交业务，Enter 确认与提交顺序见 D-27，其他组字协调另行细化。

验收：聚焦复制不启动编辑；随输入接受的规范化结果不替换当前原文；明确确认获接受后显示规范化文本且不要求失焦；切到表单另一字段不擅自完成提交；拒绝不丢草稿。

### D-07：异步提交期间继续编辑，结果匹配对应草稿

用户逐项确认选择 A。异步提交期间允许继续编辑；每个返回结果只处理它所对应的提交与草稿。若用户已产生更新的草稿，旧结果不能覆盖新文本、改变其光标或选区、结束新的编辑会话，也不能把旧拒绝原因当成新文本的校验结论。

对应旧提交的成功或拒绝仍需如实呈现。业务最终值按实际接受结果更新，新草稿仍待提交；当前草稿与接受结果匹配时，按 D-04/D-06 的提交与完成规则处理。提交身份与草稿对应关系由框架提供可追踪的协调能力，业务负责权威结果；此项不预定请求编号、版本字段或网络协议。

外部更新策略见 D-08；多次提交乱序返回时业务最终值的权威顺序、超时或结果未知继续确认；不得简单以最后到达的回复推定最新权威值。

验收：提交名称后继续编辑，旧成功结果不替换新草稿或结束新会话；旧拒绝结果不标记新草稿为无效，且旧提交状态仍可辨识；光标与选区不因旧结果跳变。

### D-08：外部更新策略归业务，草稿与业务值操作语义明确

用户确认外部更新交由业务自行处理，并要求业务明确知道修改的是草稿还是真实值。业务最终值变化不自动覆盖正在编辑的草稿；业务决定保留、替换或取消编辑，以及是否提示冲突。没有编辑会话时，输入框正常同步业务值。UILib 不规定通用冲突提示或选择界面。

框架提供读取编辑状态、明确替换编辑文本和结束/取消编辑的能力；业务明确请求操作后，框架保持文本、光标、选区与会话状态一致。业务值写入、草稿修改、请求提交、接受/拒绝提交、结束/取消编辑必须有可区分的语义，接口与接入说明不得让业务依靠焦点、调用时机或隐藏模式猜测操作目标。具体命名和接口形状留给设计阶段。

修改草稿不表示业务接受，不自动写业务最终值；写业务值不隐含丢弃活跃草稿；请求提交不等同已接受，也不自动等同网络保存。提交策略按 D-04 执行，接受与拒绝按 D-05 至 D-07 协调；业务明确替换草稿或取消编辑属于独立操作。

验收：编辑期间外部业务值更新，草稿保持；业务明确替换草稿时显示变更并协调编辑状态，业务值不因草稿操作暗中改变；无编辑会话时跟随业务值。业务可从接口契约辨别每个操作的目标和副作用，无需理解内部字段。

### D-09：业务管理草稿生命周期，控件卸载不隐含提交或丢弃

用户逐项确认选择 A。草稿属于明确的编辑状态对象，生命周期由业务决定。控件卸载只释放该控件的焦点、输入和绑定，不隐含提交或丢弃草稿；业务可保留编辑状态供重新挂载，也可明确取消编辑或销毁编辑状态。

控件卸载、取消编辑与销毁编辑状态是可区分的操作，其契约须明确。切页、关闭页面是否保留草稿属于业务规则，框架不强制统一。业务保留的编辑状态不得继续依赖已卸载控件的输入或节点绑定；重新挂载不自动恢复旧焦点或输入所有权。撤销历史、输入法组字等子状态的恢复细则尚未决定。

验收：同一编辑状态解绑控件后重新挂载，草稿仍可使用；旧控件不再接收输入。业务明确销毁编辑状态时不再保留草稿；卸载不触发业务接受或提交请求。

### D-10：明确拆分尺寸意图，边界独立声明

用户逐项确认选择 A。尺寸表达明确区分固定尺寸、自然尺寸、填充/剩余空间分配；最小/最大边界独立声明，不代替尺寸意图。固定尺寸表达指定尺寸且不随内容自然增长；自然尺寸根据内容、字体、换行等求出所需尺寸；填充或剩余空间分配使用父容器可用空间或参与兄弟间的空间分配。

同一种声明在宽、高、普通容器和滚动视口中保持一致含义，不以一个属性随上下文变义代替明确表达。该裁定确定语义方向，不直接决定接口名称、旧 preferred 的迁移方式、默认策略或公共兼容方案。

尺寸意图与自身最小/最大边界的优先级见 D-11；父空间不足仍守最小尺寸见 D-12；溢出策略、百分比的参照盒及测量依赖继续逐项确认。固定尺寸不能突破自身边界。

验收：业务能够从声明直接辨别尺寸意图与边界；同样声明在宽高及不同容器中保持相同语义，动态内容/字体改变按相应意图重新布局。具体结果在优先级与溢出政策确认后细化。

### D-11：自身最小/最大边界优先于尺寸意图

用户逐项确认选择 A。先按声明的尺寸意图求出尺寸，再限制到自身最小/最大边界允许的范围；固定尺寸也受边界约束，不忽略边界。最小值大于最大值属于无效声明，须明确报出，不能静默猜测或挑选其中一边。

本项只确定自身尺寸声明的组合优先级，不裁定父容器空间不足、溢出或内容裁剪。错误报告的通道与发生无效声明时的运行处理方式留待设计；动态边界变化同样遵循此规则。

验收：固定尺寸超出最大边界时使用最大边界，低于最小边界时使用最小边界；自然尺寸与空间分配也遵守同一范围。合法范围中的固定尺寸保持其指定尺寸。最小值大于最大值时有明确诊断，不产生静默的优先级特例。

### D-12：父容器空间不足时仍守住最小尺寸

用户逐项确认选择 A。最小尺寸是硬边界；父容器空间不足时也不把子控件压到其最小尺寸以下。容器通过明确声明的滚动、换行、裁剪或其他适配策略处理空间不足，不能把最小尺寸暗中降为尽量满足的目标。

本项只决定最小边界不可突破，不规定所有控件保持自然尺寸或固定尺寸，也不自动选择滚动、换行或裁剪。溢出策略声明与默认行为见 D-13；固定与自然尺寸缩减规则见 D-14/D-15。局部裁剪不改变控件的布局尺寸；可见与可命中范围须沿同一裁剪事实协调。

验收：父空间小于子控件最小需求时，布局尺寸仍满足最小边界；空间不足进入容器声明的处理策略，而不是静默压小控件。窗口、字号等动态变化后仍遵循同一规则。

### D-13：普通容器默认允许溢出，裁剪与滚动明确声明

用户逐项确认选择 A。普通容器默认允许溢出，不自动裁剪，也不自动成为滚动容器；需要裁剪或滚动时由页面/组件作者明确声明。溢出不自动扩大父容器的布局尺寸，超出部分的可见性仍受上层裁剪范围限制。

换行、重排与折叠属于布局策略，裁剪与滚动属于溢出处理，框架不因空间不足擅自选择布局降级。裁剪的可见范围与可命中范围须一致。默认允许溢出不预定父盒外子节点的命中遍历和重叠优先级，相关输入规则另行明确。

本项确定通用容器默认值；滚动视口等明确承担裁剪职责的组件仍按其声明行为工作。固定尺寸规则见 D-14；自然尺寸规则见 D-15；溢出交互细则及兼容迁移继续确认。

验收：普通容器子内容超出父盒时不会被该容器自动裁剪或触发滚动，父盒尺寸不因此改变；显式裁剪及上层裁剪生效，隐藏部分不命中；显式滚动容器保有其视口与滚动行为。

### D-14：固定尺寸不参与父空间不足时的自动缩减

用户逐项确认选择 A。固定尺寸按自身最小/最大边界限制后，不因父容器空间不足而自动缩小，即使缩小后的尺寸仍高于最小边界。需要让步时应使用明确的可伸缩尺寸表达，不能将固定尺寸暗中解释为初始尺寸或软目标。空间不足按容器声明及 D-13 的默认溢出规则处理。

本项不改变 D-11：自身边界仍优先；动态改变固定尺寸声明或自身边界也仍可改变实际尺寸。自然尺寸规则见 D-15；可伸缩表达及兄弟间分配细则继续确认，暂不预定新 API。

验收：同一固定尺寸声明及自身边界保持不变时，缩小父容器不改变该控件的布局尺寸；容器的裁剪或滚动可以改变可见区域，不替代或改写布局尺寸。

### D-15：自然尺寸默认不参与自动缩减，测量与缩减分开

用户逐项确认选择 A。自然尺寸按内容与已声明的测量规则求值，再受自身最小/最大边界限制；默认不因父空间不足自动缩小布局盒。需要参与空间缩减时另行明确声明，不能让自然尺寸暗含自动压缩策略。

按已声明的换行规则重新测量，使内容所需宽高变化，仍属于自然尺寸；测量后为容纳兄弟而压小布局盒属于独立缩减策略。此项不禁止换行或响应式布局，不要求保留旧测量快照，也不取消 D-11 的边界限制。

具体测量约束、可伸缩表达及兄弟间分配继续确认。验收：父空间变化不静默将自然尺寸降为软目标；声明的换行、字体或文案变化触发重新测量；显式缩减与内容测量的效果可从声明区分，且最小边界仍为硬边界。

### D-16：框架测量自然尺寸区域并分配正文剩余空间

用户逐项确认选择 A。页面作者声明标题、页签与操作区按自然尺寸布局，正文占用剩余空间并独立滚动；UILib 负责测量这些区域，扣除间距与内边距，再分配正文视口。业务无需预先手算固定区高度。这里“固定区”指不随正文滚动，不要求数值高度固定。

文案、语言、字号、主题或窗口宽度影响区域测量时，框架自动失效并重新测量、分配；业务不依靠重新打开或访问标准控件内部节点补偿布局。空间不足仍遵循 D-11 至 D-15 的边界与布局策略，不保证任意小窗口下所有区域同时完整显示；极小窗口适配职责见 D-23，具体页面方案由页面作者决定。

本项确立测量与分配职责，不预定测量轮次或布局算法。验收：标题换行、字号/语言变化或窗口缩放后，固定区保持独立于正文滚动，正文视口随之变化；无需业务固定区公式，布局、绘制与命中一致。

### D-17：正式主题派生入口保证首次挂载的有效初值

用户逐项确认选择 A。通过 UILib 正式主题派生入口创建主题后，可立即挂载标准控件；框架保证有效初值，后续来源变化继续动态更新。业务无需手算初值或主动刷新来满足首次挂载要求。

本项只确定主题派生能力的初始化合同，不要求任意 Computed 改成同步求值，不承诺将无效业务主题自动修复为合法主题。具体入口与实现方式留给设计；初始化不得意外把派生内部依赖挂到外层重建 effect。

验收：沿正式派生主题路径首次挂载输入框，首帧无 theme value 空值异常；后续改变基础主题，控件继续更新，业务不提供补偿初值或 flush。当前仅确认需求，尚未实施或运行验证。

### D-18：ESC 按层处理，消费即停止外层关闭

用户逐项确认选择 A。ESC 先交给当前输入范围中的处理者；一旦被消费，不再触发外层关闭。仅在未被消费时交给页面关闭策略或宿主默认行为；宿主必须依据 UILib 的处理结果决定是否执行默认行为，不能在输入尚未处理时抢先关闭页面。

一次 ESC 不能同时触发内外两层关闭。页面是否需要关闭确认、是否丢弃草稿由业务处理；输入法组字、文本编辑是否消费 ESC，以及具体浮层优先级继续细化。本项不预定消费回执或调度的接口实现。

验收：内层菜单消费一次 ESC 后只关闭菜单，页面仍在；后续 ESC 才交给下一处理层。对话框消费时宿主不执行原生关屏；未消费时页面策略或宿主默认行为正常执行。当前只确认合同，未宣称当前游戏产物已修复。

### D-19：纯提示通知完全不参与输入与焦点路由

用户逐项确认选择 A。纯提示用途的被动通知不抢焦点、不改变 Tab/Shift+Tab 的焦点范围、不消费 ESC，也不拦截指针或改变键盘/文本输入的目标；其出现与消失不打断原有交互。

带“撤销”等操作按钮的通知属于可交互通知，需要明确声明输入行为，不能隐含套用纯提示通知的规则。框架须依据声明的输入参与语义选择焦点范围和路由，不能仅因浮层处于最上层或可见就将其作为键盘范围。具体接口及可交互通知规则另行设计。

验收：输入框收字和 Dialog 中 Tab/Shift+Tab 切换期间出现、消失纯提示通知，目标与焦点范围不变；ESC 仍交给原有处理层；指针穿透通知。当前仅确认需求，静态风险尚未实机复现或修复验证。

### D-20：标准控件通过公开文案策略承担适配职责

用户逐项确认选择 A。业务通过公开能力声明文案显示策略，例如换行、单行省略或允许溢出；标准按钮等控件按实际可用空间完成内部文字测量、布局与绘制。文案、语言、字号、主题或可用空间变化后自动更新，业务无需访问内部子节点或在布局完成后补设文字宽度。

本项确定职责与公开能力，不要求所有控件使用同一默认策略；标准按钮默认策略见 D-21；受限高度按钮的省略与完整文案访问见 D-22；其他控件策略另行确认。测量与适配须遵循 D-10 至 D-16 的尺寸、边界与剩余空间规则，不以内部节点结构作为公共契约。

验收：通过公开策略设置长文案，在同一已打开页面改变语言、字号或控件可用宽度，控件按声明重新适配；业务不遍历内部文字节点，绘制与交互范围保持协调。当前仅确认规格，未实施生产改动。

### D-21：标准按钮默认文案换行，自然高度随内容增长

用户逐项确认选择 A。标准按钮未指定文案策略时，按实际可用文字宽度换行；按钮采用自然高度时，随换行后的内容增高。需要紧凑单行等其他行为时，通过 D-20 的公开策略明确声明。

本项仅确定标准按钮默认值，不将所有控件的文案策略统一为换行。作者明确限制按钮高度时仍遵循尺寸声明与自身边界，不因默认换行擅自扩大固定尺寸或突破最大高度；高度不足的默认文案处理见 D-22。

验收：未指定文案策略的自然高度按钮，在文案、语言、字号或可用宽度变化后重新换行并测量高度，完整呈现内容所需高度；明确指定其他文案策略时按声明执行，业务无需操作内部文字节点。

### D-22：受限高度按钮按完整行省略并提供完整文案提示

用户逐项确认选择 A。作者限制标准按钮高度且换行文本放不下时，默认只显示可完整容纳的行并标示省略，不绘制半行文字；完整文案可通过悬停或键盘聚焦后的提示查看。作者可通过公开策略明确选择其他处理。

省略及提示不改变按钮布局尺寸，不擅自增高或缩小字号。提示属于纯展示内容，不抢焦点或改变输入路由，遵循 D-19 的被动语义。文字区域连完整行或省略标示都容不下时的呈现细则，以及提示触发时机和放置规则留给后续设计；框架须保留完整文案以供提示使用。

验收：受限高度按钮的长文案只呈现完整行且有省略标示；鼠标悬停与键盘聚焦均可查看完整文案，按钮尺寸与焦点保持；文案、字号或空间变化后重新计算省略及提示内容。

### D-23：极小窗口适配由页面作者声明，框架执行

用户逐项确认选择 A。UILib 提供可声明的滚动、换行、区域显隐和布局切换能力，页面作者选择极小窗口下的适配方案，框架负责执行。框架不因空间不足擅自缩字号、隐藏操作，或把整个页面改成滚动。

页面可选择整体滚动、精简布局或声明最低适用窗口范围；低于声明范围时提供明确说明及退出方式，避免留下无法操作的页面。具体方案与适用条件由页面决定，不规定所有页面使用同一阈值或布局。窗口、缩放、字号等变化后按声明动态更新，仍遵循已确认的尺寸硬边界。

验收：逐步缩小页面可用空间，页面执行作者声明的适配方案，框架无隐藏的降级行为；低于声明适用范围时说明与退出方式仍可使用。此项确定通用职责，不替 Architect 选择具体页面方案。

### D-24：持续存在的逻辑控件在普通更新中保持交互连续性

用户逐项确认选择 A。同一逻辑控件持续存在时，普通状态、布局与绘制更新保持其草稿、光标、选区、焦点和滚动状态；框架不因重新测量或绘制而重置这些状态。控件身份由框架按 D-25 自动维护，业务明确表达生命周期，普通更新不隐含重建或重置。

滚动范围变小时，仅将位置限制到新的有效范围，不自动回到起点。控件被移除、输入范围失活或业务明确重置时按对应生命周期合同处理；此项不要求已失效控件继续接收输入，也不改变 collapsed 的已有公开例外。跨页恢复另行声明，控件身份规则见 D-25。

验收：输入与选区操作期间改变主题、文案、窗口尺寸或不影响控件身份的业务状态，草稿、光标、选区及合法焦点保持；滚动位置保持或限制到新有效范围。移除或失活仍释放相应输入状态。旧页面整页重挂载的代码不能单独证明此需求已满足。

### D-25：UILib 自动创建 UUID 控件身份，主要用于框架内部维护

用户明确指定：控件身份由 UILib 默认创建 UUID，保证完全唯一，不要求业务提供；身份标识主要用于框架内部维护。框架不得以列表位置代替控件身份，也不得将业务标识作为通用控件创建的必要条件。

同一个存续控件在移动或排序时身份不变，按 D-24 保持交互连续性。创建新控件与移动已有控件是不同动作；自动 UUID 本身不能推断重新创建的控件是否代表同一业务对象。销毁后重新创建按 D-26 视为新生命周期，不默认为 UUID 可自动识别业务等价性。UUID 的具体生成与唯一性保障方式留给设计。

验收：业务无需提供标识即可创建控件，框架自动维护唯一身份；已有控件排序或移动不会转移身份及交互状态到其他控件。重复身份不得被框架静默接受。

### D-26：销毁后重建属于新的控件生命周期

用户逐项确认选择 A。明确销毁后重新创建视为新的控件生命周期，新控件获得新 UUID，不自动继承旧焦点、选区或滚动状态。框架不依据结构、内容或位置推断并迁移旧控件身份。业务可按 D-09 复用独立编辑状态保留草稿；具体子状态恢复须有明确契约，不以重建暗中恢复旧输入所有权。

普通动态更新应更新已有控件，框架不以整页重建代替更新；持续存在控件的连续性遵循 D-24。明确重建、普通更新与已有控件移动在生命周期语义上可区分，UUID 规则遵循 D-25。

验收：销毁并新建得到新身份且不自动承接旧焦点/选区/滚动；复用独立编辑状态时草稿仍可使用。已有控件的普通状态更新或排序不隐含销毁重建，不因新旧结构相似发生错误状态迁移。

### D-27：Enter 先处理输入法确认，随后按字段语义处理

用户逐项确认选择 A。输入法正在组字时，Enter 用于输入法确认，不同时触发字段或表单提交；组字结束后的后续 Enter 才按文本框及业务声明策略处理。同一次按键不得既确认输入法又提交业务。

单行框可以将 Enter 作为确认动作，提交仍按 D-04 的业务声明执行；多行框默认 Enter 换行，需要提交时明确声明其他快捷键或使用提交按钮。框架不得将默认换行暗中变为业务提交。

宿主须提供真实组字状态与事件信息，不靠普通字符事件猜测。具体宿主能力及实现留待设计；现有生产模型或字符输入测试不能单独证明 IME 合同已满足。

验收：真实输入法组字期间 Enter 只确认文字，没有字段/表单提交；组字结束后的 Enter 按单行声明或多行默认换行执行，未重复处理同一按键。非组字场景也遵循同一字段策略。

### D-28：文本框默认以 Tab/Shift+Tab 切换焦点

用户逐项确认选择 A。单行和多行文本框默认 Tab 向前切换焦点、Shift+Tab 向后切换，遵循当前焦点范围；需要输入制表符的编辑器明确开启对应模式，不以多行类型暗含制表符插入。输入法正在处理该按键时先尊重输入法消费结果，同一事件不再触发焦点切换。

本项确定文本框默认键盘行为；禁用/只读参与规则见 D-29；焦点顺序与制表符模式下离开控件的键盘方式继续明确。焦点切换是否触发提交仍由 D-04 的声明策略决定，不因 Tab 暗中接受草稿。

验收：普通单行与多行表单中 Tab/Shift+Tab 按当前范围切换，未插入制表符；明确开启的编辑器模式遵循对应声明；纯提示通知不改变焦点范围，输入法消费不导致重复动作。

### D-29：只读保留查看交互，禁用退出操作流程

用户逐项确认选择 A。只读文本框可聚焦、通过 Tab 到达、选择和复制文本及滚动查看，但不能修改文本或发起编辑提交。禁用控件不接受聚焦、编辑或激活，Tab 跳过；变为禁用时释放已有焦点及正在进行的交互，不隐含提交或丢弃草稿。

禁用原因仍可通过不激活控件的提示方式查看。文本框变为只读时，已有未提交草稿由业务明确决定如何处理，框架不擅自还原；变为只读不触发编辑提交，权限切换期间取消不再允许的修改操作。状态切换的释放动作不作为业务失焦提交的隐含触发。

验收：只读文本可经键盘到达并选择复制，不能输入、删除、剪切、粘贴或通过撤销/重做修改，也不发起编辑提交；禁用后 Tab 跳过且旧交互停止，状态变化不触发提交或清空草稿；禁用原因可以在不激活控件的情况下查看。

### D-30：文本撤销/重做只作用于编辑草稿

用户逐项确认选择 A。文本撤销/重做只改变编辑状态，不直接撤销已接受的业务操作，不直接恢复业务最终值；修改后的草稿是否提交仍按 D-04 的业务声明策略执行。业务层撤销需要独立能力与明确操作。

撤销可以产生与当前业务值不同的草稿；随输入提交的字段按同样策略请求业务接受该草稿，业务仍可拒绝。只读与禁用状态按 D-29 禁止通过撤销/重做修改文本。此项不预定撤销分组、外部替换时历史处理或提交完成后的历史保留规则。

验收：业务已接受名称修改后执行文本撤销，只改变草稿，不自动发起业务撤销或直接回退权威值；按声明策略触发的后续提交可辨别为新的接受请求。重做遵循相同范围。

### D-31：草稿编辑与重置编辑基线具有不同历史语义

用户确认选择 A。编辑状态包含当前草稿、光标、选区及撤销/重做历史，草稿是当前编辑文本。普通草稿编辑（如插入模板）可进入撤销历史；重置编辑基线替换文本并清空撤销/重做历史，不能撤销回旧基线。业务明确选择操作，框架不依据内容或焦点猜测。

切换业务对象时，业务若重置同一编辑状态则丢弃旧历史；也可切换到另一个独立编辑状态并保留原对象的草稿与历史，符合 D-09 的生命周期职责。切换对象不自动等同销毁编辑状态。继续编辑、重置基线与切换编辑状态在接口语义上可区分。

本项不预定具体对象字段、接口名称或历史存储方式；提交接受后的规范化与历史规则见 D-32。验收：插入模板可以撤销；重置基线后不能撤销回旧对象文本；业务保留独立编辑状态时，切回该状态仍可使用其草稿与历史。

### D-32：提交成功保留编辑历史，规范化与确认协调为完成步骤

用户逐项确认选择 A。提交成功不自动清空文本撤销/重做历史。显示对应当前草稿的规范化结果后，撤销可以恢复此前的编辑文本并重新开始编辑会话；不直接撤销业务操作或回退业务最终值，后续提交仍遵循 D-04/D-30。

规范化与本次确认协调为一个完成步骤，不使撤销反复陷入格式修正。框架不得将成功提交隐含解释为 D-31 的重置基线；业务明确重置时仍按其独立语义清空历史。旧异步结果与更新草稿的协调继续遵循 D-07。

本项不预定具体历史栈结构及编辑分组算法。验收：确认并获接受后仍可撤销恢复此前文本；恢复文本开启编辑会话，权威业务值不被直接回退；规范化没有形成需要反复撤销的独立格式修正循环。

### D-33：撤销按连续编辑动作分组，参考 VS Code 编辑体验

用户确认选择 A，并指定可参考 VS Code 实现。同一位置连续输入合为一组，连续同方向删除合为一组；输入与删除切换、移动光标、改变选区或切换焦点时结束当前组。一次粘贴、剪切、输入法提交或模板插入各自作为完整一步。明确确认结束当前组，但不清空历史。

VS Code 的编辑体验与相关实现可作为后续设计参考，不将尚未核查的具体行为宣称为 VS Code 已有合同，也不要求照搬其内部结构。实现应落在 UILib 自有编辑状态与响应式能力中。输入停顿是否辅助分组及具体时间阈值留待设计；文本撤销作用范围、重置基线及提交成功后的历史规则分别遵循 D-30 至 D-32。

验收：连续输入或同方向删除可整组撤销；移动光标或改变操作类型后形成独立组；粘贴、剪切、一次输入法提交和模板插入均可整步撤销。确认不会将前后编辑混为一组，也不清空已有历史。

### D-34：文本框默认不以 ESC 取消整个编辑草稿

用户逐项确认选择 A。文本框默认不以 ESC 丢弃草稿或取消整个编辑会话。输入法正在组字时先处理组字取消；文本框自身菜单等临时交互可消费 ESC。没有这些临时交互时，ESC 继续交给外层关闭策略，消费与 fallback 遵循 D-18。

业务需要“ESC 取消编辑”时须明确声明；页面关闭是否丢弃草稿仍由业务决定，遵循 D-09。具体临时交互间的优先级及输入法宿主协调留待设计，不靠普通字符事件推测组字状态。

验收：普通编辑状态按 ESC 不由文本框自动恢复业务值或丢弃草稿；组字取消或菜单关闭消费该按键时不同时关闭页面；无内部消费时外层按声明处理。

### D-35：默认焦点顺序采用逻辑树声明顺序，暂不增加独立排序属性

用户确认精简后的 A。当前焦点范围内默认按逻辑树声明顺序访问可聚焦控件；跳过隐藏、失活及禁用控件，只读输入框保留。布局移动、换行或窗口缩放本身不改变导航顺序；动态列表明确改变逻辑顺序时按更新后的声明顺序导航。

暂不引入单独的焦点排序属性，有真实需求再增加；页面作者通过组织逻辑树表达顺序，UUID 仅维护控件身份，不参与排序。声明顺序与具体内部节点存储结构分开，不将内部子节点下标规定为公共契约。

验收：Tab/Shift+Tab 按当前范围的声明顺序前进/后退，正确跳过不可参与控件并保留只读输入框；普通布局变化不重排键盘顺序。范围末尾的循环行为见 D-36；焦点移到视口外时的滚动见 D-37。

### D-36：Tab/Shift+Tab 在当前有效焦点范围内循环

用户逐项确认选择 A。Tab 从当前范围的最后一个可聚焦控件回到第一个，Shift+Tab 从第一个回到最后一个，不穿出当前有效焦点范围。只有一个可聚焦控件时保持其焦点；没有可聚焦控件时不建立焦点。顺序与参与规则遵循 D-29/D-35，纯提示通知按 D-19 不形成焦点范围。

本项确定范围边界行为，不预定范围创建与嵌套接口，焦点移到视口外控件时的滚动规则见 D-37。范围失活或控件移除时仍遵循相应生命周期合同，不以循环保留失效输入所有权。

验收：包含首尾可聚焦控件的有效范围内，正向与反向导航均循环且不跳入外层范围；单项范围保持焦点，空范围不建立焦点。范围内禁用/隐藏项被跳过，被动通知出现不改变范围或循环顺序。

### D-37：键盘导航以最小必要滚动使焦点目标可见

用户逐项确认选择 A。键盘导航到滚动视口外的控件时，框架以最小必要滚动使目标可见；已完整可见时不滚动。嵌套滚动区域逐层协调；目标大于视口时优先显示其焦点或编辑位置，不强求整体可见。

用户主动导航是 D-24 保持滚动状态的明确例外；普通布局更新仍不随意跳转。具体滚动算法留给设计。验收：Tab 到视口外字段时能看到操作目标，已可见目标不引起多余滚动；过大目标和嵌套视口能展示焦点或编辑位置。

### D-38：直接状态写入后立即可读，呈现仍由框架调度

用户逐项确认选择 A。在合法的状态访问上下文中，业务写入直接状态后，在同一次处理流程中读取该状态得到新值，不继续返回旧的已提交值。连续读写可基于前一步已写入的状态进行，不要求业务主动 flush 或刷新来使直接状态可读。

状态读取可见性与呈现调度分开：布局、绘制及最终状态呈现仍可按 D-01 批处理，直接状态写入不要求每次立即重绘；文本编辑与通知追加等顺序操作仍不得丢失。本项不授予任意线程直接操作 UI 状态的权限，也不预定队列或内部存储。派生状态读取与 Effect 执行时机另行确定。

验收：同一次业务处理先修改状态，再读取并作后续修改，读取反映前一步写入，后续操作不会基于旧值覆盖前一步；业务不调用 flush。呈现保持框架统一调度。现有 Signal 已提交值读取合同需在实现及兼容设计阶段对齐，不将当前实现视为已满足。

### D-39：状态与派生系统独立于 UI 呈现运行时成立

用户逐项确认选择 A。状态系统负责状态读写、派生关系及其一致性，不依赖控件挂载或 UI 帧推进即可使用；呈现运行时订阅状态变化，负责调度控件更新、布局、绘制与输入协调。业务读取状态无需知道 UI 是否刷新，状态读取合同不能依赖宿主推进呈现才能成立。

状态对象的持有者决定其生命周期，控件卸载解除绑定，不天然销毁独立状态，遵循 D-09。D-38 的直接状态写后立即可读保留。此项不直接决定所有派生同步计算、Computed.get 的具体行为、缓存失效算法或 Effect 的执行时机；这些属于下层设计，需先明确状态系统对外的一致性合同及副作用归属。

验收：不挂载控件、不推进 UI 帧时，状态读写与派生能力仍可按其独立合同使用；挂载仅建立呈现绑定，卸载不强制销毁独立状态。状态系统与呈现运行时之间不存在业务必须主动 flush 才能读取状态的隐含依赖。

## 5. 当前真实场景与责任边界

- **选区面板首次打开**：有主题派生值为空的原始异常堆栈。重点是标准控件与主题初始化协作，不把业务手写初值认定为上游永远正确的 API。
- **固定区 + 正文滚动**：业务用自算 fixedChromeHeight、访问按钮内部孩子等方式适配。它们是通用能力接入成本的证据；需求是内容可达和文案可读，不是要求上游复制这些公式。
- **实例编辑/权限变化**：业务决定占用、只读、pending、错误原因；控件保证显示与交互及时更新。关闭面板丢弃未提交编辑与释放占用是业务合同。
- **面板外右键临时控制视角**：下游已明确要求；宿主负责 UI/游戏输入切换与释放，业务禁止借此触发工具。是否需要通用宿主能力另裁决，不能由普通按钮 handler 偷接原版实现。
- **后台创建完成**：已有关闭后 matchedCreate=false 日志，可作为旧页面不重开的正面观测；它不能证明所有焦点/滚动/编辑状态保持。
