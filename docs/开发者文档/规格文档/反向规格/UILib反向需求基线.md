# UILib 反向需求基线

状态：**反向整理草案，供需求审阅**。它提取已有要求、记录实现事实并提出缺口；不覆盖现行规范，不将待裁决建议变成公共兼容承诺。本轮只建立规格与查冲突，不改生产代码、不删测试。

## 1. 目标与依据

用户目标：以真实需求驱动代码，优先消除需求之间未取舍的矛盾；随后让测试只保护真实行为，不让测试里的历史实现反过来定义产品。

UILib 为 UI 作者提供可动态更新、可布局、可交互、可渲染的通用内容；宿主负责输入、投放与生命周期；业务负责意图的业务含义、权限和异步结果。Architect 的重构面板是当前真实消费者，不能把其业务规则搬进通用 UI 核心。

证据基线：UILib 分支 4.0，HEAD `c0b81132d1b0e0de2beb13a6c83f8d7ec6b0a1bb`；Architect 主仓 main，HEAD `2801924d220eb4dac12a1142d04b4dd1326a841c`；重构 worktree codex/rebuild-scratch，HEAD `376057c8e6e0e56ad72cf3d6aa164b7ff7ff9c18`。以上哈希仅作定位，文档链接指向工作目录。

UILib 原有规格索引及 uicore 施工规划存在协作者未提交改动，未修改它们。Architect 消费的开发 jar 标识为 `4.11.0-4-0.40+883888b20e-dirty`，与 UILib 当前 HEAD 不同。不能把本轮源码审查结果直接宣称为该 jar 的行为。

## 3. 需求的表达方式

每条需求先给场景与可观察结果，再给责任和证据；“复用哪一个内部字段”“子节点必须位于第几个下标”不充当需求。未指定的极小窗口降级、滚动位置恢复、取整策略等保持为待裁决项，不擅自删能力或猜设计。

## 已确认裁定

### D-01：业务提交变化，框架负责调度与呈现

用户逐项确认选择 A。业务只提交状态变化或语义意图，UILib 负责调度并呈现结果；业务无需调用刷新、布局或绘制，也无需显式提交刷新批次。框架允许批处理，不要求每次调用立即重绘。

连续提交按语义处理：赋最终状态可以合并；文本编辑、通知追加等有顺序意义的操作必须依序保留，不能因合并丢失。这里确定责任与结果，不预定队列、缓存或 Signal.get 的实现。

验收：同一次业务响应连续追加通知，正常宿主刷新后全部保留；连续文本编辑按顺序作用，业务不调用 flush。文本权威、拒绝编辑和回调确认方式继续逐项裁定。C-04 的职责冲突已裁决，代码与旧指南尚待后续对齐。

### D-02：标准文本输入采用常规完整编辑能力

用户逐项确认选择 A。标准文本输入支持光标定位、方向键移动、选区、复制/剪切/粘贴、全选、撤销/重做，以及中文输入法提交；单行与多行遵循各自的换行规则。旧 R9 的“光标恒末尾、不做选区与剪贴板”等能力限制不作为新规格约束。

本项只裁定能力范围。业务文本与编辑草稿的分工见 D-03；回调接受/拒绝、外部值更新的协调规则继续逐项确认；IME 预编辑呈现、候选窗口定位、快捷键及撤销边界尚未细化。中文输入法提交是需求，不能凭已有代码声明实现通过。

验收场景：在文本中间定位并修改，选中片段替换，复制/剪切/粘贴及全选，撤销/重做，中文输入法提交；单行/多行分别检查换行行为。验证必须覆盖生产控件与对应宿主输入路径。

### D-03：编辑文本与业务最终值分开

用户逐项确认选择 A。编辑文本由 UI 编辑状态承载，允许负号、空字符串等暂时不完整的输入；业务最终值由业务校验并接受。光标、选区及编辑文本经框架状态机制管理，不由控件藏一份不可追踪的副本。编辑文本与业务值表达不同语义，各自有明确权威，不能以“唯一真值”为由把二者强行合并。

名称、搜索等场景可配置为随输入更新。提交时机见 D-04；明确拒绝的处理见 D-05；规范化显示与编辑会话见 D-06；外部更新及草稿生命周期继续逐项确认；此项不预定具体 API、缓存或内部字段。

验收：将坐标 12 改成 -5 的过程中可保留负号，清空后重新输入不会被强制还原；未接受的编辑文本不冒充合法业务值。同帧连续编辑应依序作用于编辑状态，遵循 D-01。

### D-04：业务按场景声明编辑提交策略

用户逐项确认选择 A。UILib 统一支持随输入提交、确认时提交、失焦时提交，以及表单“应用”统一提交；业务明确选择适用策略，框架按声明执行，不凭控件类型暗自决定。此处提交是请求业务接受编辑结果，不自动等同于网络请求或服务端保存。

策略只决定何时请求接受，不取消 D-03 的草稿与业务值区分，也不改变 D-01 的框架调度职责。明确拒绝的草稿/提示处理见 D-05；Enter 与多行换行、IME 确认及失焦的协调、重复提交与表单原子性继续逐项确认；具体 API 与默认策略尚未决定。

验收：分别配置搜索随输入、字段确认、字段失焦及表单统一提交，观察业务接受请求只在声明的触发条件发生；纯编辑阶段保留草稿，业务无需调用刷新。

### D-05：明确拒绝提交时保留草稿并说明原因

用户逐项确认选择 A。业务明确拒绝编辑提交时，业务最终值保持原值；输入框保留被拒绝的编辑文本，显示拒绝原因并允许继续修改。拒绝本身不强制抢回焦点；失焦提交被拒绝也不因此强制重新聚焦。

本项只约束明确拒绝。接受后的规范化显示见 D-06；异步结果未知、编辑后错误提示的更新时机，提交过程中出现更新草稿的协调见 D-07。错误原因由业务提供，UILib 承担对应提示呈现；不预定提示组件或具体接口。

验收：提交超出业务允许范围的坐标或不允许的名称，草稿不被还原、错误原因可见、最终值不变；用户可继续修改。拒绝反馈不主动改变当前焦点。

### D-06：编辑会话与规范化结果的显示

用户选择规范化显示规则 A，并确认采用编辑会话定义。正在编辑由明确的编辑会话判断，焦点不单独决定其开始或结束。用户首次修改文本（输入、删除、剪切、粘贴或开始输入法组字）开始会话；仅聚焦、移动光标、选择或复制文本不开始会话。

随输入提交获得接受不结束会话，业务值可更新，输入框仍保留正在编辑的原文。用户明确确认，或按业务声明策略完成编辑并获接受后，会话结束并显示业务接受的规范化结果，即使焦点仍留在输入框。拒绝时保留草稿与原因，遵循 D-05。

失焦只是可能触发完成的事件，按声明策略解释：失焦提交获接受后可结束会话；表单统一应用不因切换字段就完成该字段提交。框架不能把“有焦点”等同“正在编辑”，也不能把“失焦”等同“已接受”。

本项针对接受结果对应当前草稿的情况；异步结果与更新草稿的匹配见 D-07；外部业务值变更见 D-08；草稿生命周期与控件卸载见 D-09；取消操作及子状态恢复细则继续确认。输入法组字开始会话不表示组字阶段即应提交业务，组字与提交协调另行细化。

验收：聚焦复制不启动编辑；随输入接受的规范化结果不替换当前原文；明确确认获接受后显示规范化文本且不要求失焦；切到表单另一字段不擅自完成提交；拒绝不丢草稿。

### D-07：异步提交期间继续编辑，结果匹配对应草稿

用户逐项确认选择 A。异步提交期间允许继续编辑；每个返回结果只处理它所对应的提交与草稿。若用户已产生更新的草稿，旧结果不能覆盖新文本、改变其光标或选区、结束新的编辑会话，也不能把旧拒绝原因当成新文本的校验结论。

对应旧提交的成功或拒绝仍需如实呈现。业务最终值按实际接受结果更新，新草稿仍待提交；当前草稿与接受结果匹配时，按 D-04/D-06 的提交与完成规则处理。提交身份与草稿对应关系由框架提供可追踪的协调能力，业务负责权威结果；此项不预定请求编号、版本字段或网络协议。

外部更新策略见 D-08；多次提交乱序返回时业务最终值的权威顺序、超时或结果未知继续确认；不得简单以最后到达的回复推定最新权威值。

验收：提交名称后继续编辑，旧成功结果不替换新草稿或结束新会话；旧拒绝结果不标记新草稿为无效，且旧提交状态仍可辨识；光标与选区不因旧结果跳变。

### D-08：外部更新策略归业务，草稿与业务值操作语义明确

用户确认外部更新交由业务自行处理，并要求业务明确知道修改的是草稿还是真实值。业务最终值变化不自动覆盖正在编辑的草稿；业务决定保留、替换或取消编辑，以及是否提示冲突。没有编辑会话时，输入框正常同步业务值。UILib 不规定通用冲突提示或选择界面。

框架提供读取编辑状态、明确替换编辑文本和结束/取消编辑的能力；业务明确请求操作后，框架保持文本、光标、选区与会话状态一致。业务值写入、草稿修改、请求提交、接受/拒绝提交、结束/取消编辑必须有可区分的语义，接口与接入说明不得让业务依靠焦点、调用时机或隐藏模式猜测操作目标。具体命名和接口形状留给设计阶段。

修改草稿不表示业务接受，不自动写业务最终值；写业务值不隐含丢弃活跃草稿；请求提交不等同已接受，也不自动等同网络保存。提交策略按 D-04 执行，接受与拒绝按 D-05 至 D-07 协调；业务明确替换草稿或取消编辑属于独立操作。

验收：编辑期间外部业务值更新，草稿保持；业务明确替换草稿时显示变更并协调编辑状态，业务值不因草稿操作暗中改变；无编辑会话时跟随业务值。业务可从接口契约辨别每个操作的目标和副作用，无需理解内部字段。

### D-09：业务管理草稿生命周期，控件卸载不隐含提交或丢弃

用户逐项确认选择 A。草稿属于明确的编辑状态对象，生命周期由业务决定。控件卸载只释放该控件的焦点、输入和绑定，不隐含提交或丢弃草稿；业务可保留编辑状态供重新挂载，也可明确取消编辑或销毁编辑状态。

控件卸载、取消编辑与销毁编辑状态是可区分的操作，其契约须明确。切页、关闭页面是否保留草稿属于业务规则，框架不强制统一。业务保留的编辑状态不得继续依赖已卸载控件的输入或节点绑定；重新挂载不自动恢复旧焦点或输入所有权。撤销历史、输入法组字等子状态的恢复细则尚未决定。

验收：同一编辑状态解绑控件后重新挂载，草稿仍可使用；旧控件不再接收输入。业务明确销毁编辑状态时不再保留草稿；卸载不触发业务接受或提交请求。

### D-10：明确拆分尺寸意图，边界独立声明

用户逐项确认选择 A。尺寸表达明确区分固定尺寸、自然尺寸、填充/剩余空间分配；最小/最大边界独立声明，不代替尺寸意图。固定尺寸表达指定尺寸且不随内容自然增长；自然尺寸根据内容、字体、换行等求出所需尺寸；填充或剩余空间分配使用父容器可用空间或参与兄弟间的空间分配。

同一种声明在宽、高、普通容器和滚动视口中保持一致含义，不以一个属性随上下文变义代替明确表达。该裁定确定语义方向，不直接决定接口名称、旧 preferred 的迁移方式、默认策略或公共兼容方案。

尺寸意图与自身最小/最大边界的优先级见 D-11；父空间不足仍守最小尺寸见 D-12；溢出策略、百分比的参照盒及测量依赖继续逐项确认。固定尺寸不能突破自身边界。

验收：业务能够从声明直接辨别尺寸意图与边界；同样声明在宽高及不同容器中保持相同语义，动态内容/字体改变按相应意图重新布局。具体结果在优先级与溢出政策确认后细化。

### D-11：自身最小/最大边界优先于尺寸意图

用户逐项确认选择 A。先按声明的尺寸意图求出尺寸，再限制到自身最小/最大边界允许的范围；固定尺寸也受边界约束，不忽略边界。最小值大于最大值属于无效声明，须明确报出，不能静默猜测或挑选其中一边。

本项只确定自身尺寸声明的组合优先级，不裁定父容器空间不足、溢出或内容裁剪。错误报告的通道与发生无效声明时的运行处理方式留待设计；动态边界变化同样遵循此规则。

验收：固定尺寸超出最大边界时使用最大边界，低于最小边界时使用最小边界；自然尺寸与空间分配也遵守同一范围。合法范围中的固定尺寸保持其指定尺寸。最小值大于最大值时有明确诊断，不产生静默的优先级特例。

### D-12：父容器空间不足时仍守住最小尺寸

用户逐项确认选择 A。最小尺寸是硬边界；父容器空间不足时也不把子控件压到其最小尺寸以下。容器通过明确声明的滚动、换行、裁剪或其他适配策略处理空间不足，不能把最小尺寸暗中降为尽量满足的目标。

本项只决定最小边界不可突破，不规定所有控件保持自然尺寸或固定尺寸，也不自动选择滚动、换行或裁剪。溢出策略声明与默认行为见 D-13；固定与自然尺寸缩减规则见 D-14/D-15。局部裁剪不改变控件的布局尺寸；可见与可命中范围须沿同一裁剪事实协调。

验收：父空间小于子控件最小需求时，布局尺寸仍满足最小边界；空间不足进入容器声明的处理策略，而不是静默压小控件。窗口、字号等动态变化后仍遵循同一规则。

### D-13：普通容器默认允许溢出，裁剪与滚动明确声明

用户逐项确认选择 A。普通容器默认允许溢出，不自动裁剪，也不自动成为滚动容器；需要裁剪或滚动时由页面/组件作者明确声明。溢出不自动扩大父容器的布局尺寸，超出部分的可见性仍受上层裁剪范围限制。

换行、重排与折叠属于布局策略，裁剪与滚动属于溢出处理，框架不因空间不足擅自选择布局降级。裁剪的可见范围与可命中范围须一致。默认允许溢出不预定父盒外子节点的命中遍历和重叠优先级，相关输入规则另行明确。

本项确定通用容器默认值；滚动视口等明确承担裁剪职责的组件仍按其声明行为工作。固定尺寸规则见 D-14；自然尺寸规则见 D-15；溢出交互细则及兼容迁移继续确认。

验收：普通容器子内容超出父盒时不会被该容器自动裁剪或触发滚动，父盒尺寸不因此改变；显式裁剪及上层裁剪生效，隐藏部分不命中；显式滚动容器保有其视口与滚动行为。

### D-14：固定尺寸不参与父空间不足时的自动缩减

用户逐项确认选择 A。固定尺寸按自身最小/最大边界限制后，不因父容器空间不足而自动缩小，即使缩小后的尺寸仍高于最小边界。需要让步时应使用明确的可伸缩尺寸表达，不能将固定尺寸暗中解释为初始尺寸或软目标。空间不足按容器声明及 D-13 的默认溢出规则处理。

本项不改变 D-11：自身边界仍优先；动态改变固定尺寸声明或自身边界也仍可改变实际尺寸。自然尺寸规则见 D-15；可伸缩表达及兄弟间分配细则继续确认，暂不预定新 API。

验收：同一固定尺寸声明及自身边界保持不变时，缩小父容器不改变该控件的布局尺寸；容器的裁剪或滚动可以改变可见区域，不替代或改写布局尺寸。

### D-15：自然尺寸默认不参与自动缩减，测量与缩减分开

用户逐项确认选择 A。自然尺寸按内容与已声明的测量规则求值，再受自身最小/最大边界限制；默认不因父空间不足自动缩小布局盒。需要参与空间缩减时另行明确声明，不能让自然尺寸暗含自动压缩策略。

按已声明的换行规则重新测量，使内容所需宽高变化，仍属于自然尺寸；测量后为容纳兄弟而压小布局盒属于独立缩减策略。此项不禁止换行或响应式布局，不要求保留旧测量快照，也不取消 D-11 的边界限制。

具体测量约束、可伸缩表达及兄弟间分配继续确认。验收：父空间变化不静默将自然尺寸降为软目标；声明的换行、字体或文案变化触发重新测量；显式缩减与内容测量的效果可从声明区分，且最小边界仍为硬边界。

### D-16：框架测量自然尺寸区域并分配正文剩余空间

用户逐项确认选择 A。页面作者声明标题、页签与操作区按自然尺寸布局，正文占用剩余空间并独立滚动；UILib 负责测量这些区域，扣除间距与内边距，再分配正文视口。业务无需预先手算固定区高度。这里“固定区”指不随正文滚动，不要求数值高度固定。

文案、语言、字号、主题或窗口宽度影响区域测量时，框架自动失效并重新测量、分配；业务不依靠重新打开或访问标准控件内部节点补偿布局。空间不足仍遵循 D-11 至 D-15 的边界与布局策略，不保证任意小窗口下所有区域同时完整显示；极小窗口的页面降级继续确认。

本项确立测量与分配职责，不预定测量轮次或布局算法。验收：标题换行、字号/语言变化或窗口缩放后，固定区保持独立于正文滚动，正文视口随之变化；无需业务固定区公式，布局、绘制与命中一致。

## 5. 当前真实场景与责任边界

- **选区面板首次打开**：有主题派生值为空的原始异常堆栈。重点是标准控件与主题初始化协作，不把业务手写初值认定为上游永远正确的 API。
- **固定区 + 正文滚动**：业务用自算 fixedChromeHeight、访问按钮内部孩子等方式适配。它们是通用能力接入成本的证据；需求是内容可达和文案可读，不是要求上游复制这些公式。
- **实例编辑/权限变化**：业务决定占用、只读、pending、错误原因；控件保证显示与交互及时更新。关闭面板丢弃未提交编辑与释放占用是业务合同。
- **面板外右键临时控制视角**：下游已明确要求；宿主负责 UI/游戏输入切换与释放，业务禁止借此触发工具。是否需要通用宿主能力另裁决，不能由普通按钮 handler 偷接原版实现。
- **后台创建完成**：已有关闭后 matchedCreate=false 日志，可作为旧页面不重开的正面观测；它不能证明所有焦点/滚动/编辑状态保持。
