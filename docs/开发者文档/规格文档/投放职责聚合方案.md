# 投放职责聚合方案（scene 投放层去重）

> 状态：**现行实施方案**（2026-09-01 立项，基线 HEAD `4f639a62`）。
> 目的：**抽象简化**。手段是"职责归一"（同一职责的多个实现点聚合成一处），**不是**"形态统一"（不把 HUD/主 UI/overlay 并成一个新抽象）。
> 决策来源：工作站 `裁定-HUD投影化方向-v2.md`（含跨仓与 Miner 视角、v1 勘误全文）。本文是单仓可独立执行版。

## 0. 立项前提勘误（防再次拿过期战报立项）

上一轮审查（`docs/开发者文档/架构审查/2026-08-深度架构审查.md` A1 条目）称 `SceneHudHost` 构造"与 `AbstractSceneHostWidget` 逐行相同"。**该结论对应 4.9 重构前状态，对 HEAD 已失效**。

HEAD 实测（有意义行＝长度>12 且非注释/import 的交集）：两文件**仅 3 行相同**：

- `long frameTimeNanos = System.nanoTime();`
- `private final SceneFramePipeline pipeline;`
- `runtime.__tickFrame(frameTimeNanos);`

构造样板（runtime/layoutEngine/paintEngine/replayer/pipeline）语义重合约 15 行，但 measurer 来源、cursor/clipboard 绑定分支均不同。

**规矩**：凡以"消灭 N 行重复"为由的重构，立项数必须来自当日 `git`/脚本实测，不得引用历史审查报告的行号与结论。

## 1. 为什么不做投影化（结论，非议题）

四路对抗论证 + 独立实测的裁决：**投影化在"概念数"上的真实收益是 4→3，与"删掉投影抽象本身"打平，成本差一个数量级。**

三条硬依据（均已实测）：

1. 投影抽象唯一实体 `ui/scene/input/SceneProjectionComposition.java`（556 行）+ 其测试（623 行）**生产消费者为 0**，自述 fake，且无 render/flush/layout 任何渲染半边。
2. 它还与 `SceneFramePipeline` 存在**双重唯一 drain 者冲突**：`SceneProjectionComposition:88` 自称唯一 `drainFrame()` 调用者，而 `SceneFramePipeline:240`（`INPUT_DRAIN` 相位）drain 同一个 `PlatformInputSource`；`drainFrame` 是一次性消费语义，两者并存即互相偷事件。解它需改动主 UI 帧协议。
3. 投影半边落点是全仓最高热区：`SceneInputRouter` 1156 行、90 天内 35 次提交、`overlay` 引用 127 处。同构前车之鉴 `UiHudDocumentHost`（当年"统一 HUD 宿主"宏愿产物）：2026-05-11 `78c5a659` 加入 → 2 个月 39 次提交膨胀至 1280 行、公开 9 个带"仅供框架内部"javadoc 警告的 public 钩子 → 2026-07-08 `6e0c9c78` 一次删除 51 文件/−13409 行。

**投影化触发条件（保留方向，挂账不否决）**：出现**第二个真实的多输入投放面场景**（H4 落地：HUD 窗口内 `SceneButton` 可点击且需与 `GuiScreen` 抢焦点）时，投影合同才有验证载体。届时从本方案第 4 项（装配归一）的基线上孵化重写版，比现在升格 fake 便宜得多。**需求不来，抽象不升。**

## 2. 聚合清单（7 项，按收益排序）

判据：**沿职责边界的拆是简化，跨越职责边界的并是复杂化。** HUD 与主 UI 是跨职责边界（有/无输入），故并不动；下表各项是横跨两者的同一职责，故该并。

### A1 放置坐标计算：3 实现点 → 1

| 现有点 | 内容 |
|---|---|
| `client/hud/SceneHudHost.placeAndFrame`（140-160） | 排序 + 同锚 offset 累积，数学已委托 `SceneAnchorResolver.resolveViewport` |
| `internal/chat3/view/ChatSceneController:354-355` | **手算** `rootAbsY = hostViewportHeight - margin - rootBox.getHeight()`，把 BOTTOM_LEFT 公式在消费者侧重写一遍 |
| `ui/scene/overlay` entry anchor（`getAnchorX/Y`） | overlay 自用，保留 |

**聚合到**：`SceneAnchorResolver`（唯一锚定数学）+ `RetainedWindow` 挂载后**回写放置盒**、对外暴露只读探针；chat3 改读回写值。
**净效果**：放置实现 3→2；顺手消除 `internal→client` 跨层逆依赖（`ChatSceneController:478,499` 读 `SceneHudHost.__diagChat3Box`）。

### A2 signal 物化触发（flush）：收口到管线相位

`runtime.flush()` 生产直调 6 处，分类如下：

| 位置 | 性质 | 处置 |
|---|---|---|
| `SceneFramePipeline:613-616` `pipelineFlush` | ✅ 唯一合法收口 | 保留，扩为 HUD 帧预算断言 |
| `SceneFramePipeline:505-513` `doFrameForTest` | 测试专用入口 | 保留并注释化 |
| `client/hud/SceneHudHost:240`（`RetainedWindow` 构造首刷） | 装配副产物 | 随 A4 收进统一装配 |
| `internal/chat3/.../ChatSceneController:452` 每帧强制刷 | ❌ 绕宿主补丁 | 删除（根因见下） |
| `TestPlaygroundHost:88`、`config/ui/ConfigScreen:399` 构造首刷 | 宿主重复样板 | 随 A4 收进统一装配 |

**立法**：宿主 render 栈外禁止 `runtime.flush()`；用现成探针 `frameFlushCount`/`MAX_FRAME_FLUSH_BUDGET=6`（`SceneFramePipeline:93,131,227,598`）对 HUD 帧做预算断言。
**顺带破自锁**：现状"空窗跳帧（`SceneHudHost:112`）→ 构造首刷后 effect 永不再物化 → 树恒空 → measure 0 → 永久空"，chat3 的强制 flush 是给这个缺口打的补丁。**修法是把"flush 照常、paint 跳过"写进宿主合同**，而不是保留补丁。
**措辞纪律**：本项"每帧一次"定义为**每帧一个全局 flush 事务、事务内含多轮**——`settleLayoutObservers` 的有界收敛（`MAX_LAYOUT_OBSERVER_SETTLE_PASSES=3`，每轮 flush）不得被误读为违规。
**残余（另案，不搭本车）**：`SceneRuntime.flush()` 直托进程级 `ReactiveScheduler` 单例是 `O(N²·E)` 与跨窗口物化顺序依赖的真根因；owner 分区属 scene 内核独立立项。

### A3 输入仲裁：2 套 → 1

**删** `SceneProjectionComposition`（556 行）+ 其测试（623 行），净删约 1179 行；`UI投影宿主语义.md` 的 U0/U1/U2 改写为：语义规范保留、实现已废弃、复活触发条件＝本文第 1 节末段，并把"双重唯一 drain 者冲突"记为复活前必须解决的前置问题。
**注**：`SceneProjectionComposition` 是输入语义的活规格，删除前须确认 `UI投影宿主语义.md` 已承载其全部语义条款，避免规格随实现一起消失。

### A4 度量适配器与管线装配：2 处 → 1（统一装配）

| 重复点 | 现状 |
|---|---|
| measurer 装配 | `SceneHudHost:46` 与 `AbstractSceneHostWidget:69` 同写 `new TextMeasureServiceSceneAdapter(DefaultTextMeasureService.getInstance())`，其中基侧**硬连单例不可注入**（HUD 侧可注入，`SceneHudHost:50-58` 包内构造 + 测试 `SceneHudPipelineTest` 靠它传 `MEASURER`） |
| 五件套组装 | `SceneHudHost:221-224` 与 `AbstractSceneHostWidget:70-75` 语义重合 |

**聚合到**：scene core 一个唯一装配点（`SceneHostAssembly` 工厂，或给基类加带 measurer 的 protected 构造重载）。
**两个真缺口**（统一装配必须补，否则合不了）：① 基类 render 不暴露 `windowClip`（`SceneFramePipeline:187` 的 8 参重载目前只有 HUD 用）；② 基类 measurer 不可注入。
**注意**：`SceneHudHost` **不 implements `UiSurface`**（`SceneHudHost:38` 是纯 `final class`），所以这不是"接口不统一"问题，只是装配样板问题；**不要用继承合并**（会连 `InputSurface` 一起继承，见 A7），用组合/工厂。
**测试影响**：`SceneHudPipelineTest` 有 11 处 `new SceneHudHost(...)` 构造调用，签名变动即编译碎裂（可控，需同步）。

### A5 渲染出口组装：3 处 → 1

`new UiRenderContext(...)` 出现于 `UiHudRenderListener:111`、`McScreenBridge:178`、`UiHostRenderSupport:105`。
**聚合到**：`UiHostRenderSupport`（它本就是渲染出口组装的归属）。零公共 API 变化。

### A6 外壳视觉决策：还给内容树（breaking）

`SceneHudHost:227-231` 用 `if (isChrome) { setPadding + setBackgroundColor(HUD_SHELL_BG) }` 决定内容外观——宿主越权管视觉，实现只有 4 行，但 `chrome` 是"投放合同的第一个视觉布尔"，未来会引来 shadow/blur/圆角等同类堆叠（`HudSpec` 退化成特殊编码集中营）。
**聚合到**：外壳是内容树自选（`SceneChromeTokens` 已提供 token）。**宿主只保留三件事：clip、放置、空窗隐藏。**
**净效果**：`HudSpec` 8 字段 → 5（同时把 `minWidth`/`maxWidth` 移出——那是内容 `Constraints` 语义，不是"放在哪"）。
**迁移**：`chrome(false)` 唯一用户是 chat3（`ChatHudWindow:44`）；`chrome(true)` 用户需把外壳写进内容树。**与 A7 有耦合，先做 A6 可让 chat3 只迁一次。**

### A7 输入能力面：拆，不是并（本期唯一结构性 breaking）

`UiSurface` 7 方法中 5 个是输入旁路（`onKeyTyped`/`pushText`/`setExternalTextMode`/`onPointerButton`/`setExternalPointerMode`），3 个生产实现者（`ConfigScreen:85`、`ChatInputSurface:40`、`TestPlaygroundHost:44`）无差别继承。
**聚合方式**：**拆接口**——`SceneSurface`{render,dispose} + `InputSurface extends SceneSurface`{+5 旁路}；`AbstractSceneHostWidget` 实现 `InputSurface`（行为不变），消费方（`McScreenBridge` 等）按是否驱动输入取窄面。
**这是本方案唯一"以拆达成简化"的项，也是最容易看漏的：简化常常靠拆不靠并。**

### A8 诊断与死配置清理（顺手，纯删）

- 13 处"验证后删除"临时诊断零台账：`SceneHudHost:60-64,104-111,118-132`、`UiHudRenderListener:81-82,90-93`、`ChatSceneController:454-535,985-986`、`ChatInputSurface:137-153,188-190`。已核实**删除不影响任何测试**。
- `HudScaleSetting`：**死配置**——生产侧零 `set()` 写入口（仅测试构造），scale 恒 `1F`，但宿主每帧仍走 `width/scale` + `backend.scaled(scale)`。定案：接配置入口，或删缩放分支。
- `HudTokens`：5 个字段外部引用为 0（`fontSize`/`lineBox`/`lineHeight`/`progressHeight`/`MAX_EMPHASIS_FONT_SIZE`）；活字段仅 `paddingX`/`paddingY`/`minWidth`/`STACK_GAP`。删死字段。
- `ClientHudServiceImpl:26-31` `assertClientThread()` 在 `minecraft == null` 时静默放行，改判失败。
- `UiHudRenderListener:103` 每帧 `debugScreenName.set()` 向全局 `pendingWrites` 入队，改值变化才 set。

## 5. 未验证项与真机回归清单（不得以 build 绿代替）

本方案是**静态分析产物，未执行任何运行态验证**。B1 起每批落地需真机回归：

- 多窗口四角堆叠（≥3 窗口/角，验 stackOrder/margin/`STACK_GAP`/safeInsets 与硬裁剪）——**当前该语义零测试覆盖**，是本仓已知缺口，A1 改动前后必须真机看。
- chat3：HUD ↔ 输入屏切换、开合动画、闪烁/残影（历史重灾区），A1/A2 直接触碰其驱动与 flush。
- `HudScaleSetting` 定案后：scale 各档同一 HUD 的宽度口径（现状接线层灌物理 px、宿主按逻辑 px 约束——scale 恒 1 故不可达，一旦接入即引爆）。
- F3/debug 共存、世界卸载与断线重建（`clearWorld` + registration 保留承诺）。
- HUD 无自动化视觉基线，视觉类改动只能靠截图/录屏对拍。
