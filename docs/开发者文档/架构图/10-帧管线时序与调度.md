# 帧管线时序与调度：SceneFramePipeline 重构规划

> 状态：**全部实施完成**。阶段 1（7cfbebe1）+ 阶段 2（3d01ca6 / 37dfddef / 1cdb0e62 / 4921f2ff；2-4 随阶段 1 提前完成）；阶段 3 已批两项：dismiss 同帧生效 + motion flush 合并进 SETTLE（最新提交）；settle 上限策略化未批未做
> 素材基线：源码实时状态（2026-08-18），行号以撰写时为准
> 关联：`01-scene渲染管线.md`（现状 L1 数据流）、`07-线程与所有权.md`（render tick owner）
> 前置约束：本方案触及 scene 宿主管线这一核心架构边界，依 AGENTS.md 高影响边界条款，**实施前须取得用户确认**

## 一、背景与动机

现状一帧的真实时序协议全部内联在 `AbstractSceneHostWidget.render`（114-164 行）一个方法里，
顺序正确性依赖注释与工程纪律（架构图 01 明言「顺序不可调换」，但没有机制阻止调换）。
四个历史时序 bug（见第三节）全部是这个接缝的产物。

本规划把隐式顺序协议建模为显式帧管线状态机 `SceneFramePipeline`，让：
顺序有载体、反馈环有状态、flush 有单点、桥接有归属、协议可单测。

### 2.3 三个嵌套循环

1. **reactive 不动点**：`ReactiveScheduler.flush`(122) drain-writes / run-effects 双通道交替到不动点，
   `MAX_FLUSH_PASSES = 1000`(49) 防御 effect 循环依赖；一帧一事务（I9）。
2. **layout observer settle**：`settleLayoutObservers`(170) 外层循环，
   `MAX_LAYOUT_OBSERVER_SETTLE_PASSES = 3`(42)；每轮 bridgeEpoch + flush + 探脏 + relayout + layoutOverlays。
   超限后「保留下一帧」——**没有显式状态机**，靠脏标记存活隐式延续。
3. **overlay anchor 两遍 layout**：`layoutOverlays`(209) 先 layout 取 contentHeight(227-229) →
   `SceneAnchorResolver.resolveAuto` 定锚 → 正式 layout(241)。per-root 引擎 + per-root 结果
   散落在 host 两个 `IdentityHashMap`(64/76)。

### 2.4 flush 点散落三处

- render 主流程(128)（route 写入）
- `SceneRuntime.__sampleMotion`(383-395) 内嵌 flush(389)（motion completion 新 effect）
- `settleLayoutObservers` 每轮(173)（layoutDoneSignal 驱动 observer）

## 四、目标与非目标

**目标**
1. 顺序协议显式建模：16 步 → 命名阶段（FramePhase），阶段间前置条件可断言
2. settle 跨帧状态显式化：SETTLING / DEFERRED 状态机取代「脏标记隐式延续」
3. flush 单点授权：管线是唯一 flush 调用点，审计标签联动 TransactionLog
4. epoch 桥接与 overlay 簿记内聚进管线
5. 管线级可测试：PipelineDriver 单步驱动，4 个历史 bug 转成管线级回归
6. 阶段断言锚定不变量（paint 前无脏、无未 flush 写入）

**非目标（明确不做）**
- 不改一帧对外行为（阶段 1/2 行为等价重构）
- 不改 reactive 调度器语义（双通道不动点、一帧一事务保留）
- 不启用并行（SceneParallelExecutor 预留不动）
- 不做 ECS/DOD 化、不改控件 API、不改 public 兼容承诺
- 不改 `AbstractSceneHostWidget` 公共方法签名（render 五参签名不动）

## 五、目标架构设计

### 5.1 FramePhase 阶段模型

```java
public enum FramePhase {
    INPUT_DRAIN,          // drainFrame → FrameInput.frame
    LAYOUT_PRE_ROUTE,     // L1 + layoutOverlays
    ROUTE,                // 空帧跳过（内部判断）
    FLUSH,                // F1
    MOTION_SAMPLE,        // 采样；completion 置 needsFlush 标记（不再内嵌 flush）
    LAYOUT_POST_FLUSH,    // 若 needsFlush 先补 flush，再 L2 + layoutOverlays
    SETTLE,               // 跨帧状态机（见 5.3）
    HOVER_RECONCILE,      // B8
    DISMISS_INVISIBLE,    // 只读几何 → requestDismiss
    PAINT,                // 只读，产 PaintPlan（前置断言：无 layout 脏、无未 flush 写入）
    REPLAY                // 主树 + overlay bottomFirst
}
```

每阶段返回 `PhaseOutcome { PROCEED / NEEDS_FLUSH / DEFER_NEXT_FRAME }`，管线按结果推进。
阶段执行顺序由 `nextPhase()` 表驱动（switch 表，非虚调用链，保证零额外分配）。

### 5.2 SceneFramePipeline 类

- 位置：`ui.scene.host`（与 AbstractSceneHostWidget 同包；不依赖 MC/GL，守 scene core 平台无关）
- 字段：runtime / layoutEngine / paintEngine / replayer / measurer / inputSource 引用 +
  `FrameInput`（root、w、h、absX、absY、ctx、frameTimeNanos）+ `SettleState` + `OverlayLayoutBookkeeping`
- **生命周期**：宿主构造时创建，每帧复用，禁止每帧 new（守性能）
- 每阶段耗时直接喂既有 `UiPerformanceMonitor.recordPhase`(62)——现有诊断页自动获得分阶段数据，无需新设施

### 5.3 SettleState 状态机（本规划核心）

```java
final class SettleState {
    enum Mode { IDLE, SETTLING, DEFERRED }
    Mode mode = Mode.IDLE;
    int pass;              // 本帧已收敛轮数 0..MAX_SETTLE_PASSES
    boolean mustRunNextFrame;   // DEFERRED 显式化：下帧无条件进 SETTLE

    // SETTLE 阶段推进：
    //   bridgeEpoch → flush → hasPendingLayoutWork?
    //     否 → SETTLED（回 IDLE）
    //     是 → pass+1 < MAX ? 继续 relayout 循环 : mustRunNextFrame=true（下帧必跑）
}
```

与现状差异点：现状「超限保留下一帧」依赖 `selfLayoutDirty/descendantLayoutDirty` 脏标记存活；
显式化后 DEFERRED 是管线自己的标志，**即使脏标记被后续 flush 清零，下帧也保证进 SETTLE**——
消除了「settle 是否会发生」的隐式性（row-rekey 类 bug 的根）。

### 5.4 flush 单点授权与审计

- 管线私有 `pipelineFlush(String label)` 是唯一 flush 调用点；调用前 `labelNextTransaction(label)`
  联动 TransactionLog：`"frame.route"`、`"frame.motion"`、`"frame.settle-pass-1"`…审计价值直接落地
- `SceneRuntime.__sampleMotion` 移除内嵌 flush，改为返回 `motionNeedsFlush` 布尔；
  管线在 LAYOUT_POST_FLUSH 阶段入口统一补 flush（行为等价：completion 的 effect 仍在 layout 前物化）
- 注意保留 `ReactiveScheduler.flush` 的可重入保护语义（flushing 时静默 return，123-124）——管线连续调用不得依赖其生效

### 5.5 epoch 桥接内聚

- `__bridgeLayoutEpoch` 从 `SceneRuntime` 公共面移除，逻辑迁入管线 SETTLE 阶段内部
- `layoutDoneSignal` 仍由 runtime 持有并只读暴露（`ReadableSignal<Integer>`），
  **写入所有权归管线**——把「epoch（引擎层，纯 int）→ signal（响应式层）」的唯一转换点收进调度器
- 过渡期：`__bridgeLayoutEpoch` 标记 deprecated 保留一版，管线内部不调用

### 5.6 overlay 簿记内聚

- host 的 `overlayLayoutEngines` / `overlayLayoutResults`(64/76) 两个 IdentityHashMap 迁入管线私有
  `OverlayLayoutBookkeeping`：per-root 引擎缓存、anchor 两遍 layout、activeRoots 清理逻辑整体搬迁
- host 只剩 `getLastLayoutResult()` 等只读探针

### 5.7 阶段断言（不变量锚点，测试/debug 开启）

| 断言 | 位置 | 把哪条注释变机制 |
|---|---|---|
| 无未 flush pendingWrites | PAINT 前 | 「paint 只读 signal，绝不写」 |
| hasPendingLayoutWork == false | PAINT 前 | 「flush + settle 后布局收敛」 |
| flush 计数 ≤ 预算（干净帧 ≤2，脏帧 ≤4，按真实 trace 定标） | 帧末 | 「flush 点收拢」防回归 |
| REPLAY 后 backend GL 状态恢复 | 帧末（仅 debug） | replay 契约 |

### 5.8 host 瘦身后形态（草图）

```java
public void render(int w, int h, UiRenderBackend ctx, int absX, int absY) {
    FrameInput in = frameInput.reset(getRoot(), w, h, ctx, absX, absY, System.nanoTime());
    pipeline.run(in);   // 16 步全部在管线内；frameProbe.tick 移入管线 INPUT_DRAIN
}
```

子类兼容：现有两个 render 覆写（SceneFboPerfHostWidget:143、SceneStressTestHostWidget:92）
均为 `super.render` + 后置统计读取，不受影响；基类注释「覆写须调 super」降级为管线内部责任。

### 5.9 PipelineDriver（测试探针）

```java
pipeline.step();                      // 单步推进一个阶段
pipeline.runToPhase(FramePhase.SETTLE);   // 推进到指定阶段
pipeline.settlePasses();              // 读取本帧 settle 轮数
pipeline.trace();                     // phase 序列 + 每阶段耗时 trace（对拍基线）
```

取代现状测试里「双布局对齐宿主行为」的手工协议模拟（row-rekey 教训的直接产物）。

## 六、迁移策略（三阶段，每阶段独立交付）

### 阶段 1：序列容器对拍（零行为变化）

- 新增 `SceneFramePipeline`，16 步原样搬成 phase 方法，顺序 1:1 复刻（含 3 轮 settle、两遍 overlay anchor）
- **不迁任何状态**：settle 仍是局部循环、flush 仍三处、overlay map 仍在 host、`__sampleMotion` 内嵌 flush 不动
- 目的：证明拆帧无损。交付物：全量 build 绿 + 2681 JUnit 绿 + 真机冒烟 + 新增管线冒烟测试
- 建立 **trace 对拍基线**：干净帧 / 脏帧两组 phase 序列 + settle 轮数记录（后续阶段重构前后必须一致）

### 阶段 2：状态内聚（行为等价重构，每步独立提交）

1. SettleState 显式化（DEFERRED 标志；验证虚拟网格滚动场景）
2. flush 收拢 + Motion 返回 needsFlush（审计标签联动）
3. epoch 桥接内聚（`__bridgeLayoutEpoch` deprecated）
4. OverlayLayoutBookkeeping 搬迁
5. 阶段断言上线（测试开、生产按需）
- 每步：全量 build 绿 + trace 对拍与基线一致 + 对应新测试
- 完成后 host 只剩薄壳

### 阶段 3：可选时序改进（每项单独确认，不捆绑）

- dismiss 同帧生效（消除滞后一帧）
- settle 上限策略化（按树规模/是否虚拟化列表定 MAX）
- MOTION_SAMPLE 与 LAYOUT_POST_FLUSH 的 flush 合并评估

## 十一、实施发现与偏差（2026-08-18 补记）

1. **「PAINT 前布局脏」断言在当前协议下不可自然触发**：持续写入的 observer 每轮都被 settle 的
   relayout 消化，超限退出时树实际干净——协议虽隐式但健康。断言保留为防回归护栏（测试正向
   验证不误伤），生产默认关。
2. **`__sampleMotion` 去内嵌 flush 的测试消费面**：全库 62 处采样消费点中仅 2 个 Tooltip 用例依赖
   completion 同帧物化；测试 helper 对齐管线协议（sample 后按需 flush）即修复，业务语义不变。
3. **测试时间基准陷阱**：管线测试推进动画必须全帧统一时间基准（可控推进值），混用
   `System.nanoTime()` 墙钟与可控毫秒值会造成时间倒退、轨道永不完成。
4. **与规划的偏差**：① 阶段 2-4（overlay 簿记搬迁）随阶段 1 提前完成；② 阶段 2-2 的 motion
   补 flush 方案（LAYOUT_POST_FLUSH 阶段入口）被阶段 3-2 取代——completion 由 SETTLE 首轮 flush
   兜底，`motionNeedsFlush` 字段最终删除；③ flush 预算定标：真实最坏上界为
   route(1)+motion(1)+settle(≤3)+dismiss(1)=6（规划预估「脏帧 ≤4」偏低，按实现定标 6）。
5. **测试台移除**：实施期间用户另行批准移除 `/qzuilib test` 演示测试台（devtools/pages 31 文件），
   规划第七节的「14 个 devtools host 页编译」回归项随之失效，以全量 JUnit 与真机冒烟替代。
