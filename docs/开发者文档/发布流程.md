# 发布流程

> 素材基线 2026-08-14。本文件是 Qz-UILib 发布流程的唯一权威：发布前必须先完整阅读本文件，并严格按「发布动作」一节的唯一路径执行。

## 1. 版本真值

- 版本由 git tag 决定（GTNH GitVersion 方案）：构建产物、FML 元数据与 Release 中的版本号都派生自 tag，不手工写版本号。
- tag 命名是 `x.y.z`（如 `4.7.0`），或**预发布形态** `x.y.z-beta.N`（如 `4.11.0-beta.1`）；必须创建为 annotated tag（`git tag -a`）。
- **预发布后缀只允许 `-alpha.N` / `-beta.N` / `-rc.N` 三种**，这不是风格选择而是硬约束：FML 的 `ComparableVersion` 把**未知限定符**（`pre` / `dev` / `sp` 等）排在**正式版之后**——`4.11.0-pre1` 既不落在 `[4.9.0,4.11.0)` 内、又大于 `4.11.0`，会让 `NetworkModHolder` 的 `acceptVersion(自身)` 自检失败（症状见 §2）。`alpha` / `beta` / `rc` 是 FML 已知且排序**低于**正式版的限定符，因此预发布版本号天然落在既有区间的正式版上界之下。
- 另一条链路方向相反：GTNHGradle 内置只认 `endsWith("-pre")`，本仓 `addon.late.gradle` 已覆盖为认 `alpha`/`beta`/`rc`——用 `-pre` 在那条链路上反而会被当成正式发布。
- **预发布通道（蓄水池，2026-09-16 用户裁定）**：中版本级（minor）改动——即向后兼容的公共 API / 能力新增——先进预发布（`4.11.0-beta.N`，N 从 1 递增），积攒到一定量后再一次性定档正式 `4.11.0`。这样功能新增不再占用 patch 号语义，也不必为每一次新增立刻扩张 minor 兼容区间。
  - 预发布仍须**零公共面删除**（与 patch 口径相同）；若某个预发布批次含公共面删除，必须同时按 §2 收紧 `acceptableRemoteVersions`，不能沿用「区间不动」的默认。
  - 含公共面删除的批次仍走 minor（维持 4.9.0 / 4.10.0 的既有做法）；major 只留给不兼容重构。
  - 正式定档的时机由用户决定；定档时按 §2 抬上界。
- 版本号、FML 远端范围与 tag 三者必须一致：`MyMod.acceptableRemoteVersions` 按**本次已批准的兼容承诺**确定，不按 tag `x.y.z` 机械推导区间下界（补丁版本可继续落在既有已承诺区间内：4.9.1 即保持 4.9.0 的 `[4.9.0,4.10.0)`，两端互相接受、可混用；该例中的区间其后已放宽，现值以实时代码 `src/main/java/club/heiqi/uilib/MyMod.java:24` 为准）；发布前按该承诺核对代码常量、制品与发布说明三者一致。

## 2. 发布前准备

以下各项全部完成才允许打 tag：

- FML 远端范围：`MyMod.acceptableRemoteVersions` 按本次已批准的兼容承诺设置，声明为 `[<已承诺下界>,<上界>)` 左闭右开三段式、两端 major 相同——下界取已承诺的兼容下界、上界取高于当前构建版本的下一个边界，两侧占位符必为不同版本，且**必须包含当前构建版本**（区间不含自身时 FML 判定「mod 拒绝自身版本」，症状：启动期 `appears to reject its own version number`，进入世界时集成服务器 `Rejecting connection CLIENT` 后卸载全部维度）。`FmlRemoteVersionCompatibilityContractTest` 二态契约必须绿：**显式空串构成空区间、拒绝一切（含自身），禁止使用**——「精确版本相等」只属于整条属性不写的形态，需要放开限制时整条删除该属性，不写空串。
  - 预发布版本的版本号天然落在既有区间的正式版上界之下（`4.11.0-beta.1 < 4.11.0`），因此**发预发布时 `MyMod.acceptableRemoteVersions` 保持不变**，无需为每个预发布调整区间。
  - **但正式版发布时必须抬上界**（预发布通道引入的新增前置动作，最容易漏）：上界取「高于当前构建版本的下一个边界」，正式 `4.11.0` 发布时上界必须从 `4.11.0` 推到 `4.12.0`，否则区间不含自身、触发上述致命症状。
- changelog：新建 `.changelogs/<tag>.md`，包含「更新」「兼容性与升级动作」「验证边界」三节；「验证边界」只写验证级别、覆盖范围与未验证项——CI run 链接、制品 sha256、本机日志与用例计数属动态证据，由发布 workflow 写入 Release 面，不进 git 文本。同时在根 `CHANGELOG.md` 顶部追加对应版本条目。
- 完整构建：本机执行 `call gradlew.bat --no-configuration-cache build` 必须全绿；定稿提交的分支 CI 必须绿（发布 workflow 会从 tag 不可变 checkout 重跑 test build 自证，不需要为写证据再补一轮 CI）。
- issue 核对：对本次修复过的每个 issue，用 `gh issue comment` 回复修复说明与发布版本号。

## 3. 发布动作（唯一路径，禁止绕过）

1. `git tag -a <tag> -m "<tag>"` 后执行 `git push origin <tag>`。
2. 确保 `Publish Release Assets` workflow 已存在于默认分支；若发布在非默认分支进行，相关 workflow 改动需先同步 cherry-pick 到默认分支并推送。
3. 触发并等待：
   `gh workflow run "Publish Release Assets" --ref <分支> -f tag=<tag> -f confirmation="PUBLISH <tag>"`
   再用 `gh run watch --exit-status` 等待状态为 `completed/success`。
4. workflow 从 `refs/tags/<tag>` 不可变 checkout，依次执行：test build、生成 manifest 校验（manifest.json 仅内部校验用）、上传资产到既有 Release 或创建 Release、校验 Release 4 个资产齐全且已上传。

## 4. Release 规范

- title = 纯版本号（如 `4.7.0`），不带 mod 名前缀。
- notes = `.changelogs/<tag>.md` 全文，发布时标题行改为 `# Qz-UILib <tag>`。
- 资产 = 恰好 4 个 jar：`qz_uilib-<tag>.jar`、`qz_uilib-<tag>-dev.jar`、`qz_uilib-<tag>-sources.jar`、`qz_uilib-<tag>-dev-preshadow.jar`；manifest.json 不作为 Release 资产。
- 正式版：非 prerelease、非 draft。预发布版（`-alpha`/`-beta`/`-rc`）：**必须标 prerelease**、非 draft。
- title 与资产集合规则对两者相同；标 prerelease 的作用是让 GitHub 的 Latest 继续指向最近的**正式**版，避免预发布被外部当成稳定版取用。

## 5. 禁止事项

- 禁止绕过 action 用 `gh release create` 手工造 Release（会造成无资产、notes 不规范的半成品）。
- 禁止本机手工 `gh release upload` 替代 action 产物。
- tag 一经推送不可移动或重打；Release 需要修正时用 `gh release edit`（改 title/notes）与 `gh release delete-asset`，需要重建资产时重跑 `Publish Release Assets` workflow。

## 6. 历史教训

4.7.0 首次发布时，`release-tags.yml` 已被删除且执行者未核对流程，用 `gh release create` 手工造出无资产 Release；随后恢复 `Publish Release Assets` workflow 并重跑补齐资产，再按 4.6.3 规范修正 title/notes/资产集。教训：发布前必须先读本文件，并只走「发布动作」唯一路径。
