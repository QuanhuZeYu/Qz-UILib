# ERROR-20260509-config-template-save-state-rollback

## 错误现象

- `ForgeConfigTemplateScreen` 点击保存后，如果宿主 `saveAndReload()` 或默认写盘流程抛异常，页面会提示“保存失败”。
- 但对应 `Property` 的内存值已经被草稿覆盖，失败后配置对象并未回到保存前状态。
- 对声明了 `validValues` 的字符串属性，如果当前值已经不在候选集中，页面还会把它伪装成第一个选项，导致用户下次保存时静默改写。

## 触发场景

- 配置模板页先把草稿写回 `Property`，再执行保存处理器或 `Configuration.save()`。
- 保存处理器带有运行时副作用，或写盘阶段抛出运行时异常。
- 老版本配置、手工改配置或迁移中的遗留值不再属于当前 `validValues`。

## 根本原因

- 保存流程缺少事务语义：只有“先 apply，再 save”，没有失败回滚。
- 分段选择控件默认把“找不到当前值”当成索引 `0`，把“未知值”错误地映射成“首个合法值”。

## 修复方案

- 在 `ForgeConfigTemplatePropertyDrafts` 中补充属性值快照与回滚逻辑，为“先写内存、后执行保存副作用”的流程提供事务保护。
- `saveDraft()` 改为通过回滚包装执行草稿写回与保存动作；失败时恢复属性值并刷新控件状态，不再把脏状态留在内存里。
- 对离散 `validValues` 属性，只有当前值仍属于候选集时才使用分段选择控件；遗留值改走文本输入，避免静默覆盖。

## 预防措施

- 后续凡是存在“先改模型、再触发外部副作用”的保存链路，都要显式设计失败回滚，而不是只补错误提示。
- 有候选集合约束的表单控件，必须区分“合法首项”和“当前值未知”两种状态，不能用同一个回退索引混淆。
- 纯 JVM 自动测试优先覆盖这类状态事务与遗留值边界，不要只测 happy path。
