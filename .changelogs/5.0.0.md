## 本次更新

本轮是**选择器（SearchPicker）重写**的收口版本：候选源由「全量拉取 + 宿主自行过滤」改为**查询式只读 SPI**，结果区由「全量挂载」改为**窗口化渲染**，面板生命周期由「打开仍算」改为**打开即算 / 关闭即停**，尺寸与密度由「硬编码常量」改为**动态派生**，分级键与图标缓存由「按最后一个冒号切分」改为**候选域键唯一真源**。对外可见承诺不变的是「可滚到底、无加载更多」；**搜索 lane 与浏览 lane 同口径**——窗口总量 = 真实命中数、无窗口上限、可见性 = 惰性分页（本轮 A 方案已撤回原定的「搜索上限 64 + 明示截断」）。

以下按主题分组，每条给「做什么 + 为什么 + 对下游的影响」。

### 1. 候选源 SPI 与四代际失效（P2-A）

- **做什么**：新增查询式只读候选源 SPI——`club.heiqi.config.ui.editor.PickerCandidateSource`（`size()` / 三段版本号 `version()` / `matchCount(PickerQuery)` / `page(PickerQuery, offset, limit)` / `exact(key)` / `categories(dimension)` / `release()`）、查询条件值类型 `PickerQuery`、`PickerSourceVersion`、`PickerEnvironment`、provider 侧直通接缝 `CandidateSourceValueEditorProvider`、图标源 `PickerIconSource`。
- **为什么**：旧路径的「一次全量 + 宿主侧过滤」在千级候选集上把成本压给了每一帧；查询式只读让「谁持有数据、谁回答切片」成为唯一责任面，`page()` 让窗口化内核有权威切片来源。
- **对下游的影响**：**纯加法**——旧 `ValueEditorProvider` / `CategorizedValueEditorProvider` / `VisualAdapter` / `SearchPickerData` / `SearchPickerCategories` / `SceneVirtualGrid` 的既有成员零删除、零改签名；未实现新 SPI 的 provider 走旧路径，行为不变（T-1 兼容路径）。实现 `PickerCandidateSource` 的调用方须保证「同一 `(query, revision)` 下 `page()` 顺序稳定、分片拼接等于整取、key 无重复」，且全部入口只在客户端主线程调用（非主线程入口 fail-fast，见 `PickerSourceGuard`）。

- **做什么**：四代际失效通道——内容代际（`PickerGeneration`）、注册表代际、图标代际，经 `PickerRevisionBridge` 汇成 SPI `version()` 可读的 revision；`ResourceReloadService`（资源重载广播，F3+T 等）与 `LanguageEpochService`（语言纪元）把「资源/语言热更」变成可订阅信号；`MinecraftMainThreadOracle` 提供主线程判定真源。
- **为什么**：用户工程判据要求「不假定任何静态量，静态快照必须有失效通道」；图标/语言/资源包三者各自独立变化，缺一条通道就会出现「换了资源包但图标仍是旧图」的静默陈旧。
- **对下游的影响**：环境代际**只经** `onEnvironmentChanged` 下行；不推送则 `version()` 必须恒等。下游不需要自己轮询资源包或语言状态。

- **做什么**：图标族收敛为**候选域键**——`PickerIconKey`（`candidate(key)` / `variant(key, meta)`）是分级键唯一生成处；`PickerIconResolver`（候选域键 → 图标，屏级缓存、`release()` 幂等）与 `PickerIconCache`（有界：512 活跃 + 1024 tombstone）；`HostImageSource.itemIcon(ItemStack, String explicitRegistryKey)` 是显式键工厂（键优先，null/空白回落自算）。
- **为什么**：旧 `ItemRenderFallbackKeys.splitRegistryKey` 按最后一个冒号切分，对 `minecraft:stone` 会把方块名当 meta，`parts[0]` 与候选键必不相等 ⇒ 回退集合恒空、UNRENDERABLE **静默失效**。统一为候选域键后解析端不复存在。
- **对下游的影响**：实现 `PickerIconSource` 必须返回候选域键对应的图像源，**不得**覆写 `registryKey()`；变体级第二参数是 meta 令牌（不含 `@`），完整键 `candidateKey@meta` 也接受。调用 `splitRegistryKey` 的下游必须迁移（见「兼容性说明」删除项 3）。

- **做什么**：会话释放账本 `club.heiqi.config.ui.field.PickerSourceLifecycle`（弱引用集合、同实例去重）：`track(source)` 由字段装配点登记，`releaseAll(reason)` 是**唯一释放点**，接在 `ClientProxy.onClientDisconnect` 的断连路径上（经主线程派发，commit `1c196b7c`）。
- **为什么**：候选源按 SPI javadoc 与 P4 常驻范围表属**进程级会话**对象，不得在关屏时释放（否则每次关闭选择器即丢分片/清单快照）；但进程级常驻必须有确定的回收点，否则退出世界再进会带着上一局的清单快照。
- **对下游的影响**：下游自定义 `PickerCandidateSource` 若在 `release()` 里持有可释放资源，退出世界时会被自动调用一次；无需自行接线。

### 2. 窗口化内核（P3）

- **做什么**：新增 `ui.scene.control.SceneGridWindow`（**窗口数学唯一实现**：`compute` / `viewportHeight` / `visibleRowsForViewport` / `windowStartRowForScroll` / `scrollForAnchor`，值对象 `$WindowModel` 与行区间 `$RowRange`）、`SceneItemIndex`（key → 全局下标 O(1)）、`SceneGridSnapshot`；`SearchResultList` 与 `SceneVirtualGrid` 共用同一内核。
- **为什么**：旧路径由宿主自行推导窗口偏移，等于在每个宿主里各写一份窗口数学——两份实现迟早漂移，且「行区间」类型（旧 `SearchResultList$Row`）会把第二份数学固化进下游编译面。
- **对下游的影响**：`Props.items()` 语义由「全量数据」变为「**窗口切片**」；挂载量与绘制命令数与数据规模 N **无关**（只与可视行数 + overscan 有关）；新增 `pageProvider` / `totalItems` / `windowOffset` / `availableWidth` / `visibleRows` / `totalItemsSignal` / `metrics` / `configuredKeys` / `onExitUp` 分量，**全部旧构造器保留**（11/16/17/18 参兼容面）。宿主**不得自行推导窗口偏移**；`Result.windowModel()` 是窗口状态唯一回读通道。不变式（inv-W1..W4）：`windowOffset == windowStartRow * columns`；切片长度 == `min(rows*columns, totalItems - windowOffset)`；`windowOffset % columns == 0`；`totalRows == ceil(totalItems / columns)`（`totalRows` 由 `totalItems` 派生，不得由切片长度派生）。

### 3. 面板生命周期与常驻（P4）

- **做什么**：面板在行构建期只建 Signal 骨架 + open 状态机 + portal 句柄；**全部候选派生计算（filtered / gridItems / categoryRows / memberIssues / clampHighlight / VariantChooser）移入内容 Owner**，随关闭释放；`StructuredListFieldRenderer` 折叠态改为惰性构建。
- **为什么**：旧实现关闭后仍在算（订阅未断、派生未停），「不打开也花钱」是热路径账上最大的一项浪费；把派生归内容 Owner 让「关闭即停算」由所有权保证，而不是靠散落的取消订阅。
- **对下游的影响**：关闭后不再读取候选源、不再产出任何 `picker.*` 派生计数；重复打开复用进程级候选源与缓存，不重建数据面。常驻复用范围 = **同屏 open 开合之间** + 候选源进程级常驻，**跨屏不成立**——不要依赖跨屏缓存。

### 4. 动态尺寸、密度与主题（P5）

- **做什么**：新增 `ui.screen.HostViewportScale`（宿主逻辑盒边界，GUI Scale **只在 host 边界成对换算**）、`ui.scene.layout.LogicalBox`、密度三档 `PickerDensity`（`compact32` / `standard40` / `roomy48`）与 `PickerDensityTokens`（比例/夹取边界唯一常量表）、`PickerMetrics`（含 `$PanelBox`）、`PickerChrome`、`GridMetrics`；网格 stride、图标边长、面板盒、成员卡、变体行、分类行、徽章内边距、触发器图标**全部按「逻辑盒 + 字号 + 密度档」派生**。
- **为什么**：旧实现把布局常量与 6/8 位色值散落在 picker 家族各处，改一档分辨率或字号就会出现「盒子变了、格子没变」的错位；派生唯一实现让「分辨率/缩放/字号/主题任一变化」都走同一条重派生路径。
- **对下游的影响**：密度档位经 `Props.densityPreference`（`ReadableSignal<PickerDensityPreference>`）注入，**切换无需重建面板**；auto 阶梯只降不升。picker 家族内不再有硬编码 6/8 位色值与布局常量（由 `ScenePickerTokenGuardTest` 钉住），下游不要自己抄这些数字，改用 `PickerMetrics` / `PickerChrome`。

- **做什么**：**密度偏好通路**（Lead 侦察发现的能力空洞，`60d33ef6`/`b142fb5f`/`e9e20097`）：配置项 `general.pickerDensity`（auto/compact/standard/roomy，默认 auto）→ 既有唯一回灌点 `ConfigValueBridge.applyGeneral()` → 进程级信号 `club.heiqi.uilib.config.modern.PickerDensityPreferences`（非法值 WARN 回落 AUTO、帧末批处理、不随面板重建）→ 启动期 `club.heiqi.config.ui.field.PickerDensityPreferenceSource.install(...)` → `SearchPickerFieldSupport` 两处构建点接线 → 面板 `rt.bindComputed(逻辑盒 + 字号纪元 + 偏好)` 派生几何。
- **为什么**：`ScenePickerPanel.Builder.densityPreference` 存在但 `config/**` 与 `uilib/config/**` 下 grep 零命中 ⇒ 从来没有装配点传入偏好，面板永远 AUTO，三档密度对用户不可用。这是「动态化」缺口：能力已实现但不可达。
- **对下游的影响**：旧配置零影响（缺省 = auto = 现状）；改档位只重派生、不重建面板。

- **做什么**：`SceneRenderProtocolTokens` 集中非主题静态协议色（「无图」占位色 `0xFF454B54`、hover/选中 alpha、SCRIM 等），SCRIM 两值冲突收敛为 `0xCC121016`；「UNRENDERABLE」与「无图」改为**两种可区分令牌**（前者主题派生 `ItemRenderFallbackKeys.unrenderableTint(rt)`，随主题即时重派生；后者固定协议色）；新增主题语义槽 `SceneTheme.warningSubtle` / `SceneThemes.warningSubtle`（重复徽章）。
- **为什么**：两者此前共用同一个占位色，用户无法区分「这张图确实没有」和「渲染器没准备好」；主题切换时「无图」不该变色、「渲染失败」必须跟着语义色走。
- **对下游的影响**：读主题色的下游请用 `SceneThemes.warningSubtle()` 而不是自己抄色值；协议色不要硬编码。

### 5. 分级键统一与图标缓存（P2-A / P5）

- **做什么**：`ItemRenderTierRegistry.invalidateAll(String)` / `tierGeneration()` / `size()` / `tombstoneSize()` + `$Listener.onInvalidated(String)`，配合有界缓存（`MAX_ACTIVE_ENTRIES` / `MAX_TOMBSTONES`）。
- **为什么**：渲染分级（能画 / 只能画占位 / 完全不能画）会随资源包与渲染器状态变化；缺失效入口就只能重启，缺上界就会随候选集无界增长。
- **对下游的影响**：**有界、可失效、可释放**——下游拿到 icon 后不要长期持有引用跨代际使用，代际变化后应重新解析。

### 7. 框架侧正确性与性能修复（P1）

- **做什么**（`5c3f59b2`）：`measuredTextNodes` 登记表生命周期收口——结构版本号（`SceneNode.__structureVersion()`，`__` 内部桥）+ 确定性剪枝 + 已知根 LRU（容量 8）+ 入口 epoch 快路径；剪枝时同时作废「断开子树 叶→顶」路径的布局缓存。
- **为什么**：登记表此前保强引用且无确定剪枝 ⇒ 反复挂载/卸载后条目只增不减（内存泄漏 + 每帧扫描账）。入口 epoch 快路径把稳态批的登记表账降为 0。
- **对下游的影响**：无公共语义变化；`SceneNode` 的「禁止重写 `equals/hashCode`」禁令在类注释锚定（identity 语义是登记表前提）。

- **做什么**（`f3d768e9`）：`layoutEpoch` 语义拆分——保留 `layoutEpoch()` 为**批计数**（每批 +1，签名与调用方零改动），新增 `SceneLayoutEngine.layoutChangeEpoch()`（仅 `relayoutCount > 0 || constraintRelayoutedNodes` 非空时自增）；`SceneFramePipeline` 的桥接改指 `aggregateLayoutChangeEpoch()`（主树 + 各 overlay 引擎变更纪元**求和**聚合）。
- **为什么**：旧桥把「跑过第几批布局」当「画面已更新」用 ⇒ 干净帧也发布，下游观察者空跑；而「只改绘制」（presentation offset / scroll / transform / opacity）不该步进几何纪元。求和而非 `max`：`max` 会在「主树纪元高、某 overlay 首次变化」时吞掉变化。
- **对下游的影响**：`layoutDoneSignal` / `__setLayoutDoneEpoch` 的语义边界改述为「布局发布」（零几何变化帧不变更，**不是**「画面已更新」）；依赖旧语义（每批必发）的下游需改指批计数 `layoutEpoch()`。

- **做什么**（`dbc15861`）：每帧分配优化——`ReactiveScheduler` 三处 scratch 化 + `dirtyEffectCount` 早退；`PaintPlan` 内部由「绝对坐标命令列表」改为「条目序列」（单命令直接回放、片段回放期叠加偏移）+ `getCommands()` 按需物化缓存 + 公开新增 `PaintPlan.addPlan(PaintPlan)`。
- **为什么**：无工作 flush 仍走全量 effect 扫描、`PaintPlan.getCommands()` 每次物化并复制命令，都是每帧固定开销；HUD 窗口裁剪盒需要「整片包装」而不物化。
- **对下游的影响**：`getCommands()` 返回类型与内容逐位不变、`size()` 口径不变、回放调用序列不变（由回放面等价性用例 + 全量测试背书）；新增 `addPlan` 为纯加法。

- **做什么**（`5e94f89a`）：静止帧剔除 L0 + L3——L0 干净批 O(1) 快路径（判据直接复用引擎自己的 `canSkipClean` 闸门，返回共享常量零变化结果，不建探针集合、不建 `LayoutResult`、不下潜）；L3 裁剪窗口子树整棵剔除（本节点 `isClipWindow()` + 无 transform + 窗口绝对盒与有效祖先裁剪矩形无交集三者同时成立）。
- **为什么**：静态帧仍逐节点下潜与发射命令；视口外的 clip 子树改前也被整片裁掉、一个像素都不落帧缓冲。判据全是树结构与几何的确定性事实，无启发式猜测。
- **对下游的影响**：保守优先（有 transform 一律继续下降；`subtreeContentBounds` 不做剔除）；被剔除时**不清脏标记**，回到可见区按脏标记重发射。下游自定义 clip window 无需改动。

- **做什么**（`dc4c3abb`，U-P5-17）：`SceneNode.setCollapsed(boolean)` / `isCollapsed()` —— **折叠 = 本节点内容退出布局域，自身按零内容叶留在父流中**；折叠子树在布局/绘制/命中/焦点四面同步退出；picker 撤销条改回声明式。
- **为什么**：`ConstraintResolver.priorKnownChildHeight` 对有子容器返回 `UNCONSTRAINED` 是「严禁读子 `cachedLayout`」这条先验铁律的正确代价，不是缺陷。根除方式**不是放宽闸门**（放宽即在未知量上做算术），而是给固定兄弟一条**声明的可知通道**：折叠节点的内容高与先验高同为零内容叶口径 ⇒ **先验 == 实际由构造保证**。等价性由 `CollapsedLayoutEquivalenceTest`（4 例）对「挂摘 vs 折叠声明」整棵可观测树逐值证明。
- **对下游的影响**：纯加法（默认 `false` ⇒ 未声明节点在四个遍历面零参与，逐位不变）。已知取舍：折叠节点自身仍占一个零尺寸槽（gap/margin 照旧，U-P5-20）；折叠子树内「已持焦点」需调用方释放（Tab 环已排除，U-P5-21）。

### 8. 诊断与计数设施（P0-B）

- **做什么**：`ui.diagnostic.UiPerfMarkers`（性能标记名唯一常量表：`COUNTER_FRAME_*` / `PHASE_PICKER_*` / `COUNTER_PICKER_*` / `COUNTER_IMAGE_ICON_CREATED`）、`UiPerformanceMonitor.recordCounter(String, long)` 与 `MAX_SCREEN_HISTORIES`、`UiRuntimeStats.getCounterSummary()`（含 27 参构造器）。
- **为什么**：性能判据要能真机采样（`temp/p0_parse_stats.py` 解析），标记名散落各处就无法保证「同一个名字同一个口径」；`useDebug` 关闭时必须零成本（`recordPhase` / `recordCounter` / `beginFrame` / `finishFrame` 均以 `Config.useDebug` 为第一道判断，关闭时不建会话、不分配）。
- **对下游的影响**：埋点是**采样设施**，不构成运行时契约；`picker.lookup.comparisons` **退役**（常量与写入者删除——删除线性查找助手后该计数恒 0，属真空真），替代判据 = 结构判据（计数列表包装下 `get` 调用数 == 0）；`picker.list.totalRows` / `rows` / `cells` 口径重定义为数据总行数 / 挂载行数 / 挂载单元数。

### 9. 交互与文案（P5）

- **做什么**：键盘——`PAGE_UP/PAGE_DOWN` 整页翻页、`HOME/END` 首末项、搜索框 `↓` 进网格并高亮首项、网格首行 `↑` 回搜索框、分类导航可聚焦并支持 `↑↓/HOME/END/ENTER/SPACE`；滚动停止后吸附整行且贴底直接取 `maxScrollPx`；外部点击收敛为 **scrim 单一检测点**；防误删闸口 = **删除即生效 + 5s 撤销条**（至多 1 条 tombstone，按原下标原值恢复；窗口到期 / 撤销成功 / 面板关闭三个释放点）；信息条改为**常驻占位**（消除 hover 出现/消失的闪烁环），并支持点击复制稳定 ID（≤2s 有界反馈）。
- **为什么**：「可滚到底、无加载更多、无加载项数上限」是用户可见承诺，键盘可达性与误删恢复是同批验收判据；scrim 单点检测解决「连点 5 次关 5 次」的幂等缺陷。
- **对下游的影响**：新增注入键 **15** 个（见迁移指引第 2 条）；1080p auto 档可见项由规格表的 120 调整为 **100**（现状 75，仍 +33%；密度红线 R1/R2 判定不变）。

### 10. P5 静默缺陷修复与断言收紧（P6 Round 4，`e9e20097` / `bc832161`）

- **做什么**：`ScenePickerPanel` 用 `Computed.create(Supplier)` 投影 `widthBudget`/`gridMetrics`，而面板内容在 portal 打开的那次 flush 内构建、`SearchResultList.create` 紧接着**同步读一次** ⇒ `initialMetrics` 恒 null ⇒ 结果网格永久落回退分支（1080p 实测 15 列 / 64px 格 / 图标边长 0，P5 oracle 为 20 列 / 48px / 40px）。修复 = 两投影改 `Computed.create(同步初值, 派生)`（框架标准解法），**不改任何 P5 派生数学/常量/令牌**。同步把「首帧列数 > 1」这条弱断言改为与 P5 同源 oracle 相等。
- **为什么**：这是本轮最重要的发现——P5 的 A1-A8 数学证明全绿（oracle 层正确），而面板测试只断言「首帧列数 > 1」，回退分支恰好给 15 列，弱断言照样通过，缺陷因此长期不可见。
- **对下游的影响**：只提高实际密度（15→20 列、64→48px 格），API 无变化。**框架级通用风险（U-P6D-3）**：凡「flush 内构建 + 下游同步读投影」的装配点都可能踩 `Computed.create(Supplier)` 首帧 `get()` 为 null 的坑，推荐形态是 `Computed.create(初值, 派生)`（`499fa213` 已在 javadoc 写明判据）。

- **做什么**（`f1385d60`，U-P5-13）：滚动条宽度动态派生——`SceneScrollbar$Props` 与 `SceneScrollContainer$ScrollbarSpec` 各新增宽度信号组件 `barWidthSignal`，`SceneScrollContainer.defaultScrollbarSpec(ReadableSignal)` / `createDefault(..., ReadableSignal)` 重载，`PickerChrome.scrollbarWidthSignal` / `scrollbarWidthSignalOf`；picker 四区（`MemberGrid` / `SearchResultList` / `CategoryNavPane` / `VariantChooser`）接入。
- **为什么**：`SceneScrollbar.Props.barWidth` 是构造期常量，而 `PickerChrome.scrollbarWidth(fs) = clamp(round(fs/2), 6, 10)` 早已存在却**无任何装配点**（死代码 = 能力空洞）。诊断确认宽度只影响三处几何（column 命中带宽 / thumb 可视宽 / 圆角=宽度÷2），滚动位置权威源、thumb 高与 Y 派生、失效矩阵、拖动判定全与宽度无关 ⇒ 可做成不动既有语义的**纯加法**。
- **对下游的影响**：旧 12 参 / 4 参 canonical 构造器**以显式构造器保留**（javap 实测两枚并存）；`equals/hashCode/toString` 语义随之纳入新组件——**按值比较**这两个 `Props` / `ScrollbarSpec` 的调用方需要知晓；信号为 null / 值 ≤0 时逐值回落常量口径。

### 11. 背景滤镜档位与玻璃成本优化（性能修复）

- **做什么**：新增配置项 `general.backdropQuality`（`full` 完整＝现状液态玻璃（默认）/ `eco` 省电＝9 抽头变体 / `solid` 关闭＝实色替代底）、枚举 `club.heiqi.uilib.ui.render.BackdropQuality` 与进程级信号 `club.heiqi.uilib.ui.render.BackdropQualityService`（`ConfigValueBridge.applyGeneral` 是唯一回灌点，**不是** `Config` 静态字段——静态镜像会被配置面守卫判为「有键、有回灌、零读取者」的假开关）；库默认主题改按档位动态解析：`SceneThemes.resolve` 的回落级在 `solid` 档取 `SceneTheme.liquidGlassDark().withoutBackdrop()`（实色可读替代），其余档取 `SceneThemes.DEFAULT`，`SceneThemes.DEFAULT` 常量本身不动。
- **为什么**（真机根因，证据链见 `踩坑记录.md` 同日条目）：配置页每帧玻璃规模 26 表面 / 3,652,344 px = **1.76 屏**（Font System 46 表面 / 2.53 屏），每像素 **13 次采样**且抽头数与半径无关；快照跨帧必不复用、每帧重捕；`resolveEffectiveDownsampleFactor == 1` 时 mip 链无人读；玻璃无可见性短路；诊断串每表面每帧无条件构造。用户裁决授权的优化面 = 零观感变化 + 降低模糊核抽头数 + 新增「背景滤镜档位」设置项（默认完整），**未授权**把页壳全屏玻璃降级为实色。
- **对下游的影响**：旧配置零影响（缺省 `full` = 与改前逐像素一致）；档位改动经「配置 → 进程级信号 → 订阅方重派生」生效，**不重建节点**；显式 `SceneThemes.DEFAULT` 常量仍恒为液态玻璃，需要跟随档位的调用方走 `SceneThemes.resolve` / `surface` 系入口；热路径读档位用 `BackdropQualityService.getInstance().current()`（`full` / `eco` / `solid`）。

### 行为变化（必须知晓）

- **`maxItems`「语义反转」已撤回（A 方案，必须通报）**：**搜索 lane 不再有窗口上限**——窗口总量 = 候选源真实命中数 `matchCount(query)`（与浏览 lane 同口径），可见性 = **惰性分页**（`pageProvider` 按 `WindowRequest(offset, limit)` 拉片，单次物化量 ∝ 窗口行数 × 列数，与命中总数 N 无关），SPI 路径 `truncated` 恒 false（截断通道**保留**给旧全量结果路径，信息条优先级不变）。原「语义反转为搜索 lane 窗口上限、默认 64」的方案连同整条取值链（`SearchPickerSpec.maxItems()` → `Registry.register(provider,int)` → `Props.searchMaxItems()`）一并撤回并删除，逐项登记见「明确删除」4–6 与「发布期撤回登记」。修订出处：ADR **§0-R 修订 R-02**（原 R-06 裁决作废）。下游影响：若你此前为配合「64 窗口」给 `searchPicker` / `SearchPickerSpec` 传过上限或覆写过 `searchMaxItems()`，按「迁移指引」第 6 条改签名即可；迁移后搜索返回全部命中、可滚到底、无截断提示。
- **窗口化与生命周期**：`Props.items()` 变为窗口切片；`pageProvider` 由控件按窗口模型调用（宿主不得自算 offset）；`Result.windowModel()` 是窗口状态唯一回读通道；面板关闭后不再做任何候选派生与数据读取（旧行为是关闭仍在算）。
- **`SceneScrollbar$Props` / `SceneScrollContainer$ScrollbarSpec` 的 canonical 扩展而旧签名保留**：record 组件各 +1（`barWidthSignal`）⇒ canonical 12→13 参 / 4→5 参（旧签名以显式构造器并存，javap 实测），`equals/hashCode/toString` 纳入新组件；不传信号时逐值等于既有常量口径。
- **`layoutDoneSignal` 语义**：改为「布局发布」（零几何变化帧不变更），不是「画面已更新」；批计数仍由 `layoutEpoch()` 承担。
- **面板信息条**改为常驻占位（消除闪烁环），1080p auto 档可见项 75 → **100**；密度档位新增三档 + auto 阶梯（只降不升），切换经 `Props.densityPreference` 注入、无需重建面板。
- **已配置候选语义**：SPI 路径**不再排除**「已配置成员」，改为结果单元右上角主题色圆点标记 + 信息条徽章；点击走完全相同路径（重复由成员徽章如实呈现）。若下游依赖旧的「排除」行为（例如自行过滤），需同步移除。
- **库默认主题按背景滤镜档位动态解析**：`general.backdropQuality=solid` 时，未显式安装主题的 runtime 经 `SceneThemes.resolve` / `surface` / `derivedSurface` / 语义色入口读到的是 `SceneTheme.withoutBackdrop()` 实色替代（切换只重派生配方与语义色，**不重建节点**）；`SceneThemes.DEFAULT` 常量**不随档位变化**，仍是液态玻璃语义锚。档位取值 `full` / `eco` / `solid` 三档都不是 YAML 1.1 布尔词，手改 YAML 写裸词可正常读写（第三档原定名 `off` 因是布尔字面量已改名，见 `踩坑记录.md`）。
- **`picker.lookup.comparisons` 计数退役**；`picker.list.totalRows` / `rows` / `cells` 口径重定义（数据总行数 / 挂载行数 / 挂载单元数）；`picker.candidates` 口径 = 真实命中数（搜索 lane 同样取 `matchCount`，不再夹取任何窗口上限）。

1. **版本与依赖**：本版为 major（5.0.0），与 4.9.x **不承诺混用**，需成对升级（下游区间与本地制品同步换件、同批更新 sha256 与字节数）；版本区间常量写法以 `docs/开发者文档/发布流程.md` §1 为准（tag `x.y.z` ⇒ `[x.y.z, x.y+1.0)`）。
2. **文案注入**：本版新增 **15** 个注入键，不注入会回落**英文默认值**——`truncatedResults`、`hoverHint`、`keyboardHint`、`scrollHint`、`densityLabel`、`memberAddingBanner`、`memberEditingBanner`、`removedToast`、`undoAction`、`alreadyConfiguredBadge`、`infoBarIdPattern`（读取访问器 `infoBarIdLabel(label, id)`）、`infoBarCopiedPattern`（读取访问器 `infoBarCopied(id)`）（以上 `SearchPickerPanelPresentation`）；`emptyVariants`、`modeReadOnlyHint`、`emptyCategoryResults`（以上 `SearchPickerPresentation`）。**Miner 侧已全部注入并加反射式完整性守卫**；其他下游照此办理，中文文案可从 `team/P5-成品规格-细目.md` §3.3 取。
3. **已配置候选**：SPI 路径不再排除「已配置成员」，改为显示 + 标记（见「行为变化」）。

7. **删除项**：持有 `SearchResultList$Row` 请改用 `SceneGridWindow.RowRange`；调用 `SearchPickerPresentation.currentMember(...)` 请改用 `currentMemberPrimary/Secondary`；调用 `ItemRenderFallbackKeys.splitRegistryKey(...)` 请直接使用候选域键（本版起不存在解析端）；`SearchPickerSpec.maxItems()` / 两个 int 构造器与 `Values.searchPicker(id,int[,mode])` 见第 6 条签名对照。
8. **面板接线**：提供 `Props.pageProvider`（窗口切片）+ `totalItemsSignal`（动态总量）+ `densityPreference`（密度档位）+ `configuredKeys`（已配置标记）+ `onRestoreCurrent` / `onDiscardRemoved`（防误删闸口），即可获得完整的窗口化 / 动态化 / 撤销体验；不接线时保持向后兼容的默认行为。
