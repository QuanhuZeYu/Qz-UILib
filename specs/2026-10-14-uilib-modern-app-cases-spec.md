# UILib 真实应用案例驱动的新能力目标

状态：规划稿。用户要求参照 Bilibili、YouTube、Gmail 等真实前端案例，使新能力和示例更具参考价值与现代感。本文提出先交付 Gmail 风格收件箱、再进入媒体内容浏览的顺序；具体案例行为是本地应用提案，尚未作为已确认的公共控件合同。

## 1. 目标与推进方式

先形成用户能实际操作、能与真实产品对照的应用案例，再从使用中识别需要补齐的通用能力。页面组织、信息层级、交互密度、状态反馈、键盘可达性、响应布局和长内容效率一起评价，不以换配色或堆控件演示代表现代化。

案例运行在 UILib 正式 scene、信号、标准控件、共同几何及 PaintPlan 上。共享案例从功能广场进入，使用确定的本地内容和业务状态；Desktop 与 MC 可承载同一声明。核心不依赖网页运行时、浏览器或下游业务仓，业务数据不混入核心。

本轮规划替代此前以“只读文字行、单焦点、单选确认”为起点的虚拟列表方案。虚拟化属于支撑案例的候选通用机制，不能反向限制行内操作、复选框、图片或键盘访问。既有核心与模块合同继续有效，新公共能力在所属规格明确后再实施。

采用各产品具体的组织与交互模式，保持每个案例自身一致。界面使用 UILib 自有名称与样本内容，视觉依据从[官方产品页](<https://workspace.google.com/products/gmail/>)及可获得的公开资料取得；不承诺随产品实验变化的逐像素复制，也不推断其内部框架、虚拟化或缓存算法。

## 3. 首期案例：收件箱工作台

### 3.1 用户要完成的操作

用户进入收件箱，按分类或文字查找消息，打开并阅读正文，给消息加星或改变已读状态，勾选多条后归档，再从“所有邮件”或“星标”找到它们。每个按钮有实际本地业务效果，结果来自同一模型，不用固定成功提示模拟操作。

完整邮箱服务、账号登录、真实邮件收发、Gmail 全套搜索语法、推荐算法和网络接入不属于这个前端案例。新消息通过明确的样本事件入口加入本地模型，加载/错误状态只有在该案例实际引入对应异步来源时才增加。

### 3.2 信息结构与视觉

- 顶部是应用标识、搜索和必要的视图操作，主要工作区域保持清晰；返回功能广场的入口可达。
- 侧栏展示收件箱、星标和所有邮件及当前筛选状态；分类与搜索共同确定结果集合。
- 内容工具栏在无勾选时提供结果级操作，有勾选时呈现批量归档、已读/未读及清空选择，区分作用对象。
- 列表行表达复选、星标、发件人、主题、摘要、时间和状态，必要次级动作有明确命中；行主体负责打开阅读内容。
- 阅读区展示当前消息与所属动作。宽空间可使用右侧阅读窗；窄空间切到独立阅读视图并保留返回路径与列表状态。下方阅读窗作为后续布局扩展，不把多种模式同时变成首期门槛。

视觉采用中性应用背景、明确工作表面、细分隔和内容层级。未读、打开、勾选、悬停和焦点分别可辨，不能只靠颜色。紧凑列表不把每行重复装成厚重卡片；主题、字号和窗口变化继续动态生效。图标操作有完整可读名称/提示及键盘入口，不能用难以辨认的字符或过小命中区交差。

采用真实长短混合中文、Latin、时间和摘要数据，按内容决定排版。界面密度是可变视觉策略，不能靠冻结行高、窗口或字体维持正确性。低于页面适用空间时沿核心声明精简/滚动策略并保留退出，不暗中缩字或隐藏关键操作。

### 3.3 业务状态与操作边界

| 状态 | 含义与权威 |
| --- | --- |
| 稳定消息 id | 业务条目身份，与节点 UUID、当前位置和内容文本分开 |
| 当前打开消息 | 决定阅读区内容；与勾选集合、键盘焦点分别管理 |
| 勾选集合 | 决定批量操作；使用稳定 id，不能随排序按位置迁移 |
| 星标、已读、是否在收件箱 | 消息模型事实，所有视图从同一来源派生 |
| 查询和当前分类 | 纯派生结果的输入，不在计算中创建控件或执行业务动作 |
| 焦点、按压和滚动 | 由核心唯一输入/呈现机制维护，业务不另建路由或几何 |

点击复选框只改变勾选，不打开消息；星标只改变星标，不勾选或打开；行主体打开当前消息，本案例选择在打开时标为已读。批量动作只作用于当前查询/分类下已勾选的消息；查询或分类改变时清空勾选并更新工具栏。结果级全选只选当前结果集合，部分选择有独立可辨状态。

归档使消息离开收件箱，仍可在所有邮件及适用的星标视图找到。操作完成清空本次勾选，结果和计数从模型重新派生。当前打开消息因归档离开结果时，阅读区继续显示该有效消息；真实删除目标时阅读区显示明确空状态，不默认打开邻行。

新消息、同 id 内容更新或排序变化不夺取焦点、不误改勾选或重新打开其他消息。普通更新沿既有身份与输入合同；按下后删除/失活目标，尾部不触发占据旧位置的后来消息。主体操作与独立子控件分别进入同一 router，不能靠整行 onClick 冒泡同时执行。

键盘首先沿既有 Tab/Shift+Tab、标准按钮激活、编辑和 ESC 合同。查询框保留正式输入/组字行为；批量工具和行内动作可达。Gmail 的[快捷键](<https://support.google.com/mail/answer/6594?hl=en>)是参照，不默认把其所有字母快捷键接管到页面或搜索框。

### 3.4 状态保留与生命周期

切换列表/阅读布局保留本次查询、分类和阅读对象，普通宽度变化不重建整页。功能广场切出时沿既有页面保留政策卸载输入与挂载订阅；返回消费当前状态，不恢复旧手势。关闭整个案例释放所属业务模型、页面树及资源；调用方明确共享的来源按核心所属合同保留。

## 4. 框架能力从案例中提取

| 案例需求 | 优先复用 | 已识别的设计工作 |
| --- | --- | --- |
| 搜索、文字、动作与状态更新 | SceneTextField/SceneEditState、SceneLabel、SceneButton、Signal/Computed | 页面组合及业务语义 |
| 稳定行增删重排 | NodeBinding.repeat、Owner、现有动态结构 | 区分当前打开、勾选、行输入目标 |
| 复选与全选部分态 | 标准控件与唯一输入路由 | 当前 core 目录未发现正式复选框；需设计可复用选中/未选/部分态，归标准控件规格 |
| 次级图标操作与提示 | 标准按钮、正式图像/绘制和所属层 | 先验证既有组合；存在实际缺口时补通用图标按钮/提示，而非案例专用输入 |
| 列表与阅读窗 | 普通布局、尺寸策略、滚动及正式控件扩展 | 响应式组合；不预建通用 docking/workspace 框架 |
| 长交互列表 | 现有有效测量复用、滚动、共同几何和性能广场 | 取得行为参照与热点后，设计支持真实行子控件的虚拟集合 |
| 媒体卡片 | SceneImage、SceneGrid、SceneLayer | 第二案例沿实际图片/卡片状态反馈评估 |

公共控件新增语义写到所属模块规格，不以 gallery 实现另立核心合同。案例业务模型、邮箱和媒体策略留在案例层。虚拟化若进入实现，必须维护独立行内操作、导航、业务状态与所有权，不能把案例降为只读行或统一列表焦点来绕开问题。

## 5. 阶段交付

首期按“操作闭环 → 完整行内/批量操作 → 长内容与发行验证”推进。普通完整列表可作为行为参考版本，不能在大集合已证实不满足使用要求时被当成最终性能交付。首期结论包含真实 Desktop 画面和操作证据，以及核心与 Desktop 的长内容测量；必要结构改进从这些反馈选定。

第二案例单独交付内容发现、搜索/分类、加入稍后观看、进入详情和返回的流程，采用本地图片与确定样本。不引入真实视频解码、流媒体或公网推荐。YouTube 为主参照，Bilibili 提供已查证的具体中文组织方式；不把两套导航/状态随意拼成第三套产品。

评论、动态流、图片真实异步尺寸、写信编辑及拖拽均在对应案例明确用户目标后再立项。案例完成条件独立，后续路线不扩大首期交付范围。

## 6. 首期验收

| 操作 | 用户可观察结果 |
| --- | --- |
| 查找消息、打开、返回列表 | 当前正文正确，查询/分类和列表状态延续 |
| 勾选、星标、点击主体 | 只执行各自动作，打开/勾选/焦点不混为一个状态 |
| 多选、全选部分态、批量归档 | 目标 id 正确，工具栏及计数同步；所有邮件仍能找到归档对象 |
| 新消息和同 id 更新、排序、查询变化 | 当前数据更新，不误操作位置相同的其他消息 |
| 正在按压的消息退出，随后释放 | 不误打开或修改邻行，下一次完整点击才能操作 |
| Tab、搜索输入、行内工具和阅读区操作 | 都进入正式路由；字母输入不被邮箱快捷键偷走 |
| 宽窄切换、主题/字号/同语言资料重载 | 操作可达、内容与命中一致，无手工刷新或静态尺寸假定 |
| 切出返回、反复打开关闭 | 状态符合所选页面生命周期，挂载订阅不叠加，资源可释放 |
| 相同内容在核心与 Desktop 跑长列表动作 | 目标路径命中，进入/更新/滚动/重排成本与实际处理量分开报告 |

画面验收与业务输入相互印证；浏览器参考图不替代 UILib 字体/像素/宿主证据。新增自动场景只保护真实行为和实际回归，复用统一测试应用。代码交付完成完整 build 与独立审查；MC 未实测时明确范围，不外推 Desktop。
