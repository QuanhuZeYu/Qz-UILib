# UILib 收件箱前端还原目标稿

状态：本期目标已获用户认可并完成实现及验收。依据用户对首期实际 UI 的反馈，目标是尽可能接近参考前端的视觉与使用体验。本文维护本期案例目标，不修改已确认核心合同；新增标准控件合同归所属规格。

## 1. 本期结果

将现有收件箱做成能够与固定 Gmail 前端参考并排审阅的完整应用界面。优先收敛应用比例、字体、邮件行密度、搜索与导航、状态反馈，再完成阅读及响应布局。每个增量交付实际 Desktop 画面；业务测试通过只证明行为，不代替视觉达标。

沿用[现代应用案例规格](<2026-10-14-uilib-modern-app-cases-spec.md>)的搜索、分类、星标、复选、归档、阅读、分页与稳定身份合同。YouTube/Bilibili 内容浏览保留后续路线；本期资源集中到同一收件箱。

## 2. 参照与裁决

主参考选定 Google 官方文章 [The new Gmail user interface is becoming the standard experience](<https://workspaceupdates.googleblog.com/2022/11/new-gmail-user-interface-standard-experience.html>)的完整收件箱图，冻结该图版本。它是 2022 年公开版本，作为明确可复核的视觉目标，不声称已取得当前登录态 Gmail。

[官方导航帮助](<https://support.google.com/mail/answer/11555490?hl=en>)用于结构与折叠行为；[官方产品页](<https://workspace.google.com/products/gmail/>)只补充视觉词汇。营销拼图、骨架示意和不同年份版本不混作同一像素基准。

选择“现有邮箱范围内的高还原”方案：

- 保留参考中的顶部搜索、左侧导航、主工作表面、紧凑行、右端时间及批量工具组织。
- 使用 QZ 自有名称与样本。Gmail 商标、Chat/Meet 轨道、Google 应用侧栏及 AI 面板不装成无效按钮，也不为它们保留空白槽。
- 侧栏主要按钮使用有实际效果的“接收示例邮件”，替代参考的 Compose 业务；该差异在对照中明确登记。写信、草稿、发件箱属于独立业务增量，不靠空壳按钮凑外观。
- 既有三类导航完整呈现，保留当前分类与计数。不给未实现的文件夹或标签贴静态入口。

只换配色无法消除排版与字体差距；完整 Gmail 业务克隆又会分散本期目标。选定范围内尽力还原，省略区域和业务差异逐项公开，不用“风格相似”接受仍明显偏离的布局。

## 3. 当前已观测差距

| 区域 | 当前事实 | 本期要形成的结果 |
| --- | --- | --- |
| 应用框架 | 外层广场标题和操作占独立高区，页面内再次展示标题、搜索及多层工具 | 进入收件箱后呈现完整应用面；返回广场与主题入口并入可达的应用操作 |
| 字体 | 默认候选首先使用 Unifont，当前中英画面有明显像素/等宽观感 | 案例采用随附的现代无衬线中英字体及真实粗体，字号/基线/字重层级一致 |
| 搜索 | 字段标签、输入框及“清空搜索”独立占区 | 顶部整合搜索图标、输入、空态提示与清空动作，聚焦/输入反馈清楚 |
| 邮件行 | 发件人和主题在普通按钮中显式换行，摘要另起整行 | 宽屏为复选、星标、发件人、主题与摘要、时间的紧凑横向结构 |
| 工具栏 | 结果、选择提示、翻页各占一层，批量操作还新增一层 | 同一稳定工具区域按选择状态替换动作；翻页与范围收在右端 |
| 状态 | 高亮主要覆盖主体按钮，整行状态和控件视觉缺乏一致性 | 未读、打开、勾选、悬停、按压与焦点各有明确表达及组合优先级 |
| 图形与表面 | 现有图标为少量线段，表面层级弱，圆角 helper 为整数条带 | 统一轮廓、线宽、填充态、圆角与细分隔，真实像素边缘平滑 |
| 阅读区 | 普通文字竖排，消息头和动作缺乏产品化组织 | 有明确主题、发件人/时间层级和消息动作的阅读面，独立正文滚动 |

当前事实对应首期实际截图及代码，不能外推为字体引擎或所有控件的普遍缺陷。先改变案例声明与资源选择；只有正式组合确实缺少表达能力时才扩展共享能力。

## 4. 职责与复用

页面决定业务组织、响应策略、密度及局部视觉词汇；模型继续持有消息、查询、勾选与打开对象。框架维持文字测量、共同几何、输入与生命周期，宿主提供空间、资源和原生输入。

- 优先组合 SceneNode、SceneLabel 的单行省略、SceneTextField、SceneCheckBox、SceneIconButton、Signal/Computed、NodeBinding.repeat 与正式 SceneControl 扩展。
- 多样式行主体作为一个复合动作参与既有 router，内部文字与装饰不产生多份点击；复选、星标和次级动作保持独立输入目标。共享视觉跟随命中事实，不改变现行 leaf hover/pressed 权威。
- 字体通过 TextStyle 的显式候选或具名来源接入，同一实际 face 用于度量与光栅。为案例随附可分发的无衬线中英资源与许可，不依赖本机微软雅黑路径，也不调整 MC 原版字体替代的全局默认链。
- 形状先扩展 ScenePaintShapes 的正式 RECT/LINE 展开与透明 coverage，继续由 PaintPlan 及共享 replay 消费。业务不直接调用 GL，不引入第二渲染器或窗口专用补绘。
- 不为本案例新建 CSS 引擎、网页运行时、通用 docking 或动画框架。公共样式或图标增量须服务本期真实使用点，并在所属主题规格定义。

## 5. 可见行为

### 5.1 应用外壳与工具

进入收件箱后，顶部应用身份、搜索和必要操作横向组织；返回广场始终可达，开发操作不占主要内容区。左侧分类有统一图标、名称、计数和整行选中表面。宽空间展开，空间不足时采用明确的紧凑导航；极小空间沿既有适用范围与退出策略。

搜索的编辑状态、光标、选择、输入法与提交继续归 SceneTextField/SceneEditState；装饰和空态提示不覆盖真实编辑内容或拦截输入。清空后立即更新当前结果。必要说明通过名称和被动提示表达。

工具栏按当前勾选集合显示实际可用动作。出现批量动作时不向下推整个列表；较窄空间允许工具区自然重排，仍保留范围、前后翻页和每页数量。全选仍是全部当前筛选结果，名称和计数明确跨页范围。

### 5.2 邮件列表

默认桌面列表采用单行主结构：复选、星标、发件人列、主题与次级摘要、时间。发件人和时间列对齐；主题优先取得可用空间，摘要先省略；内容原文和完整可读名称保留。长中英混排与 emoji 沿正式文字服务处理，不手切字符串。

行主体涵盖发件人、主题、摘要及其间空白，整行背景可反馈当前行状态。独立控件仅执行各自动作。页内使用既有自然测量和滚动，密度是最小尺寸及间距策略，不用固定高度截断放大后的文字。

未读使用真实较重字重和可辨状态；勾选有复选标记和整行表面；星标具有明确填充/轮廓差别。打开对象使用独立标识，不能被勾选替代。悬停/按压为临时反馈，键盘焦点轮廓始终可见且不被颜色状态遮盖，鼠标点击保留逻辑焦点但不显示键盘焦点框。

行内“标为已读/未读”保留真实动作；次级操作占稳定槽位，不因悬停改变列宽。只有指针悬停会显现的按钮不可作为唯一键盘入口，键盘聚焦时同样可识别。

### 5.3 阅读、通知及动态变化

阅读窗沿现有宽屏旁读、窄屏独立阅读策略，补齐主题、发件人、时间与可用消息动作。返回保留查询、分类、分页及稳定打开对象；正文独立滚动。归档、删除与旧物理尾部规则沿原合同。

操作完成反馈放入稳定位置或既有被动层，不抢焦点、不改变列表视口。空结果是有明确说明的完整工作表面。

窗口、字号、主题、语言与同语言资源重载通过变化通知更新。浅色先对齐主参考，深色维持同一层级与状态区分；不以特定文本颜色猜测当前主题模式。

## 6. 视觉验收与完成标准

### 6.1 对照方法

每轮保存版本、framebuffer 尺寸、字体身份/资源摘要、主题、数据、操作和截图。Desktop 生产回放是画面结论的来源，设计图或 HTML 只能辅助。

主对照冻结同一数据和视口，保存参考/当前/最终并排图及必要的半透明叠图。只允许预先声明的整图等比缩放、裁剪和区域映射；不同文本内容、商标及省略的外部服务区域可明确遮罩。不能逐区拉伸或把邮件行、工具栏等实际差距遮掉。

逐区检查应用外壳、搜索、导航、工具栏、邮件行、阅读区及状态。几何从真实布局取值，字族和字重从实际 TextLayout/face 取值；像素审阅看字形、边缘、表面和层级。先在参考图标注区域及列/基线，再沿声明映射生成目标标尺；固定目标后，正常字号主要布局边界与标尺的绝对误差以 4 px 内为初始目标，同时报告实际偏差。不得用单一全图相似率或“还原度百分比”盖过可见差距。

### 6.2 首轮设计标尺

以下是标准字号 15 em、1400×900 framebuffer 的起始设计值，服务首轮真实画面校准，属于可变案例策略，不是冻结字体或窗口的核心合同：

| 项 | 起始值 | 动态要求 |
| --- | --- | --- |
| 顶部区域 | 最小高度 64 px | 字体或内容更高时自然增长 |
| 左导航 | 目标宽度 240 px | 随字体及内容边界变化，空间不足采用紧凑策略 |
| 主工具区域 | 最小高度 48 px | 宽屏保持单区，窄屏自然重排 |
| 普通行 | 最小高度 40 px | 高度取实际内容与最小值的较大者 |
| 列表首行起点 | 约 112 px | 标准样本标尺；内容增长后随布局自然变化 |
| 图标与动作区 | 图标约 20 px；行内命中至少 32 px | 随字号与密度策略更新，不把绘制轮廓当作全部命中 |

数值在实施首轮根据冻结参考的区域映射和实际 face 校准，并保留调整理由。后续对照使用固定标尺，不能只修改标尺把差距判为通过。放大字号时单独验证可读与操作可达，不要求维持标准行数。

### 6.3 必交付场景

- 浅色宽屏收件箱：应用比例、单行密度、发件人/时间列与文字层级接近主参考。
- 同一行的未读、悬停、按压、勾选、打开、焦点与组合状态：画面和动作一致，列表不跳位。
- 搜索非空、清空及无结果：输入可用，结果和工具及时更新。
- 批量归档及所有邮件找回：范围正确，通知不挤占主区。
- 宽屏阅读、窄屏阅读返回、长主题与长正文：不重建整页掩盖布局问题。
- 深色、放大字号、较长文案、同语言字体/资料重载：当前页面直接更新，真实字形与命中一致。
- 分页长数据：保持既有有限实例化与完整数据访问，首期真实回归继续有效。

最终交付需要视觉对照结论、既有行为回归、完整 build、独立审查和短小的人工体验步骤。视觉与行为分别给结论；主区域仍明显不符时，本期还原目标未完成。MC 运行结果按实际授权和执行记录单独说明，Desktop 不代替 MC。

## 7. 第二轮深入对齐

用户于 2026-10-15 提供 2504×1469 的实际 Gmail 截图，并明确要求继续深入对齐后部署双测试实例。本轮以该截图替代第 2 节历史图作为主视觉参考；原图 SHA256 为 `827c713411b2b420d782eea3f7e132c287e45290c437aa5f9b782a48bfbe1307`，原始附件与对照留在忽略的验证目录。继续保留 QZ 身份、真实示例收取动作、三个已有文件夹与外部服务省略范围。

收件箱增加真实的主要、推广、社交分类。消息明确携带分类；切换分类清除勾选、回到首分页并结束阅读，当前查询为空时按分类筛选收件箱。搜索覆盖当前文件夹内全部分类；星标与所有邮件也覆盖全部分类，返回收件箱保留选定分类。分类计数及未读提示派生自同一消息来源，归档、更新和接收后立即变化，不设置无效标签或静态徽章。

标准案例字号调整为 14 em，顶部最小 64 px、导航目标宽 256 px、导航条目最小 32 px、工具区最小 48 px、分类区最小 56 px、邮件行最小 40 px。标准宽屏列表首行约 168 px，发件人约 x=332、主题约 x=532；这些是本轮直接从新参考提取的案例起点，随字号与内容自然增长。邮箱嵌入入口保留调用方字号，仍验证显式字体和资源换代。

搜索表面、导航选中、收取按钮、批量选择与细分隔分别使用明确视觉角色；未选复选和星标采用浅灰，工具与导航图标采用中灰。宽屏分类限制在自然内容宽度，剩余空间留在同一表面；窄窗分类自适应分配，完整名称仍可操作。分类与稳定工具区分别占位，勾选切换不改变首行起点。

用户随后提供本机 Chrome CDP 接口并登录 Gmail，授权真实页面对照与动态细节。该页面用于读取实际字体、尺寸、角色色与CSS过渡；私人消息不复制为样本。案例显式组合随附OFL Google Sans与Noto Sans SC，搜索文字为16em/14em相对比例，时间为12em/14em相对比例。主菜单在宽屏切换256px完整导航与72px图标导航，保留消息、搜索、分页与动作身份；窄窗沿紧凑分类。搜索聚焦在约100ms变为亮表面和轻阴影；导航表面约150ms颜色过渡；邮件悬停沿细边和阴影、次级已读动作在稳定槽位约150ms渐显，键盘聚焦立即可见，释放按压仍沿现有输入权威。上述颜色、阴影和渐显只改变绘制，终点恢复静态计划复用，不每帧全量重排。后续导航内部几何过渡按[邮箱真实动效目标](<2026-10-15-uilib-mailbox-motion-spec.md>)与正式有限呈现值绑定实施，几何与命中继续共用同一事实。

验收补充真实分类切换、跨分类查询、分类归档与更新、原参考尺寸回放；以本轮前后相同数据/视口对照及真实像素评估。完整 build 后本地提交，再将同一版本正式主包、core、font-adapter 与测试扩展部署到现有两个 MC 测试实例，备份旧包并核对摘要，保留实例配置。交付两个实例的测试入口与可直接打开邮箱的 Desktop 入口；部署核验、Desktop 运行与 MC 人工体验分别记录。
